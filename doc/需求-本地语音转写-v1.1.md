# 需求：本地语音转写（v1.1）

> 状态：**已实现并真机验证**（2026-09-25）。
> 拍板原文：「① 直接按 candle 实现（量化 small，按需下载）开搞吧」——否决 whisper.cpp（C++）。

## 1. 为什么有这条需求

会话界面的录音按钮（v1.1 会话界面四项）能录、能落盘，但**发不出去**：

实测（2026-09-25，四种入口全打了一遍）：

| 入口 | 结果 |
|---|---|
| `GET /models` 的 `input_modalities` | 合法取值只有 `text` / `image`，**没有任何模型声明 audio** |
| `POST /audio/transcriptions` | 404（没有 ASR 入口） |
| chat 里塞 `{"type":"input_audio"}` | 422（只认 `text` / `image_url` / `file`） |
| `POST /files` 上传 WAV | 400（类型白名单只收 webp/png/jpeg/gif） |

⇒「把录音发给模型」这条腿今天不存在。要做成"说一句话就能干活"，只能**本地转写**：
录音 → 本机出文字 → 文本填进输入框（模型收到的仍然是文本）。**音频一个字节都不出本机**，
这反而比"发厂商"更干净。

## 2. 方案：纯 Rust（candle），不是 whisper.cpp

`whisper.cpp` 是顺着生态惯性写的默认值，与本项目约束冲突：
它要么静态编进 exe（引 cmake + C++ 工具链），要么多带一个 sidecar 文件 ——
两条都破坏拍板的发行形态（**一个可执行文件 + `global/` + `projects/` + `plugins/`**）。
candle 已在依赖里（项目记忆的嵌入模型就是它），`cargo build` 一条命令就位，且
**音频解码不用进 Rust**：WebView 自带 WebAudio，前端 `decodeAudioData` + 16kHz 重采样，
Rust 侧只吃 16kHz 单声道浮点数组。

## 3. 模型格式：踩了三种命名，最后只有一种能用

这一段是本次最大的坑，写下来免得下次再踩：

| 候选 | 格式/命名 | 结果 |
|---|---|---|
| `ggerganov/whisper.cpp` 官方 `ggml-*.bin`（实测 `ggml-small-q5_1.bin`，190,085,487 B，sha256 `ae85e4a935d7a567bd102fe55afc16bb595bdb618e11b2fc7591bc08120411bb`） | 老 **GGML**：11 个 hparams + 文件内 mel filters + 无 score 词表 | ✗ candle 的 `ggml_file` 是**按 llama.cpp 布局**写的（7 个 hparams + token/score 词表），读不进来 |
| 社区 GGUF：实测过 `handy-computer/whisper-small-gguf/whisper-small-Q8_0.gguf`（269,751,136 B，sha256 `9b9c8811bbcc82a7766f0fb0925614bdacb0923b2cc630daeac17108b655b860`） | 是合法 GGUF，但张量名是 whisper.cpp 系 —— **实测到的名字**：`dec.blocks.0.cross_attn.k.weight` | ✗ candle 按 **HF/transformers 命名**取（`model.encoder.layers.0.self_attn.q_proj`）；两套名字对不上，`load` 直接报缺张量 |
| **`Demonthos/candle-quantized-whisper-large-v3-turbo`** | GGUF v2，587 张量，命名与 candle **逐字对得上** | ✓ **采用** |
| `openai/whisper-small` 的 safetensors + candle **非量化**路径（实测 `model.safetensors` 966,995,080 B，sha256 `1d7734884874f1a1513ed9aa760a4f8e97aaa02fd6d93a3a85d27b2ae9ca596b`） | HF 原版权重（fp32） | ✗ **实测跑不通**（见 §6 末）—— 加载得进、解不出 EOT |

顺带否掉的一条：`lmz/candle-whisper` 是 candle 原生格式，但**只有 tiny**（中文效果不够）。

**上表每一条都可以自己复验**（不用信这段文字）：`cargo run -q -p harness-engine --example voice_inspect -- <权重文件> [--try-load]`
—— 它按魔数判格式、打印全部张量名与前若干条，`--try-load` 还会真调一次 candle 看名字对不对得上
（就是对这一条报"缺张量"的）。

**最终模型**：`Demonthos/candle-quantized-whisper-large-v3-turbo`
（453.6 MiB，权重 q4_k + 归一化/偏置 f32，多语种，比 large-v3 快数倍）。

- 为什么不是 small：**没有 candle 原生格式的量化 small**（社区量化版全是 whisper.cpp 命名）。
- 来源：`hf-mirror.com`（`huggingface.co` 本机直连不通；魔搭**没有**这份镜像，已查）。
  两个来源同一 `{file}` 模板 + 逐文件 sha256，换源不许改口径。
- 三个文件：`model.gguf`（475,640,800 B, sha256 `3d8dcbab…`）、`tokenizer.json`（2,710,337 B）、
  `config.json`（1,256 B）。规格编进二进制（`voice-spec.json`），单 exe 自己知道该取什么。

## 4. mel 滤波器：**用官方表，不自己算公式**

我按 librosa（Slaney 归一化）实现过一版，与 whisper 发布的 `mel_filters.npz` 比，
**第一个滤波器的系数就差了 0.5%**（0.024747 vs 0.024863）——形状对、数值不等于对。
这种东西**错了不报错**，只会让识别率悄悄变差、且极难定位。

所以把 whisper 自带的表直接编进二进制（来源 `openai/whisper` 包的 `assets/mel_filters.npz`，MIT）：

| 文件 | 尺寸 | 通道 | 用途 |
|---|---|---|---|
| `voice/mel-filters.bin` | 102,912 B | 128 × 201 | large-v3 系列（当前默认模型） |
| `voice/mel-80.bin` | 64,320 B | 80 × 201 | small / base（用户自带模型也能跑） |

**两份表进 git（共 167KB）是刻意的取舍**：它们不是"模型权重"（不是几 GB 的产物、也不随版本漂），
而是**几十 KB 的确定性常量**；编进二进制省掉一次下载、也省掉"自己按公式算"的风险（上面那 0.5%）。

模型目录里 `config.json` 的 `num_mel_bins` 决定用哪份（`mel::filters_for`），
**要不到的表直接报错** —— 给一个尺寸相近的表会让识别率悄悄变差且没有症状，不值得赌。

单测钉住两套表的"逐行峰值列 + 峰值 + 非零个数"（能抓转置/错位/换表），另加两条
**物理意义**判据（稳定纯音跨帧必须几乎不变、高频音峰值必须落在更高通道）—— 这两条就是抓
§5.1 那个"时间轴被切/错位"的。

## 5. 两个必须机器化的坑

### 5.1 `pcm_to_mel` 恒补到 30 秒 + 布局是 `[mel][frame]`

whisper 官方实现永远补零到 30 秒再编码，于是"按住说一句话"也要付整段 30 秒的编码代价
（实测 3.8 秒中文：**编码 62.6 秒**，RTF 17×，不可用）。而 candle 的编码器是
`positional_embedding.narrow(0, 0, seq_len)`，**本来就支持变长**，所以默认按真实长度编码
（多留 1 秒余量、向上取偶，因为 conv2 的 stride=2）→ **编码 62.6s → 9.0s（6.5×）**。

但这里有个不报错的坑：`pcm_to_mel` 的输出布局是 `mel[mel_bin * n_len + frame]`，
且**帧数恒为 3000**（与给的音频多长无关）。把整块 mel 交给一个更小的 shape，
`from_vec` 会**取前 N 个元素** —— 那不是"截断时间轴"，而是**把 mel 轴切掉、帧轴错位**，
模型于是听见噪声并开始幻觉：中文音频转出 **"Thank you."**。
⇒ 必须自己按布局逐通道切片（`slice_mel`），并有单测钉住（`mel_前端的物理意义…` +
`截断_mel_必须按通道逐行切而不是砍尾巴`）。

### 5.2 缺模型不许静默降级成"没反应"

按需下载（**453MB，绝不自动下**）：没装就点一下问用户"下不下、多大、从哪来"，
进度走 `voice://model` 事件进状态栏；三类状态（没装 / 装坏了 / 没配目录）给三种说法。
转写失败**不能把用户说的话弄丢**：兜底把音频存进项目桶（`<根>/projects/<键>/voice/`）
并把路径告诉用户 —— 永不写进用户仓库。

### 5.3 编码窗口做成**配置项**（不是写死的常量）

见 §6：Trim 与 Full **识别内容一致但不是逐位等价**。既然两个目标（"快" 与 "与官方逐位对齐"）
都合理，就不该由实现替用户选死 —— 于是暴露成 `ruyix.code.harness.voice.window` = `trim` | `full`：

- **默认 `trim`**（快 6.5×，实测识别内容与官方口径一致）；
- **读侧口径是不对称的**：只有**明确写 `full`** 才用 full，其余（空串 / `on` / 拼错 / 大小写混乱）
  一律回落 `trim`。理由：解析意外把用户推进 `full`，代价是**每次转写慢 6 倍**；
  意外留在 `trim`，代价只是"没享受加速"——而它本来就是默认。
- 实现位置：枚举登记在引擎 `ENUM_KEYS`（⇒ 配置表单**自动**出下拉、宿主桥接**自动**按白名单校验，
  不必为此写一行 UI）；宿主在**进阻塞线程之前**读出来（`MutexGuard` 不是 `Send`），
  并用 `Window::from_cfg` 解析。
- 判据：引擎 `window_from_cfg_only_full_opts_in`（8 个坏值逐个回落）+ 宿主桥接用例
  `voice_window_bridges_and_bad_values_fall_back_to_trim` + 真窗口（改 runtime 配置后
  `voice_transcribe` 返回的 `window` 字段随之变化）。

### 5.4 剪静音 + 分段：v1.1 后期补的"能用"那一半（2026-09-26）

**起因（用户原话）**："我们目前用的 400 多 M 的 ASR 模型，语音识别还是很慢，而且一点都不准。
好坑啊，根本做不到豆包那么智能！"

查实之后，责任不在模型 —— 在**只做了最小可跑通的那半条链路**。对照一份"能打"的 whisper 实现，
当时缺的是这六件事（逐条 grep 过，不是印象）：

| 能力 | 补之前 |
|---|---|
| 温度回退（置信度低就升温重试） | ✗ |
| beam search | ✗（纯贪心 argmax） |
| logprob / 压缩率阈值（判"这段在幻觉"） | ✗ |
| **VAD / 静音切分** | ✗（静音也照样喂 → 幻觉） |
| initial_prompt（热词表） | ✗ |
| **长音频分段** | ✗ **>30 秒直接截断只转前 30 秒** |

**"一点都不准"最可能的元凶是最后一条**：说超过 30 秒的话，后半句**根本没被转** ——
那不是"不准"，是**没听**。其次是不剪静音（气口被当语音 → 幻觉）与没有热词（术语/人名必错）。

**本批次补的（第一档，不动运行时）**：

1. **能量 VAD**（`voice/vad.rs` 的 `energy_vad`）：帧 25ms/步进 10ms，噪声底取 20 分位，
   判据 `能量 > max(噪声底 × 6, 绝对下限)`，不足 0.25 秒的碎片丢掉、间隔 <0.4 秒合并（气口）、
   两侧各留 0.15 秒。**两级阈值**：第一级一个语音段都没找到时，说明"静音太少、噪声底落在语音里"
   （实测 40 秒连续说话、静音只占 2% ⇒ 20 分位被语音抬高 6 倍 ⇒ 整段被判成没有人声 ✗），
   这时退回**相对峰值**判据（峰值的一小部分算语音）。取舍明确：
   **宁可多转一段，也不能把用户真说的话判成"没听到人声"**。
2. **分段（先装箱、再切）**：把相邻语音段**并进同一个 ≤30 秒窗口**，只在装不下时**在气口处收口**。
   这里踩过一次：第一版是"一段一窗"，77 秒的十句话变成 **22 个窗口 ⇒ 22 遍编码器**（每遍 5~8 秒），
   用户感受到的"慢"有一半是自己造的 ✗。判据 `speech_bursts_are_packed_into_full_windows`
   钉住"窗口数要接近 总长/30s"。
3. **指标接出来**（`speech_secs` / `windows` / `no_speech` / `avg_logprob`）：`avg_logprob` 是
   "该不该信这句话"的唯一机器判据，界面据此提示"置信度偏低，请核对"；`no_speech` 让
   **静音拒识**与**真故障**分开（以前两者都只有一句"没听出内容"）。
4. **配置项**：`voice.vad`（默认开）、`voice.max_secs`（默认 120 秒，超出**如实标注** truncated）。

**实测（release，同一台机器）**：

- **纯静音 4 秒**：`判为无人声 = true`、0 窗口、文本空 ✓（**旧行为在这里吐 "Thank you."** ——
  这就是"静音幻觉"的直接证据，也是 VAD 存在的理由）；
- **长音频 77.8 秒**（SAPI 合成十句中文 ×2，含句间气口）：**十句全在** ✓ · 3 个窗口 ✓ ·
  `截断=false` ✓ · RTF **3.91×**（303.7 秒；编码 194 秒 + 解码 158 秒）—— 旧行为只有前 30 秒；
- 三段 3~7 秒音频回归：A `帮我把构建命令改成Cargo Build` ✓ · B `这个爆错是空指针…`（同音字依旧）✓ ·
  C `把库存服务的连接池从20改成50然后重启一下服务` ✓（**重复环已消除**）；
- **长音频里"两遍相同内容"没有被误剪** ✓（重复度 ≈ 0.5 < 阈值 0.6）—— 这条特意验了，
  因为"去重尾巴"误剪是它最大的风险面。

**残差（真应用复验抓到的，如实记）**：`strip_repeated_tail` 只治**精确**重复。真应用那次跑出
`…然后重启一下服务` + **一个模糊的第二次**（`然后重吓一下服励`）⇒ 重复度没到阈值、`deduped=0`，
半句车轱辘话留在结果里 ✗。抓到了但**故意不修**：模糊去重（近似匹配）有误剪真文本的风险，
而我手上只有合成音、没有真实录音来验证误剪率 —— 不拿没验过的启发式去动用户的文本。
这条残差与同音字错误（`爆/报`、`登陆/登录`、`日质/日志`）指向同一个结论：**该上"本地出稿 +
LLM 纠错"那一档**（文本本来就要发给模型，零额外隐私成本，恰好能把这半句和同音字一起理顺）。

5. **温度回退（whisper 的 `decode_with_fallback`）**：先贪心；这一段若被判为"没把握"
   （`avg_logprob < -1.0`）或"在打转"（重复度 > 0.6），就升温到 0.2 / 0.4 … 重跑整窗。
   - **现场**：6.86 秒那段音频贪心解出 `把库存服务的连接池从20改成50然后重启一下服务`
     **重复 8 遍**（82 token / 解码 30.7 秒 / 端到端 48.5 秒）。这条**回归**（同一段音频在 v1.1
     早期是对的）说明：分段/剪静音改了喂进去的音频之后，贪心的稳定性会变。
   - **但升温治不了它（如实记，这是我一开始写错的地方）**：六档温度全试完**仍然在环里**
     （端到端 225 秒 / RTF 33× ✗）。环的成因是"前缀里已经有这串、模型顺着继续"
     （没有 KV 缓存、每步重发整段前缀，这个条件被反复强化），**采样打不散**。
     按 token 做 no-repeat 4-gram 拉黑也**不够**：中文重复时 BPE 的边界合并会让 4-gram 变样
     （"服务然后"可能并成一个 token），环照样跑 ✗。
   - **真正管用的是"去重尾巴"**（`strip_repeated_tail`，确定性纯函数）：反复剥掉结尾处
     重复出现的一整块，**留下第一次说出口那句**。分工明确：**打转 → 去重；没把握 → 升温**。
     实测同一段音频：`重复环=1`、文本恢复为一遍 ✓（端到端 61.6 秒 —— 仍有一次升温重跑的代价，
     因为贪心那一档的重复度判据先触发过）。
   - 重复度判据：whisper 用 `len(text)/len(zlib(text))`（> 2.4 判幻觉）。**我们不引 zlib**，
     用 `1 − 唯一 4-gram 数 / 4-gram 总数`（同一目的、口径不同、如实写明）。这里栽过一次：
     第一版写成"最高频 4-gram 次数 / 总数"，8 遍重复环算出来只有 **0.042** ✗（形状错了 ⇒
     指标看着对、实际不报警）。**用真文本当夹具**的单测把两个形状分开了。
   - 采样用**确定性 xorshift**（种子 = 常量 + 步数）：去掉"采样随机"这一处不确定性。
     **但别因此声称"同一条音频每次结果一样"**（我一开始就这么写了，实测打脸 ✗）：
     引擎里的浮点归约受线程调度影响，贪心那一步的 argmax 会被末位抖动翻转 ——
     同一段 6.86 秒音频，引擎探针跑出**一遍干净文本**，真应用里跑出**一遍 + 一个模糊的重复尾巴**
     （`…然后重吓一下服励`，`deduped=0`）。**多线程推理的贪心不是逐位可复现的**，这条要写进文档，
     判据也别建立在"逐字相同"上。

**还没做的（下一档，如实记）**：`initial_prompt` 热词表、beam search、q8_0/medium 换档。
**结构性慢**（不是 bug，是实现形状）：① 解码每步重发整段 token 前缀 ⇒ O(n²)，越啰嗦越慢。
**别写成「没用好 KV 缓存」** —— 我试过增量解码（第一步整段、之后每步只喂新 token + 复用 kv_cache），
**输出直接崩**（3.78 秒音频解出乱码替换符、6.86 秒解出「把」，都跑满 448 步，已回退）。
原因在 candle 0.9.2 的实现：位置编码按**输入长度**从 0 取起（`positional_embedding.narrow(0, 0, x.len())`），
喂单 token 等于把位置重置；它自己的 whisper 示例也是每步 flush ⇒ **这个版本无法增量解码**。
要提速只能 fork 给位置编码加偏移（改依赖、风险高）、换实现、或上 GPU。
② 编码成本与音频总长成正比（77.8 秒音频实测：编码 194 秒 + 解码 158 秒 ⇒ **RTF 4.56×**）。
③ **温度回退的代价**：重复环只被「精确去重」剥掉一部分时，重复度仍超阈值 ⇒ 六档全试
（实测 c 段 decode 55.5 秒 / RTF 10.4×，倒数第一档才被接受）。这条留着可优化，
但压成三档会换来「接受更早、更差的那一档」，宁慢勿错。它们与"本地 CPU vs 云端大模型"的
差距是**两件不同的事**：前者是工程完整度，后者是形态差异（豆包那种智能是云端大模型 +
长音频 + 流式 + 热词 + 专门调优，本地 CPU 上一个 456MB 的 q4_k 追不上，这不是调参问题）。

## 6. 实测数据（真机，本机 Windows CPU / 逻辑核 16）

语料：Windows SAPI（Microsoft Huihui Desktop）合成的中文语音，**已知原文**；
模型 `Demonthos/candle-whisper-large-v3-turbo`（q4_k），release 构建，进程内只加载一次
（**加载 0.34s**，453MB 走 mmap）。

| 音频 | 原文 | 转出 | 编码 | 总耗时 | RTF |
|---|---|---|---|---|---|
| 3.78s | 帮我把构建命令改成 cargo build | 帮我把构建命令改成Cargo build ✓ | 9.6s（Trim） | **11.6s** | 3.07× |

（上表最后一列的三行都是**重构后复验**过的一组；加载 0.34~0.59s，取决于是否首次触碰那 453MB）

**能声称的**：
- 链路正确：4 段中文（含中英混说、数字）**内容全部正确**，1 处同音字（爆/报）。
- **Trim 与 Full 识别内容一致**（同一段音频的字都对上，含中英混说与数字），Trim 快 **6.5~6.8×**。
  **但不是逐位等价**（三臂同框实测纠正过一版过度声称）：Trim 吐 `Cargo build`、Full 吐 `CargoBuild`，
  差在中英边界那个空格。机制可解释 —— 两者的 log-mel 归一化各取**自己窗口内**的 max，窗口不同就会
  让这种边界 token 翻转。所以 Trim 是"**实测不掉字**的加速"：可接受，但**别当成等价替换**。
- 端到端 RTF **2.8~3.6×**（CPU / q4_k / 16 核），即"说 5 秒 ≈ 等 18 秒"。

**不能声称的**（缺口，见 §7）：
- 合成音 ≠ 真人；噪声/远场/口音未测；语料只有 3 句，**不构成准确率估计**。
- 未与 whisper.cpp 同机对比（那需要先装 C++ 工具链）——"candle 比它慢多少倍"**没有数据**。

**否掉的第三条路（同机实测）**：`openai/whisper-small` 的 **fp32 safetensors**（967MB）走 candle 的
**非量化**路径 —— **跑不通**：同一段音频解不出 EOT，一路解到 `max_target_positions=448` 的窗口上限后
崩（`narrow invalid args ... len:449`），第一段就没跑完；而同一段音频走量化 GGUF（turbo q4_k）
文本完全正确、还更快。所以本版本**只支持量化 GGUF**：`asr.rs` 在加载处对这种目录**直接拒绝并写明原因**
（留一个"能加载但静默吐垃圾"的分支就是坑）。顺带说明"量化"在这里不只是省体积，它也是**唯一走得通**的那条。

**口径更正记录（2026-09-25，同日）**：本文件与 `CLAUDE.md` 一度写成"Trim 与 Full **逐字相同**"，
那是**过度声称**。三臂同框实测的真实情况是：Trim 吐 `Cargo build`、Full 吐 `CargoBuild` ——
**字都对，但不是逐字相同**，差在中英边界那个空格（机制见上一节：两侧 log-mel 归一化的 max 取自
不同长度的窗口）。口径已改为"**内容一致 / 实测不掉字**"，并写明**不是逐位等价**。
（教训：一次性对照跑出的"一样"别写成"相同"——前者是内容判断，后者是逐位判断。）

**对照臂（参考实现，不是交付物）**：`faster-whisper`（CTranslate2, small, int8, 单线程）
在同一段音频上：**文本完全正确**（"帮我把构建命令改成 Cargo Build"）、**RTF 0.53×**。
复跑条件（第一次是这么挂的，别重踩）：`HF_ENDPOINT=https://hf-mirror.com`（本机直连 huggingface.co 不通）
**加** `HF_HUB_DISABLE_XET=1` —— 不禁用 xet 时它会去 `cas-server.xethub.hf.co` 取文件并回 **401**，
报错长得很像"模型不存在/鉴权问题"，其实只是网络路径不通。
意义有二：① 证明**音频本身没问题**（否则我会一直怀疑自己的录音）；② 给出"同样正确但快 ~6 倍"
的现实参照 —— 代价是引入 Python/CTranslate2 依赖，破坏单 exe 形态，所以不采用。

## 7. 缺口 / 待拍板

1. **速度**：RTF ~3× 对"说一句话"能用但不算快（5 秒话等 18 秒）。可探索且代价明确的三条：
   ① 等 candle 补 small 的量化生态；② 自建 HF safetensors → candle GGUF 的转换步骤（本版本没做）；
   ③ 接受"只转前 30 秒"。**本版本选"能用且纯 Rust"，速度问题如实记在这里。**
2. **流式/长音频**：**长音频已修**（v1.1 加固）—— 剪静音 + 分段装箱（相邻语音段并进 ≤30 秒窗、只在气口收口），
   77.75 秒十句全转、`truncated=false`；超出 `voice.max_secs` 的部分如实标注。**流式仍未做**
   （说一句等一句的实时字幕没有）；**模糊重复尾巴未治**（精确重复已去重，近似重复抓不到，见 §5.4）。
3. **麦克风权限**：WebView2 的 `PermissionRequested` 未接 —— 真窗口里 `getUserMedia` 被拒时
   前端会原样报 `NotAllowedError`，但**没有在真窗口验过**（需要真麦克风）。
4. **按需下载只在本地验过**：`voice_model_fetch` 的下载路径本机是用 `D:\Models` 里已有的权重验的；
   **从 hf-mirror 真下 456MB + 逐文件 sha256 校验这一条，没有在真机上跑过**（spec 里的
   sha256/字节数是我下载时实测到的真值，但"运行时那条下载代码"没打过真流量）。
5. **mel 表与 torch 口径的常数差**：我的 Rust mel 与 numpy（按 whisper 算法复算）相比，
   整体差一个**常数** ~0.075（≈ 全局尺度差，疑为 candle 的 FFT/hann 与 torch 的口径差）；
   实测转写正确，所以不作为缺陷处理，但**没有做到逐位一致**，这里如实记录。
4. **说话人/热词/标点**：whisper 自带的标点已够，热词（项目术语）未做。

## §8 GPU 加速（A 路线）：可选插件，不是第二套安装

**为什么一直在用 CPU**（报障原话：项目里已有 GPU 探测代码，为什么不用 GPU）：
candle 的设备是**编译期特性** —— 默认构建里 `Device::Cuda` 这个枚举值**根本不存在**，
运行时探测到 RTX 5060 也切不过去。而 `agent/machine.rs::gpu_desc()` 那套 nvidia-smi 探测
**早就在**，它回答的是「这台机器有什么」，不是「这个二进制能用什么」—— 两句话不是一回事。

**设计（一个 exe，两条路）**：
- **设备**：`voice/asr.rs::pick_device(prefer_gpu)` —— 真去 `Device::new_cuda(0)` 试一次，
  失败回落 CPU 并把原因带走；决策表 `decide_kind(prefer_gpu, cuda_built, cuda_ok)` 是**纯函数**（有单测）。
- **探测复用**：宿主 `machine::nvidia_gpu_present()`（**同一套 nvidia-smi，绝不另写第二份**），结果进程内缓存。
- **配置**：`voice.gpu = auto | off`（auto = 探测 + 真试；off = 一律 CPU；读侧只有明确 off 才关）。
- **可选插件**：CUDA 运行时 DLL（cudart / cublas / cublasLt / nvrtc，几百 MB）放 `plugins/gpu-asr/`，
  启动时前置进 PATH；**不放 exe 根目录** —— 保住「一个 exe + global + projects + plugins」的形态。
  该放哪几个 DLL、怎么自查有没有真用上，见**随包附带的 `plugins/gpu-asr/README.md`**
  （模板在 `src-tauri/templates/gpu-asr-README.md`；打包脚本与程序首启写的是同一份，不会漂移）。
- **不许沉默**：实际跑在哪（`device`）+ 没用上 GPU 的原因（`device_note`）一路回报到状态栏。
- 改了 `voice.gpu` 会**重载**模型（权重的设备是加载时定死的，不重载就是「配置改了没反应」）。

**构建**（需要 CUDA Toolkit / nvcc）：
```bash
cargo build --release -p ruyix --features harness-engine/cuda
```

**预注册判据**（装完工具链后跑；判读规则先写死，免得事后挑数据）：
1. `voice_probe` 长音频的 `device` 应为 `cuda`，且**编码 + 解码合计至少降 5 倍**
   （CPU 基线：77.75 秒音频 → 编码 194 秒 + 解码 158 秒）；
2. 文本与 CPU 版**归一化后一致**（「逐字相同」不是判据 —— 多线程浮点归约会让贪心分岔，见 §5.4）；
3. 把 `plugins/gpu-asr/` 改名 ⇒ 必须回落 CPU **且状态栏写出原因**（「可选」要真的可选）；
4. 不带 `cuda` 特性的构建：不请求 GPU 时行为一字不变（今天的门禁已覆盖）。

**缺口（如实）**：本机没装 CUDA Toolkit，`cuda` 分支**只写了、没编译过**；上面 4 条判据**一条都还没跑**。
sm_120（Blackwell）较新，candle 的 CUDA 内核在它上面可能有算子没编 —— 属于「能试，但必须实测才算数」。

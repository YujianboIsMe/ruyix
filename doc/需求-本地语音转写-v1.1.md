# 需求：本地语音转写（v1.1）

> 状态：**已实现并真机验证**（2026-09-25）。
> 拍板原文：「① 直接按 candle 实现（量化 small，按需下载）开搞吧」——否决 whisper.cpp（C++）。

## 1. 为什么有这条需求

会话界面的录音按钮（v1.1 会话界面四项）能录、能落盘，但**发不出去**：

实测（2026-09-25，四种入口全打了一遍）：

| 入口 | 结果 |
|---|---|
| `GET /models` 的 `input_modalities` | 合法取值只有 `text` / `image`，**没有任何模型声明 audio** |
| `POST /audio/transcriptions` | 404（没有 ASR 入口） |
| chat 里塞 `{"type":"input_audio"}` | 422（只认 `text` / `image_url` / `file`） |
| `POST /files` 上传 WAV | 400（类型白名单只收 webp/png/jpeg/gif） |

⇒「把录音发给模型」这条腿今天不存在。要做成"说一句话就能干活"，只能**本地转写**：
录音 → 本机出文字 → 文本填进输入框（模型收到的仍然是文本）。**音频一个字节都不出本机**，
这反而比"发厂商"更干净。

## 2. 方案：纯 Rust（candle），不是 whisper.cpp

`whisper.cpp` 是顺着生态惯性写的默认值，与本项目约束冲突：
它要么静态编进 exe（引 cmake + C++ 工具链），要么多带一个 sidecar 文件 ——
两条都破坏拍板的发行形态（**一个可执行文件 + `global/` + `projects/` + `plugins/`**）。
candle 已在依赖里（项目记忆的嵌入模型就是它），`cargo build` 一条命令就位，且
**音频解码不用进 Rust**：WebView 自带 WebAudio，前端 `decodeAudioData` + 16kHz 重采样，
Rust 侧只吃 16kHz 单声道浮点数组。

## 3. 模型格式：踩了三种命名，最后只有一种能用

这一段是本次最大的坑，写下来免得下次再踩：

| 候选 | 格式/命名 | 结果 |
|---|---|---|
| `ggerganov/whisper.cpp` 官方 `ggml-*.bin` | 老 **GGML**：11 个 hparams + 文件内 mel filters + 无 score 词表 | ✗ candle 的 `ggml_file` 是**按 llama.cpp 布局**写的（7 个 hparams + token/score 词表），读不进来 |
| 社区 GGUF（`handy-computer/whisper-small-gguf` 等） | GGUF，但张量名是 whisper.cpp 系（`enc.`/`dec.` 或 `encoder.blocks.0.attn.query`） | ✗ candle 按 **HF/transformers 命名**取（`model.encoder.layers.0.self_attn.q_proj`） |
| **`Demonthos/candle-quantized-whisper-large-v3-turbo`** | GGUF v2，587 张量，命名与 candle **逐字对得上** | ✓ **采用** |
| `openai/whisper-small` 的 safetensors + candle **非量化**路径 | HF 原版权重（967MB fp32） | ✗ **实测跑不通**（见 §6 末）—— 加载得进、解不出 EOT |

顺带否掉的一条：`lmz/candle-whisper` 是 candle 原生格式，但**只有 tiny**（中文效果不够）。

**最终模型**：`Demonthos/candle-quantized-whisper-large-v3-turbo`
（453.6 MiB，权重 q4_k + 归一化/偏置 f32，多语种，比 large-v3 快数倍）。

- 为什么不是 small：**没有 candle 原生格式的量化 small**（社区量化版全是 whisper.cpp 命名）。
- 来源：`hf-mirror.com`（`huggingface.co` 本机直连不通；魔搭**没有**这份镜像，已查）。
  两个来源同一 `{file}` 模板 + 逐文件 sha256，换源不许改口径。
- 三个文件：`model.gguf`（475,640,800 B, sha256 `3d8dcbab…`）、`tokenizer.json`（2,710,337 B）、
  `config.json`（1,256 B）。规格编进二进制（`voice-spec.json`），单 exe 自己知道该取什么。

## 4. mel 滤波器：**用官方表，不自己算公式**

我按 librosa（Slaney 归一化）实现过一版，与 whisper 发布的 `mel_filters.npz` 比，
**第一个滤波器的系数就差了 0.5%**（0.024747 vs 0.024863）——形状对、数值不等于对。
这种东西**错了不报错**，只会让识别率悄悄变差、且极难定位。

所以把 whisper 自带的表直接编进二进制（来源 `openai/whisper` 包的 `assets/mel_filters.npz`，MIT）：

| 文件 | 尺寸 | 通道 | 用途 |
|---|---|---|---|
| `voice/mel-filters.bin` | 102,912 B | 128 × 201 | large-v3 系列（当前默认模型） |
| `voice/mel-80.bin` | 64,320 B | 80 × 201 | small / base（用户自带模型也能跑） |

**两份表进 git（共 167KB）是刻意的取舍**：它们不是"模型权重"（不是几 GB 的产物、也不随版本漂），
而是**几十 KB 的确定性常量**；编进二进制省掉一次下载、也省掉"自己按公式算"的风险（上面那 0.5%）。

模型目录里 `config.json` 的 `num_mel_bins` 决定用哪份（`mel::filters_for`），
**要不到的表直接报错** —— 给一个尺寸相近的表会让识别率悄悄变差且没有症状，不值得赌。

单测钉住两套表的"逐行峰值列 + 峰值 + 非零个数"（能抓转置/错位/换表），另加两条
**物理意义**判据（稳定纯音跨帧必须几乎不变、高频音峰值必须落在更高通道）—— 这两条就是抓
§5.1 那个"时间轴被切/错位"的。

## 5. 两个必须机器化的坑

### 5.1 `pcm_to_mel` 恒补到 30 秒 + 布局是 `[mel][frame]`

whisper 官方实现永远补零到 30 秒再编码，于是"按住说一句话"也要付整段 30 秒的编码代价
（实测 3.8 秒中文：**编码 62.6 秒**，RTF 17×，不可用）。而 candle 的编码器是
`positional_embedding.narrow(0, 0, seq_len)`，**本来就支持变长**，所以默认按真实长度编码
（多留 1 秒余量、向上取偶，因为 conv2 的 stride=2）→ **编码 62.6s → 9.0s（6.5×）**。

但这里有个不报错的坑：`pcm_to_mel` 的输出布局是 `mel[mel_bin * n_len + frame]`，
且**帧数恒为 3000**（与给的音频多长无关）。把整块 mel 交给一个更小的 shape，
`from_vec` 会**取前 N 个元素** —— 那不是"截断时间轴"，而是**把 mel 轴切掉、帧轴错位**，
模型于是听见噪声并开始幻觉：中文音频转出 **"Thank you."**。
⇒ 必须自己按布局逐通道切片（`slice_mel`），并有单测钉住（`mel_前端的物理意义…` +
`截断_mel_必须按通道逐行切而不是砍尾巴`）。

### 5.2 缺模型不许静默降级成"没反应"

按需下载（**453MB，绝不自动下**）：没装就点一下问用户"下不下、多大、从哪来"，
进度走 `voice://model` 事件进状态栏；三类状态（没装 / 装坏了 / 没配目录）给三种说法。
转写失败**不能把用户说的话弄丢**：兜底把音频存进项目桶（`<根>/projects/<键>/voice/`）
并把路径告诉用户 —— 永不写进用户仓库。

## 6. 实测数据（真机，本机 Windows CPU / 逻辑核 16）

语料：Windows SAPI（Microsoft Huihui Desktop）合成的中文语音，**已知原文**；
模型 `Demonthos/candle-whisper-large-v3-turbo`（q4_k），release 构建，进程内只加载一次
（**加载 0.34s**，453MB 走 mmap）。

| 音频 | 原文 | 转出 | 编码 | 总耗时 | RTF |
|---|---|---|---|---|---|
| 3.78s | 帮我把构建命令改成 cargo build | 帮我把构建命令改成Cargo build ✓ | 9.6s（Trim） | **11.6s** | 3.07× |
| 3.78s | 同上，**Full 窗口对照** | 帮我把构建命令改成CargoBuild ✓（内容与 Trim 一致；差异只在中英边界那个空格） | 68.2s | 74.5s | 19.7× |
| 5.39s | 这个报错是空指针，帮我看看是哪里传进来的 | 这个**爆**错是空指针帮我看看是哪里传进来的（1 处同音字） | 13.9s | 17.3s | 3.20× |
| 6.86s | 把库存服务的连接池从二十改成五十，然后重启一下服务 | 把库存服务的连接池从20改成50然后重启一下服务 ✓ | 16.8s | 21.6s | 3.15× |

（上表最后一列的三行都是**重构后复验**过的一组；加载 0.34~0.59s，取决于是否首次触碰那 453MB）

**能声称的**：
- 链路正确：4 段中文（含中英混说、数字）**内容全部正确**，1 处同音字（爆/报）。
- **Trim 与 Full 识别内容一致**（同一段音频的字都对上，含中英混说与数字），Trim 快 **6.5~6.8×**。
  **但不是逐位等价**（三臂同框实测纠正过一版过度声称）：Trim 吐 `Cargo build`、Full 吐 `CargoBuild`，
  差在中英边界那个空格。机制可解释 —— 两者的 log-mel 归一化各取**自己窗口内**的 max，窗口不同就会
  让这种边界 token 翻转。所以 Trim 是"**实测不掉字**的加速"：可接受，但**别当成等价替换**。
- 端到端 RTF **2.8~3.6×**（CPU / q4_k / 16 核），即"说 5 秒 ≈ 等 18 秒"。

**不能声称的**（缺口，见 §7）：
- 合成音 ≠ 真人；噪声/远场/口音未测；语料只有 3 句，**不构成准确率估计**。
- 未与 whisper.cpp 同机对比（那需要先装 C++ 工具链）——"candle 比它慢多少倍"**没有数据**。

**否掉的第三条路（同机实测）**：`openai/whisper-small` 的 **fp32 safetensors**（967MB）走 candle 的
**非量化**路径 —— **跑不通**：同一段音频解不出 EOT，一路解到 `max_target_positions=448` 的窗口上限后
崩（`narrow invalid args ... len:449`），第一段就没跑完；而同一段音频走量化 GGUF（turbo q4_k）
文本完全正确、还更快。所以本版本**只支持量化 GGUF**：`asr.rs` 在加载处对这种目录**直接拒绝并写明原因**
（留一个"能加载但静默吐垃圾"的分支就是坑）。顺带说明"量化"在这里不只是省体积，它也是**唯一走得通**的那条。

**对照臂（参考实现，不是交付物）**：`faster-whisper`（CTranslate2, small, int8, 单线程）
在同一段音频上：**文本完全正确**（"帮我把构建命令改成 Cargo Build"）、**RTF 0.53×**。
意义有二：① 证明**音频本身没问题**（否则我会一直怀疑自己的录音）；② 给出"同样正确但快 ~6 倍"
的现实参照 —— 代价是引入 Python/CTranslate2 依赖，破坏单 exe 形态，所以不采用。

## 7. 缺口 / 待拍板

1. **速度**：RTF ~3× 对"说一句话"能用但不算快（5 秒话等 18 秒）。可探索且代价明确的三条：
   ① 等 candle 补 small 的量化生态；② 自建 HF safetensors → candle GGUF 的转换步骤（本版本没做）；
   ③ 接受"只转前 30 秒"。**本版本选"能用且纯 Rust"，速度问题如实记在这里。**
2. **流式/长音频**：现在整段转、>30 秒只转前 30 秒并在结果里标注 `truncated`（已如实回报）。
3. **麦克风权限**：WebView2 的 `PermissionRequested` 未接 —— 真窗口里 `getUserMedia` 被拒时
   前端会原样报 `NotAllowedError`，但**没有在真窗口验过**（需要真麦克风）。
4. **按需下载只在本地验过**：`voice_model_fetch` 的下载路径本机是用 `D:\Models` 里已有的权重验的；
   **从 hf-mirror 真下 456MB + 逐文件 sha256 校验这一条，没有在真机上跑过**（spec 里的
   sha256/字节数是我下载时实测到的真值，但"运行时那条下载代码"没打过真流量）。
5. **mel 表与 torch 口径的常数差**：我的 Rust mel 与 numpy（按 whisper 算法复算）相比，
   整体差一个**常数** ~0.075（≈ 全局尺度差，疑为 candle 的 FFT/hann 与 torch 的口径差）；
   实测转写正确，所以不作为缺陷处理，但**没有做到逐位一致**，这里如实记录。
4. **说话人/热词/标点**：whisper 自带的标点已够，热词（项目术语）未做。

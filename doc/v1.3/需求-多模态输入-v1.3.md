# 需求：多模态输入（截图发给 Agent）— v1.3

**归属版本**：v1.3（v1.2 的 LSC 上下文账本/重基线调度不受影响；本需求只加"输入侧"的一条新通道）
**状态**：待拍板（§7 四个点）
**登记日期**：2026-09-28

---

## 1. 一句话

开发过程中把**截图**发进会话是刚需（报 UI bug、看设计稿、让 Agent 对着报错窗口说话）。现在
**一条链路都没有**：能力表里明明写着"能读图"，但没有任何地方能把图送进请求体。

## 3. 厂商事实（**实测**，2026-09-28，`api.deepseek.com`，`model=deepseek-flash`）

不猜，用真密钥打真接口（脚本见 `refactor/mm-probe.py`）：

| 探针 | 结果 |
|---|---|
| `/anthropic/v1/messages` + `{"type":"image","source":{"type":"base64","media_type":"image/png","data":…}}` | **200**，模型**真读图**：给 8×8 纯红 PNG，它 thinking 里写「图像看起来纯色，偏红/橙色…从视觉看为红色或深橙红色」 |
| `/chat/completions` + `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}` | **200**，也读图（蓝块答对） |
| 真截图 1707×1067（PNG 570 KB / base64 761 KB） | **200**，能读出屏幕内容 |
| 随机图 2000×1200（PNG 7.2 MB / base64 **9.6 MB**） | **200** —— 但**往返 84 秒** |
| PowerShell `Graphics.CopyFromScreen` 抓屏 | 本机可用（1707×1067 → 570 KB PNG） |

**三条结论**：① 两条路由都支持，**不需要为读图换协议**（这点和 `web_search` 不同，后者是 `(协议 × 模型)` 二维的）；
② **体积不拒但要缩** —— 9.6 MB base64 能过，代价是 84 秒；③ 抓屏在本机有现成路径（PowerShell，零依赖）。

## 4. 候选方案（图片怎么"进来"）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 粘贴 + 选图**（推荐） | `paste` 事件取 `clipboardData.items` 的 image blob；`<input type=file accept=image/*>` 兜底 | 零新依赖；Win+Shift+S 截图 → Ctrl+V 是开发者的既有肌肉记忆；覆盖"刚需"的 ~90% |
| B. 一键截图按钮 | 宿主抓屏（PowerShell / `Graphics.Capture` / xcap 之类）→ 落盘 → 进待发区 | "一键"体验最好，且能抓**应用自己**（报 UI bug 最常要的就是它）；代价是一条平台分支 + 可能的依赖 |
| C. 拖拽图片文件进会话 | WebView2 的 drop 事件 → 同 A 的落盘路径 | 实现成本最低，但"截图→拖拽"比"截图→粘贴"绕 |

**我的立场**：先做 **A**（真刚需、零依赖、判据最硬），**B 作为紧随其后的增强**（B 的价值在"抓 ruyix 自己"，
这恰好是这个项目最常被反馈的一类问题 —— 但要先拍板是抓全屏还是抓窗口）。C 顺手带上（同一个落盘函数）。

## 5. 图片怎么存、怎么传（关键取舍）

**我的立场：落盘 + 传路径，宿主读盘转 base64，引擎只认 base64 parts。**

| 决策 | 选择 | 理由 |
|---|---|---|
| 附件落哪 | `<便携根>/projects/<项目键>/shots/<ts>-<name>.png` | ① 会话要持久化（重启后还看得到图），图片必须有稳定位置；② v1.0 纪律：**绝不写用户仓库**；③ 引擎侧"只读项目/沙箱"的封闭纪律不用开例外 |
| 谁读盘 | **宿主**（`agent_reply` 收路径，`std::fs::read` + base64 + mime 白名单 + 体积上限） | 引擎保持零文件系统假设；宿主本来就有文件访问权，不必给引擎开 jail 例外 |
| 引擎侧形状 | `ChatMessage.images: Vec<ImagePart { mime, data_base64 }>`；**无图时 content 仍是纯字符串** | 有图才改发 content **数组** ⇒ 既有（无图）请求体**逐字节不变**，v1.2 的前缀缓存与全部既有测试不动 |
| 放哪条消息 | **任务消息（第一条 user）**；历史里旧消息的图保留最近 N 条 | 任务图属于 S 根（v1.2 契约要求它逐字节稳定）；历史图只影响后续轮次的 token 成本 |
| 非读图模型 | **拒绝并说明**，不许静默丢图 | 与 ISSUE-5（模型名 fail-closed）同口径：宁可说"这个模型不支持读图"，也不能假装发过去了 |
| 缩图 | **> 2 MB 自动缩到最长边 ≤ 1600px** 再发 | 实测 9.6 MB base64 要 84 秒；缩图是唯一能同时降延迟与省 token 的手段（代价：可能 +1 个 image 依赖 —— 见拍板点 3） |

## 6. 判据（预注册，实现时逐条落成测试/门禁）

1. **无图路径逐字节不变**：单测钉"无图 ⇒ content 仍是字符串"，防"顺手把所有消息都改成数组"的回归；
   既有 `cargo test`（引擎 442 / 宿主 168）读数逐项一致。
2. **有图路径形状**：两条路由各一条单测，用 `testllm` 的假 LLM 抓**请求体**，断言
   anthropic 出 `{"type":"image","source":{"type":"base64","media_type":…}}`、
   openai 出 `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}`。
3. **能力闸**：`model_caps(model).multimodal == false` ⇒ 带图请求被拒且理由可读（引擎侧）；
   UI 侧附件入口禁用 + 写明原因。
4. **体积**：单张 > 10 MB 硬拒（实测 9.6 MB base64 能过但 84 秒，10 MB 以上没探到边界，取保守值）；
   > 2 MB 走缩图路径并留痕。
5. **持久化**：带图的用户消息存盘再读回，图片字段仍在（`SessionMsg` 声明齐全）；重启后缩略图还在。
6. **端到端真 run**：flash + 真截图，问"这张图里有什么"，回答里出现图里的东西（**用 flash，禁用 pro**）。
7. **门禁**：ui-smoke 新增契约 —— 粘贴入口（`paste` + `clipboardData.items`）、附件缩略图渲染、
   非读图模型的禁用与理由文案、`SessionMsg` 声明了 attachments（防 serde 抹字段）。

## 7. 待拍板点

1. **入口范围**：只做 A（粘贴+选图）/ A+C / A+B+C（B = 一键截图按钮）。
2. **一键截图抓什么**（若做 B）：全屏 / 只抓 ruyix 窗口 / 让用户框选。
3. **要不要自动缩图**（+1 依赖）：我建议**要**（>2 MB 缩到最长边 1600px）；不缩的代价是 84 秒往返
   与几万 token。
4. **历史图保留几轮**：我建议任务图每轮都在（它是 S 根），历史里旧消息的图只留最近 2 条。

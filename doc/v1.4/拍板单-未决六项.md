## 2. 逐项

### A-1 提议步跑在哪 —— ✅ **已拍板 2026-10-08：(A) 会话里由人驱动**

落地：驱动器 `propose <n>` 现在会写一份**牌子** `arms/round-<n>/round-<n>.brief.md` —— 上面有
"上一回合逐任务读数 / 允许自改的面 / 预算 / 门禁 / 不许动什么 / 下一步命令"。人把**那份副本目录**
当项目在 ruyix 里打开、对会话说「照牌子改」即可；**零新机制**（会话、四原语、副本都是现成的）。

**现状**：一轮三步里 **②③ 驱动器已落**（`doc/v1.4/templates/rsi/rsi_round.py`，`plan` / `propose` / `score`
三个子命令 + 12 条自检），P0 尺子（`crates/harness-engine/examples/rsi_bench.rs`，自检 12 条）与
P1 白名单闸（`agent.write_allow` + 5 条单测）也都落了。**① 提议步没有归属** —— 它是这一版唯一需要
"新代码形状"的决定。

| 候选 | 做法 | 代价 |
|---|---|---|
| **(A) 会话里由人驱动**（建议） | 人在会话里说"按上一轮读数改 X"，agent 用现成四原语在**副本**上改；驱动器只负责建副本 / 算 diff / 跑尺子 / 出 patch | 不是自动化，每轮点一次；"递归"停在人这一环（v1.4 本来就这样） |
| (B) `rsi_bench --propose` | 一条命令跑完整轮 | 要先补一个**提示词片段加载点**（`plugins/prompts/**` 现在没人读，P2 §5-4 明说"开了就是改了个没人读的文件"）；且让测量工具兼任驱动器 —— 读数与被测物同源 |
| (C) 宿主加 `rsi_round` 命令 | UI 上点一下跑一轮 | 本单最大的一步，且把 RSI 机制搬进宿主源码 —— 与需求 §4.1「落点在用户侧」直接冲突 |

**建议 A**。理由三条：① 判据 1.1 要求"有可信信号之前不加自动化"，而现在只有一次真跑读数；
② 这一版的骨头是 ②③（读数 / 门槛 / patch / receipt），它们已经落地；③ 判据 5（负样本回归）在 A 下
天然有人验收。

**选错的代价**：选 B 先把一个"没有加载点的面"变成了前置依赖，等于把 A-2 的边界破了个口；
选 C 违反 §4.1，且是本单里唯一会动宿主源码的选项。

**核对出来的好消息（对着代码核过）**：选 A **不需要新配置面**。`agent.write_allow` 不在引擎的
`FORM_HIDDEN`（`crates/harness-engine/src/config.rs:1317`）里，而配置表单是由 `config_schema()`
**驱动**的（`ui/scripts/config.js:106` 只过滤 `ui: true`）⇒ 这个键**已经**会出现在 harness 表单里，
是一个逗号分隔的文本框（`kindOf("list") → "text"`，`config.js:89`；列表的扁平口径就是逗号连接，
见 `config.rs` 的 `flat_value` 注释"列表用逗号连接，与 `coerce` 的分隔符解析对称"）。

⇒ 顺带更正：`doc/v1.4/P1-写入白名单与只读边界-v1.4.md` §5-2 那句「宿主 config 表单暂未列这个键，
手填没有意义」**已经过时**（表单是 schema 驱动的，它自动就列了）。选 A 之前把它改掉，一行的事。

**判据**：跑完一轮，人能凭 receipt 说清"这句提示词 / 这行表为什么改"，且改前读数可回滚。

### A-3 轮数 / 候选数 / 预算硬顶 —— ✅ **已拍板 2026-10-08：3 轮 / 1 候选 / 3600s**

落地：`allow.toml` 三个字段都有了**真默认值**（`rounds=3` · `candidates=1` · `budget_secs=3600`），
其中 `candidates` 是本刀新增并校验（`≥1`，写 0 当场拒）。

**现状（核对到行）**：`rsi_bench.rs` 默认 `DEFAULT_ROUNDS = 3`、`MARGIN_DEFAULT_PP = 5.0`、
`MIN_VALID_RATIO = 0.6`；裁决要求**每条臂**都满足 `round_scores.len() >= ceil(rounds × 0.6)`
（`rsi_bench.rs:1522`，`stats.iter().any(...)` 是**逐臂**判的）。驱动器读 `allow.toml` 的
`rounds`（默认 3）/ `margin_pp`（默认 5.0）/ `budget_secs`（默认 3600）。
**候选数不是配置键**：`propose <n>` 只建一条候选臂，结构上就是 1。

**关键数字（升不升级就看它）**：3 轮 ⇒ `ceil(1.8) = 2` ⇒ **每条臂只允许 1 个无效轮**，
第 2 个就判「不可判定」；5 轮 ⇒ `ceil(3.0) = 3` ⇒ 允许 2 个。P0 的真模型臂实测 **0 个无效轮**
（`评测台-最小形状-v1.4.md` §6），所以 3 轮起步是安全的；一旦出现 A-5 那类假红，3 轮会**立刻**
把整轮打成不可判定 —— 这也是 A-5 值得先拍的原因。

**建议**：3 轮 / 1 候选 / 1h 硬顶（现状默认），把"升 5 轮"写成备用动作（出现无效轮就升）。

**候选数为什么建议 1**：一次改两处，读数变化无法归因 —— 本仓库所有配对实验都是单变量；
2 个候选还要各建一份臂、各跑满轮数，成本 ×2。

**别混两条杠杆**：**轮数**买稳定性（同一候选多跑几遍），**任务数**买分辨率。当前任务集只有 3–4 条
（`评测台-最小形状-v1.4.md` §7 自己写着"只够看大差异"），0–100 分制下一条任务翻转 = 25–33 pp
≫ MARGIN 5 pp ⇒ 单任务层面的胜负**现在量不出来**。想让 MARGIN 有意义，先加任务，不是加轮数。

**判据**：receipt 里 `rounds` / `margin_pp` / `budget_secs` 与 `bench_argv` 一致；无效轮逐条留痕，
且裁决与有效轮数相符（不足 ⇒ 明写"不可判定"，不作数）。

### A-4 驱动器要不要自动跑四个既有门禁 —— ✅ **已拍板 2026-10-08：声明式**

落地：`allow.toml` 的 `[rsi].gates` 是**命令清单**，驱动只跑它、不替人决定跑什么。
裁决「候选更优」之后先过门禁：**任何一条非 0 ⇒ 这一回合不产 patch**，receipt 逐条记 `rc`；
`promote` 再查一遍 receipt 里的门禁（没绿不许进主干）。没声明 `gates` 时如实记空表并提示 ——
那是"**没有证据**"，不是"通过"。

**现状**：`rsi_round.py` 的 `score` **只跑尺子并出账**，没有跑 `cargo test` / `clippy` /
`ui-smoke` / 三个几何探针 ⇒ 判据 4 的"且既有门禁全绿"目前是**人**在合之前核对（P2 §3.1 已如实登记）。

| 候选 | 做法 | 代价 |
|---|---|---|
| (a) 保持人工 | receipt 里记一行"门禁：人核" | "既有门禁全绿"永远是口头的，而判据 4 要的是读数 |
| (b) 驱动器写死四个命令 | 直接调 | 要把"仓库在哪"编进**用户侧**脚本 —— 换机器 / 换目录就废 |
| **(c) 声明式**（建议） | `allow.toml` 里写 `[rsi].gates = [{ cmd = "cargo test", cwd = "…", expect = [0] }, …]`，驱动器只执行 + 记账 | 不认项目类型；清单正确性仍靠人 |

**建议 (c)**。它与 `allow.toml` 现有风格一致（`bench_exe` 已经是路径声明），零新概念，
且对任何项目都成立 —— 用户侧脚本里不该出现宿主仓库的路径。

**边界（如实说）**：(c) 只证明"声明的命令退出码对"，不证明"声明的就是该跑的那四条" ——
所以 receipt 要记 `gates_argv` 与逐条退出码，供人事后审计。门禁很贵（`cargo test` 是**全 workspace**，
数十秒起），预算硬顶要把它算进去。

**判据**：一份 receipt 里既有尺子读数、也有逐条门禁命令与退出码；任一条非 0 ⇒ **不出 patch**（判据 4）。

### A-5 引擎侧 pycache / MAX_PATH 的修法 —— ✅ **已拍板并按 (a) + (c) 落地（2026-10-08）**

**落地形状**（`crates/harness-engine/src/verify.rs`）：

1. **(a)** 两处 `python -m py_compile <f>` 换成一条**不写盘**的探针
   `PY_SYNTAX_PROBE = import ast,sys;ast.parse(open(sys.argv[1],'rb').read(),sys.argv[1])`
   （全量语法检查 + `staged_syntax_checks` 各一处）。传 `bytes` ⇒ `compile()` 照样认 coding cookie
   与 BOM；探针串**不含空格**（要过一层 `cmd /C`，少一层引号就少一个踩点）。
2. **语法检查的环境也换掉**：`syntax_envs()` = `PYTHONIOENCODING=utf-8` +
   **`PYTHONDONTWRITEBYTECODE=1`**，不再用 `PYTHONPYCACHEPREFIX` 改道 —— 这样连 `import ast,sys`
   引起的 **stdlib 缓存**也不落盘。（**这条是新测试逼出来的**：只换探针时，stdlib 的 pyc 照样被写进
   改道目录，「一个字节都不写」并不成立。）注：`PYTHONDONTWRITEBYTECODE` 对**显式写盘**的
   `py_compile` 无效 —— 那正是当初不能靠它救场的原因；它对「import + parse」的探针才正好对症。
3. **(c)** 新增环境闸 `py_env_guard(dirs, root)`：状态根**必须绝对**、字节码路径预估 > 250 ⇒
   报「**环境不支持**（附理由与出路）」，并且落在**仍会写字节码**的那一格（python 测试支）变成
   **跳过 + 原因**（"这一轮没有读数"），既不当通过、也不当失败。

**判据（都已绿）**：`python_syntax_check_writes_no_bytecode_at_all`（状态根下无 pycache 树、源码旁无
`__pycache__` —— **平台无关**，macOS 也能跑）/ `a_relative_state_root_is_environment_not_syntax` /
`an_overlong_bytecode_path_is_environment_not_syntax`（后两条同时断言**语法格照常通过** ⇒ 语法结论
已与状态根、路径长度、cwd 解耦）+ 老用例改成钉 `ast.parse`；`verify::` **11 通过 / 0 失败**。

**正面的副作用**：语法格的结论从此与环境无关 —— 当初那次假红（写对了的 `calc.py` 被判
「语法/编译错误」并打回 `final`）在**因果上**被切断，而不是"绕开了"。

以下为当时的候选与建议（存档）：

**现状（核对到行）**：假红来自**唯一一处**写字节码的地方 —— `crates/harness-engine/src/verify.rs:539`
的 `python -m py_compile <f>`，它带着 `PYTHONPYCACHEPREFIX`（`py_envs`，`verify.rs:480`）指向
`VerifyDirs::pycache`（宿主 = `<项目状态根>/verify/pycache`，见 `verify.rs::verify_dirs`）。pyc 真实路径
≈ **2 × 落点深度 + 常数**，因为 CPython 把**源码的绝对路径**镜像到前缀底下。

**核对出来的关键事实**：python **测试**那条路**不写字节码** —— 它给的是 `PYTHONDONTWRITEBYTECODE=1`
（见 `verify.rs` 的 python 测试分支），`import pytest` 探针虽然用 `py_envs`，但 import 的 pyc 写失败不影响导入
（只会降级到 unittest）。⇒ **这一整类只污染"语法检查"这一条读数**，修法不必扩大。

| 候选 | 内容 | 取舍 |
|---|---|---|
| **(a) 换掉 `py_compile`**（建议） | `python -c "import ast,sys;ast.parse(open(sys.argv[1],encoding='utf-8').read())" -- <f>` —— **不写任何文件** | 少一层"能编译成字节码"的保证；但这条检查的名字与理由本来就是**语法**，字节码写盘从来不是它的目的 |
| (b) 前缀改短 | `PYTHONPYCACHEPREFIX` 指到系统临时目录下的短名 | 治标，且多一个要清理的临时目录 |
| **(c) 兜底 fail-closed**（建议，与 a 并行） | 状态根必须绝对；估算 pyc 路径 > 250 ⇒ 报「环境不支持（路径过长）」而**不是**报语法错 | 不修根因，但保证"坏尺子报没有读数" |

**建议 (a) + (c)**。(a) 之后 `verify` 全流程**一个字节码文件都不写**，`PYTHONPYCACHEPREFIX` 这条改道
对语法检查不再需要（是否连 `VerifyDirs::pycache` 一起删可作为 (a) 的附带决定 —— 删了更干净，
但 `staged_syntax_checks` 也在跑 `py_compile`，要一起处理）。

**别指望 `PYTHONDONTWRITEBYTECODE=1` 能救 `py_compile`**：那个环境变量管的是**导入系统**
（`sys.dont_write_bytecode`），`py_compile` 是显式写盘、不看它 —— 测试那条路能用它，正因为它走
import / pytest 而不是 `py_compile`。

**验证与平台（重要）**：记录的实测（18/18 打回、`[WinError 206]`）是 **Windows** 侧的（260 上限）；

### A-6 `execute` 越界要不要现在补一道闸 —— ✅ **已拍板 2026-10-08：不补**

**决定**：不补。越界防线落在两层 —— ① P2 的**副本隔离**（提议步只在 `arms/round-N` 里跑，

读数与事后审计都能看出「这一轮确实是在副本里跑的」。
落点：`doc/v1.4/templates/rsi/rsi_round.py::surface_hashes` + `scripts/rsi-round-selftest.sh` 四条断言。

以下为当时的候选与建议（存档）：

**现状（核对到行）**：P1 的闸装在两个入口（`Ctx::apply_write`：`agent/tools.rs`；并发波：

（`execute_allowed` 只有破坏性模式拒绝清单），所以 `python -c "open('x','w')"` 照样能写 ——
P1 文档 §5-1 自己点名了这一点。

| 候选 | 内容 | 代价 |
|---|---|---|
| **(a) 不补**（建议） | 真正的不越界靠"把 run 放在**副本**里跑"（P2 的 `arms/round-N`） | 若哪天有人在便携根**原地**跑提议步，等于没闸 |

**建议 (a)**，**但要和 A-1 绑在一起看**：(a) 成立的前提是"提议步只在副本里跑"这条**纪律**，

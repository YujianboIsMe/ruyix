> 长期目标叫 RSI（递归自我改进）；**v1.4 只做第一台阶**，正式名叫「harness 自改闭环」。
> 相关：`doc/v1.2/需求-Agent-上下文布局与去重账本-v1.2.md`（配对实验脚手架的来源）、

## 0. 口径：这个项目里「自我改进」指什么

ruyix 的 agent 本来就能对一个**项目**做 Read / Write / Execute / Connect。自改闭环就是把
「项目」换成**驱动它自己的那些东西**（提示词片段、工具表、包管理器表、技能文档、规约规则、
调度参数），并且**以外部可判定的读数为适应度**。

不指：模型在线改自己的权重、「agent 自己决定自己要不要更聪明」这类不可证伪的表述。

**为什么这个仓库恰好适合做这件事**：可生长的地方早就被做成了**表 / 数据**，而不是散在逻辑里 ——
"加一个能力 = 加一行表，不是加一个 match 臂"。这是自改能成立的前置条件：改的是数据，
不是控制流。

| 自改面 | 形态 | 现在的位置 | v1.4 开不开 |
|---|---|---|---|
| 技能文档（SKILL） | 纯数据 | `skills.toml`（能力系统，全局 + 项目合并） | ✅ L0 |
| CLI 工具白名单 | 纯数据 | `tools.toml` | ✅ L0 |
| 提示词片段 / 数据插件 | 纯数据 | `plugins/`（现只承载高亮主题） | ✅ L0 |
| 命令发现表 | 编译期常量表 | `engine::discover::TOOLS` | ✅ L0（**需覆盖加载点**，见 §4.2） |
| 包管理器表 | 编译期常量表 | `src-tauri/src/agent/env_setup.rs::Pm` | ✅ L0（同上） |
| 规约检查规则 | Python 包 + 配置 | `tools/lint/` | ✅ L0 |
| 调度 / 上下文数值参数 | 数值 | `ruyix.code.harness.agent.ctx.*` 等 | ✅ L1（**离线调参器**，不让模型在线瞎试） |
| 引擎 / 宿主逻辑 | Rust 代码 | `crates/harness-engine`、`src-tauri` | ❌ 明确不开（见 §4.1） |
| 评测任务集与判据 | 数据 | `<便携根>/projects/<键>/rsi/tasks/` | ❌ **只读**（改考卷 = 立即作废，见 §1.2） |

## 1. 三条硬边界（先钉住，才谈得上做）

### 1.1 没有适应度就没有自改，只有自我编辑漂移
所有采纳决定必须挂在一个**外部可判定信号**上：编译 / 测试通过、评测台分数、真 run 成功率。
"这段提示词读着更顺"**不是**信号。现状：449 个引擎单测证明的是**机制**，"这版比上版强"
目前**没有任何数支撑** ⇒ 所以 **最小评测台是前置依赖**（P0，先做）。

### 1.2 判据与任务集对 agent 只读
能被自改的东西一旦包含"考卷"，闭环立刻退化成 reward hacking（删测试 / 绕任务 / 放宽判据）。
防线两条：① 任务集与判据文件的**哈希在本轮内锁定**，改了就作废本轮并留痕；
② 判据文件放在 agent 的**白名单之外**，写入即被拒（引擎侧硬拦，不是提示词礼貌请求）。

### 1.3 「递归」留到下一版
真正的递归是"改进者自己也被改进"（改判据、改引擎逻辑）—— 那要求 §1.1 的信号已被证明可信。
v1.4 只做**窄的、可回滚的、需人合并的**第一台阶；名字诚实一点：`harness 自改闭环`。

## 2. 它常见的四种坏法（与防线）

| 坏法 | 症状 | 防线 |
|---|---|---|
| 谁验证验证者 | 模型自评 = 无信号 | 适应度只能是外部可判定的；无外部信号的改动**一律不采纳** |
| 奖励劫持 | 删测试 / 改判据 / 声称"做不到的已做到" | 判据只读 + 变更审计（diff 里动测试或判据要**显式标红**）+ 任务集必须含**负样本任务**（已知做不到，改完仍须失败） |
| 漂移不可解释 | 迭代若干轮后没人知道某段提示词为什么长这样 | 每轮留 receipt（动机 / 证据 / 前后读数 / 回滚点）+ **保守合并**（沿用 P4 的 `MARGIN` 先例：差额不够大不合并） |
| 成本爆炸 | 每轮自改都跑全量评测 | 分档：小改跑子集、进 final 前跑全量；预算硬顶 + 轮数上限 |

## 3. 分层与信任级别（v1.4 = L0 + L1）

| 层 | 内容 | 信任级别 |
|---|---|---|
| **L0** | 技能文档、工具白名单、`plugins/` 下的数据（提示词片段 / 表行）、lint 规则 | 自改 + 配对测 + **人合并** |
| **L1** | `ruyix.code.harness.*` 数值参数（`ctx.*`、keep 轮数、batch 上限…） | 由**离线调参器**（参数扫描 + 配对评测）产出建议，**人合并** |
| L2 | 引擎 / 宿主**逻辑**代码（Rust） | v1.4 **不开**。将来若开：只许出补丁 + 证据，人在分支上合并 |
| L3 | 评测任务集与判据 | **永不开**（见 §1.2） |

## 4. 落点：用户侧，不进 ruyix 源码

### 4.1 硬要求（用户拍板）
自改闭环与它的产物**落在用户侧**（便携根的 `plugins/` 与项目桶），**不是** ruyix 的源码改动。
好处与代价都很清楚：产物可弃、可回滚、随便携包分发、不进主干；代价是宿主必须提供
"可以放"的位置与"加载时合并"的机会（见 §4.2）。

### 4.2 现状缺口（必须诚实指出）
`discover::TOOLS` 与 `env_setup::Pm` 是**编译期常量表** —— 用户侧改不了，宿主目前只开了一个缝
（`ruyix.code.harness.discover.extra` 追加二进制名）。所以"L0 能自改"这句话，对这两张表**目前是假的**。
两条路：
- **(a) 加一个加载/合并点**（推荐）：宿主启动时把 `plugins/tools/<id>/*.toml` 里的表行**并入**上面两张表。
  这属于"部署形态"的一次改动（读文件 + 合并），**不是** RSI 逻辑进源码；一次改动、之后自改全在数据里。
- **(b) 本版不收这两张表**：L0 缩到"技能文档 + 工具白名单 + 数据插件 + lint 规则"四类，先用起来。
待拍板（§7-6）。

### 4.3 驱动器：用**已有**的机制，不加新原语
自改闭环不需要引擎里的新代码，它可以用 ruyix 自己的四原语与既有的运行机制跑起来：
- `rsi` 就是**一个用户侧项目**：`<便携根>/projects/<rsi 键>/`，内含
  `tasks/`（任务集 + 判据 + 负样本）、`arms/`（两臂输出）、`receipts/round-<n>.json`、`out/`（自改产物）。
- **跑评测**用宿主已有的 `run_target`（一次性命令）或托管进程（长任务）；
  **让 agent 自己跑**用它的 `execute`。评测脚本是普通脚本，零 npm 依赖。
- **测量**用 v1.2 已有的仪器与配对脚手架（`ctx_layout_ab` 的形状直接照搬：配对臂 + 保真校验 +
  逐轮原始值）。

## 5. 最小可交付（v1.4 的形状）

> 一个**离线**的自改闭环：agent 只能改**白名单**里的数据；每次改动在**冻结任务集**上跑
> **配对两臂**（≥N 轮、同 temperature、取中位数、留逐轮原始值）；只有
> **提升 > MARGIN 且不违反任何既有门禁**，才生成 `patch + receipt`；
> **人合并**（v1.4 绝不自动进主干）。

固定参数（沿用仓库既有先例）：`MARGIN = 5%`（`scheduler::MARGIN` 同款理由：差额太小不值当合并）、
每轮最大候选数上限、每轮预算硬顶、`receipts/round-<n>.json` 每轮一份。

## 6. 预注册判据（跑之前钉死，任何一条不成立即本轮作废）

1. **白名单外只读**：改白名单外的文件 ⇒ 被**拒**，且拒绝理由指名是哪一类（不是提示词礼貌劝阻）。
2. **考卷不可改**：任务集与判据文件在本轮内哈希不变；变了 ⇒ 本轮作废 + 留痕。
3. **配对两臂**：同一任务集、同一 temperature、同轮数；读数留**逐轮原始值**，无效轮**剔除而非当 0**。
4. **采纳门槛**：提升 > MARGIN，且既有门禁全绿（`cargo test`、`cargo clippy`、`ui-smoke`、三个几何探针）。
5. **负样本**：任务集必须含已知做不到的任务；自改版在负样本上**仍须失败**（防"声称做到"）。
6. **可回滚**：每轮留可回滚点，`git checkout` 能回到改前，且能证明改前读数。
7. **无信号不采纳**：读数无显著差异的改动（例如纯措辞调整）不许合并。
8. **零源码改动**（v1.4 范围）：本轮跑完 `crates/harness-engine` 与 `src-tauri` 无新改动 ——
   自改产物只落在用户侧（`plugins/` + `projects/<键>/rsi/`）。唯一例外是 §4.2 的加载合并点（若拍板）。

## 8. 实施计划（每阶段都有可判定的交付物）

| 阶段 | 交付物 | 判据 |
|---|---|---|
| **P0 最小评测台** | 任务集格式（含负样本）+ 判据脚本 + 配对双臂跑器 + **基线读数表** | 同一任务集连跑两轮，读数可复现（中位数差异在噪声内）；无效轮剔除有记录 |
| **P1 白名单与只读边界** | 白名单定义（用户侧清单文件）+ 越界即拒 + 考卷哈希锁 | 判据 1/2 逐条可复现（故意越界一次，被拒且理由具体） |
| **P2 自改闭环** | propose → 配对测 → MARGIN 判定 → `patch + receipt` | 判据 3/4/6/7；至少跑出一轮**被拒绝**的候选（证明门槛真的会拦） |
| **P3 人合并与回合账本** | 合并流程（人） + `receipts/` 账本 + 负样本回归 | 判据 5；人能凭 receipt 决定合/不合，且合完可回滚 |

## 9. 明确不做（v1.4）

- ❌ 改评测任务集 / 判据（§1.2）
- ❌ 让模型自评当适应度
- ❌ 自动合并（人不在环里）
- ❌ 引擎 / 宿主**逻辑**代码的自动修改（L2）
- ❌ 在线自改生产配置（L1 只做离线离线调参，建议由人确认后落配置）
- ❌ 把 RSI 机制编进 ruyix 源码（落点见 §4）

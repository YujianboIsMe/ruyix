# 问题：验证的 `__pycache__` 改道撞上 MAX_PATH，被读成「语法/编译错误」

> 归属版本：v1.4（P0 最小评测台**第一次真跑**时发现）· 2026-09-28
> 状态：**已修**（2026-10-08，v1.4 拍板单 A-5 按 **(a) `ast.parse` 取代 `py_compile` + (c) 环境闸** 落地，
> 见 §6；`verify::` 11 通过 / 0 失败）。本文的机理与实测**照原样保留** —— 它就是那条假红的证据。
> 复现：`rsi_bench --self-check`（含「落点太深 ⇒ 跑之前拒绝」那条）+ `RSI_KEEP=1` 保留现场；
> 当时那两个一次性脚本**已删**（2026-09-30），步骤在本文 §5 里写全

## 1. 现象

脚本化臂里，模型**写对**了 `calc.py`（`write calc.py（32 字节）` + 窄层检查 1 项全过），
第 2 轮交 `final` 时被打回：

```text
[warn] [agent] 第 2 轮交付被打回：[机械验证·全量验证] 未通过：1 项失败（首个：calc.py 退出码 Some(1)）
✗ syntax calc.py：退出码 Some(1)
- calc.py（python）：退出码 Some(1)
  语法/编译错误，先改这个再谈测试
```

模型于是被迫再改一轮（脚本化臂没有第三轮 ⇒ 整轮变成「无效」）。实测**18/18 轮全被打回**，
而同一份夹具、同一个剧本、换成另一个落点就**全过**。

## 2. 机理

`verify.rs` 的 python 语法检查是 `<python_bin> -m py_compile <文件>`，并且为了"跑完仓库干净"
把字节码改道：

```rust
fn py_envs(dirs: &VerifyDirs) -> [(&'static str, &str); 2] {
    [("PYTHONIOENCODING", "utf-8"), ("PYTHONPYCACHEPREFIX", dirs.pycache.as_str())]
}
```

CPython 对 `PYTHONPYCACHEPREFIX` 的行为是：把**源码的绝对路径镜像**到那个前缀底下。于是

```text
pyc 真实路径 = <前缀>  +  镜像的<源码绝对路径>  +  __pycache__/<名字>.cpython-311.pyc
```

长度 ≈ **2 × 落点深度 + 常数**。越过 Windows 的 260 ⇒

```text
[WinError 206] 文件名或扩展名太长。: 'C:\...\pycache'
exit=1
```

`py_compile` 退出 1 ⇒ `CheckResult::from_output` 判「语法/编译错误」⇒ 门禁**打回 final**。

## 3. 两个触发条件（都实测过）

| # | 条件 | 实测 | 估算 |
|---|---|---|---|
| 1 | 落点**很深**（例如深层临时目录） | 自检里的长临时目录：写对了也 12/12 打回 | pyc ≈ 325 字符 |
| 2 | **状态根是相对路径** | `--out target/rsi-bench-rep-a`（相对）⇒ 18/18 打回；改成绝对路径 ⇒ 全过 | 相对前缀在 python 的 cwd（= 项目目录）下解析，再与绝对源码镜像拼接 ⇒ 长度翻倍 |

第 2 条是**宿主也能踩**的：`AppConfig::project_state_root` 若是相对路径，就会命中。
ruyix 宿主一直给绝对路径（`<便携根>/projects/<键>`），所以线上没炸；引擎作为库没守住这条。

## 4. 危害（为什么值得单独记一笔）

**尺子坏了装成读数。** 引擎给出的是一条**代码结论**（「语法/编译错误」），而真实原因是**环境**
（路径太长）。后果三连：

1. 模型被误导着去"修语法"，白烧轮次；
2. 评测台把一次写对的改动读成"这版更差"（奖励劫持的反面：**假红**）；
3. 真用户的便携根一旦够深，正常的改动会被判成语法错。

## 6. 修法与判据（2026-10-08 已落）

| 决定 | 落地 |
|---|---|
| **(a)** 换掉 `py_compile` | `verify.rs::PY_SYNTAX_PROBE`（`ast.parse`，**不写任何文件**）替掉两处 `py_compile`（全量语法检查 + `staged_syntax_checks`）；语法检查的环境同时换成 `syntax_envs()`（`PYTHONDONTWRITEBYTECODE=1`），连 stdlib 的 import 缓存也不落盘 |
| **(c)** 兜底 fail-closed | `verify.rs::py_env_guard`：状态根必须绝对、字节码路径预估 > 250 ⇒ 在**仍会写字节码**的那一格（python 测试支）报「**环境不支持**」（跳过 + 原因），不是语法错 |
| 判据 | ① `python_syntax_check_writes_no_bytecode_at_all`（**平台无关**：状态根下无 pycache 树、源码旁无 `__pycache__`）② 相对状态根 / 超长路径 ⇒ 环境不支持，**且语法格照常通过**（证明语法结论已与环境解耦）③ 老用例改成钉 `ast.parse` |
| 顺带记一笔 | 只换探针时测试**红了**：`import ast,sys` 会把 **stdlib 的 pyc** 写进改道目录，"一个字节都不写"并不成立 ⇒ 环境也必须换。这条是这一刀最有价值的发现，已写进代码注释 |

**仍保留的东西**：`VerifyDirs::pycache` 与 `py_envs`（改道）没删 —— 它们服务的是**测试 / import**
那条仍会写字节码的路。评测台的路径闸（`rsi_bench::guard_long_paths`）也留着，但**理由更新了**：
引擎已不会因这条假红而打回 `final`，闸现在只是**兜底**（别把一整轮烧在注定失败的环境上）。

### 6.1 现场条件复原（修完后的对照读数）

把当初出假红的那两个条件**同一次跑出来对照**（脚本化臂 `--fake`，零成本、确定性；同一份考卷）：

| 跑法 | 基准臂 | 候选臂 | 无效轮 | 逐任务 | 病灶痕迹 |
|---|---|---|---|---|---|
| `--out target/rsi-rel-out`（**相对**，当初的条件） | 12/12 ok | 12/12 ok | 0 | 与右列**逐项相同** | 无 `WinError 206` / 无 `✗ syntax` |
| `--out D:/Projects/Rust/ruyix/target/rsi-abs-out`（绝对，对照臂） | 12/12 ok | 12/12 ok | 0 | 同上 | 同上 |

考卷 sha256 跑前跑后一致（`c6cb496709093c36…`）；负样本 `impossible-add` 两臂都仍**失败**（expect=fail
没被"修好"—— 修的是环境，不是判据）。**能声称**：那条把环境病读成代码结论的链在这两个条件下都不再出现。
**不能声称**：脚本化臂测不到模型行为，这里测的只是"管道与统计没被环境污染"。

顺带两条**观察到的事实**（不是缺陷，记着免得下次误判）：

- `runs/<id>/project/__pycache__/*.pyc` 是**判据脚本**自己跑 python（import 被测模块）写的，落在
  **沙盒副本**里（不进用户仓库）。判据若要断言"目录里有什么"，**别拿整棵树当白名单**比对。
- `runs/<id>/state/verify/pycache/` 只在**有测试**的任务（`fix-mul-and-test`）出现 —— 那是 python
  **测试支**按设计走的改道（`py_envs`），语法格早已不写任何东西（见 §6）。

## 5. 建议方案（**已采纳，存档**）

| 方案 | 内容 | 代价 |
|---|---|---|
| **(a) 换掉 py_compile**（推荐） | 语法检查改 `python -c "import ast,sys;ast.parse(open(sys.argv[1],encoding='utf-8').read())"` —— **不写任何文件** ⇒ 没有 pycache ⇒ 没有长度问题，也不用再清理 | 比 py_compile 少一层"能编译成字节码"的保证（语法层面等价；字节码写盘从来不是这条检查的目的） |
| (b) 前缀改短 | `PYTHONPYCACHEPREFIX` 指到系统临时目录下的短名（`rsib-pyc-<hash>`） | 多一处需要清理的临时目录；治标 |
| (c) 兜底 fail-closed | `verify` 要求状态根是**绝对**路径，且估算的 pyc 路径超限时如实报「环境不支持（路径过长）」而不是报语法错 | 不修根因，但保证"坏尺子报没有读数" |

倾向：**(a) 为主 + (c) 兜底**；(c) 单独也值得做 —— 它保证这类病再也不装成读数。

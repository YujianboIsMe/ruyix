## 1. 目标形态：三个 region，三条不变式

请求体在**任何时刻**都是三段拼接：

```
[ S 不可变根 ][ E 只追加梯子 ][ A 每步重建的易变尾 ]
  system + 工具声明      压缩后的历史条目        本轮证据/账本/待办
  + 任务原文             （只追加、不就地改）
```

| 不变式 | 判据（可自动查） |
|---|---|
| **I1 S 字节不变** | 相邻两轮请求的 S 段 sha256 相等；S 一旦需要变，说明它被误当成了可变区 |
| **I2 E 只追加** | E 段是上一轮的**前缀**（`starts_with` 判定），压缩只能**追加一条 capsule 摘要**，不许改写既有条目 |
| **I3 A 可重建** | A 段丢弃后仅凭 S+E+侧存即可重建（**这一条正是"不靠重跑工具"的实现**） |

> 现状违反 I1：`tool_loop.rs` 每轮重建 `msgs[0]`，把 findings/账本拼进 system ⇒ 每轮作废整段前缀缓存。
> 这是本期**第一个要挪**的东西，且不需要任何算法。

## 3. `ContextLedger`：去重与有效性的三件套

```rust
/// 一次调用的规范化键（**规范化是去重的前提**）
struct CallKey { tool: Tool, norm_args: String }

/// 一条账本记录（只增不改）
struct LedgerEntry {
    key: CallKey,
    digest: u64,            // 结果摘要（用于"同一结果"的判定与 trace）
    result_ref: Ref,        // → capsule 侧存：全量结果**永不丢**
    version: VersionVec,    // 该调用读到的资源版本
    step: u32,
}

/// 资源版本向量（保守：拿不到就不许去重）
struct VersionVec { entries: Vec<(ResourceId, VersionTag)> }
```

**三件套（逐条对应上游机制，逐条可测）**

| 机制 | 本仓库做法 | 拒绝/接受的规则 |
|---|---|---|
| **规范化** | 路径归一（`./a` → `a`、分隔符统一、Windows 折大小写、`read "."` 的各种拼法）；命令归一（折叠空白、去掉 `2>nul` 这类无副作用重定向、命令名折小写、**命令里的路径 token 一起归一**）；省缺省参数由类型一次性完成（`limit: null` 经 serde 就是 `None`） | 归一只做**语义等价**的变换；模棱两可 ⇒ **不归一**（宁可多执行一次）。命令里那半条是被**黄金测试**抓出来的：第一版只归一了"资源表"，`git diff -- ./a` 与 `git diff -- a` 因此算两个键 ⇒ 上游命中的那两个事件我们没命中 |
| **包含关系** | 整文件读 ⊇ 该文件的任何区间读（`SpanKey{resource, lo, hi}`，`hi = -1` = 到末尾）；`grep` 的包含键是 `(pattern, path)`，与上游同形 | 只有**版本一致**时才允许"用整份顶替片段"；覆盖它的候选里取**跨度最大**的那个。**跨路径作用域的包含（全仓 grep ⊇ 子目录 grep）刻意不做**：上游也没有，而黄金测试要求**决策逐条对齐** —— 把判据改宽一档，"对齐"这条硬标准就作废了 |
| **版本有效期** | 文件 `(mtime_ms, size)` · 本会话写过的路径 `Overlay(内容哈希)` · 目录 `(mtime, 写入代次)` · 不存在 `Missing` · 仓库级 `git HEAD + 工作树脏否` | **纯工具**白名单内的调用才可去重；白名单外**一律执行**；版本拿不到（`unknown`）⇒ **执行**（fail-safe）。**不取 sha256**：每次调用哈希整个文件是纯开销，而 `(mtime, size)` 变了一定变；"同秒同大小覆写"这条漏网由 `Overlay` 与目录的写入代次补上（我们自己的写入本来就全在跟踪里） |

**纯工具白名单（P2 实现的起步集，写进代码而不是提示词：模型不许自己说"我很纯"）**

- **`read` 永远纯**（整份读、窗口读、目录读都算）；
- **`execute` 里的白名单**（看首 token，`git` 再看子命令）：`dir` / `ls` / `type` / `cat` / `head` / `tail` / `findstr` / `where` / `find` / `git {grep,log,status,diff,show,ls-files}`；
  纯命令可以带管道，但**每一段的首 token 都得在白名单里**（`| tee f` 会写盘）；
  含写向文件的重定向或 `&&` / `||` / `;` ⇒ **不纯**；
- **一律不纯**：`write` · 白名单外的 `execute`（构建 / 安装 / 起服务 / 写文件）· `execute` 的后台形态与句柄操作（第二次 `status` 的答案本来就不同，去重它会给出错答案）· `connect`（对端是外部系统，版本向量拿不到 ⇒ fail-safe；上游"list 算纯"那条本期**不接**）· `plan` / `final` / `ask_user` / `record_findings`（控制动作）。

> 设计取向：**宁可多执行一次，也不许"看起来一样就跳过"**。去重是性能优化，不是正确性优化——这个方向反了会静默给出错答案。

## 4. 去重命中时的**行为**（不能只"跳过"）

命中 ⇒ **不执行**，但必须：① 返回**上次的真实结果**（从 capsule 读，逐字节一致）；② 结果尾部附一行
`（第 N 轮已执行过同一纯调用，资源版本未变；本次直接复用，未重跑）`；③ 记 trace 行 `dedup <tool> <norm_args>`。
—— 模型必须**知道**自己看到的是复用结果，否则它会怀疑"是不是没执行成功"从而再试一次（实测正是这个循环）。

## 5. 结果侧存（P2 是内存里有界，P3 换成 capsule）

- **P2 的形态**：结果存在账本里（`LedgerEntry::result`），**上限 `agent.ctx.dedup_max_bytes`（默认 8MB）**，
  超限把**最老的一条整条挤掉**（键与结果一起没 ⇒ 下次真执行，fail-safe；不做"留着键但取不到内容"那种半吊子状态）。
  选有界内存是刻意的：一个 run 的账本不该无上限地吃内存，而 8MB 对"读了几十个文件"来说够用。
- **P3 已落地的形态**（`agent/capsule.rs`）：`<便携根>/projects/<项目键>/ctx/<run-id>/`（**绝不写用户仓库**）——`<step>-<tool>-<hash8>.txt`
  全量结果 + 一条 JSONL 索引；读回把该目录加入 `read` 工具的**只读白名单例外**（与 findings 落盘同一处例外，
  必须写在同一段注释里）；生命周期与 run 同寿；判据：召回内容与原文 **sha256 相等**（"无损"的唯一证明）。
  ⇒ **P3 落地后 §5 第一条的容量上限确实退场了**：`Body::Stored` 的 `mem_len()` 是 0，
  记账与挤占只作用于 `Body::Inline`（`agent.ctx.capsule` 关着时的老形态）。
  索引里带 `sha256` 与 `len`，召回时**逐字节校验**（不符就拒绝交付并计数，不静默给脏数据）；
  `read` 的只读例外只有一处（`Ctx::state_file`）：规范化后必须落在 `state_root` 之内。

**失败的结果不进账本**（P2 的实现口径）：只有 `Ok` 的结果才 `record`。理由：把一次瞬时失败
（网络抖动 / 端口没起）钉死成"以后都这样"，比多执行一次贵得多 —— 这仍是 §3 那条"宁可多执行一次"。

## 7. `RebaseScheduler`（什么时候压缩）

- **入参**：horizon（H=96）· 当前 ladder 大小 · 预算 B · 每步预计新增 token · 缓存的"用 vs 重建"代价比；
- **已知 horizon**：反向 DP 求最优重基线点 + 每步 MPC 重规划（上游同法）；
- **未知 horizon**：ski-rental（竞争比 `e/(e−1)`）；本仓库 H 已知 ⇒ 主路径是 DP，ski-rental 作为**兜底**（`max_elapsed_secs` 提前终止时 horizon 会变）；
- **触发下限**：无论调度器说什么，都不得低于 `history_keep_rounds`（安全下限，门禁 ≥10）；
- **可观测**：每次决策记 trace：`rebase 决策=执行/跳过 理由=DP|ski-rental|下限|预算 预计省 X 字节`
  （P4 实现时补了第四种理由 `预算` —— 预算越界是**强制**压，它优先于下限与 DP）。

### 7.1 P4 实现口径（2026-09-27）

- `agent/scheduler.rs`：状态只有一维（"距上次压几轮"）⇒ 反向 DP 是 `rem × d` 的二维表（96×96，微不足道）；
  `decide` = 用**实测**增长做一次 MPC 重规划、只取第一步；视野未知（跑过 H）走 ski-rental；下限与预算在 DP 之前判。
- **两条实测结论写进代码**：① DP 算的是"现在压 vs 稍后压"，差额通常只有重建代价的几个百分点
  ⇒ 需要 `MARGIN = 0.05` 的材料性下限，否则会为"省 49 单位"就压（而那一压把前缀打断）；
  ② **G1 不能当 P4 的判据**（小阶梯上折得越多比率越高）⇒ 判据是"G2 不越界 + 折叠次数不多于老规则"。
- 阶梯大小与增长都是**字节代理**（`estimate_tokens` = 字节/4，架构 §6 允许），trace 里明写"字节代理计量"。

## 8. 迁移与回滚

### 8.1 开关（已落地三个：P1 两个 + P2 一个）

- **`agent.ctx.layout`**（**默认开**，P1；拍板 7 前是默认关）：见 §1。显式关掉 ⇒ 与 v1.1 逐字节相同。
- **`agent.ctx.metrics`**（默认**关**，P1）：**仪器** —— 逐轮打印公共前缀占比、S 段指纹、
  以及厂商回报的命中 token；run 末给一条加权小结。为什么和 layout 分开：判据是"占比**上升**"，
  而**对照臂也必须能量**（基线只能测出来，不能猜）。仪器只长在实验臂上，那个"上升"就无从比较。
  关掉时零额外计算、零额外日志行。**P2 的仪器（`ExecAudit`：唯一执行 / 仍重复执行 / 版本失效重执行 /
  不纯执行 / 拦截重复）挂在同一个开关上** —— 因为"重复执行次数下降 ≥50%"这条判据同样需要对照臂的基线。
- **`agent.ctx.dedup`**（默认**关**，P2）：去重账本。关掉 ⇒ 与 v1.1 逐字节相同（连 `classify` 都不调用）。
- **`agent.ctx.dedup_max_bytes`**（默认 8MB，P2）：结果侧存上限；`0` = 不限。
- **`agent.ctx.enabled` 总开关仍然不加**：P2 落地后子开关是两个（`dedup` / `layout`），
  它们**独立开合**（各自的判据、各自的门禁），不是"同一件事的两道锁" ⇒ 再套一层总开关依然只会
  多一次翻找。等真出现"必须一起开"的证据再加。
- **`agent.ctx.capsule`**（**默认开**，P3）：结果正文落 capsule 侧存；显式关掉 ⇒ 结果留在内存（P2 形态）。
- **`agent.ctx.schedule`**（**默认开**，P4）：何时压交给调度器；显式关掉 ⇒ 老触发条件一字不变。
- **`agent.ctx.horizon`**（96）· **`window_tokens`**（131072）· **`budget_tokens`**（0 = 按窗口 60% 推）·
  **`carry_rate`**（0.1）· **`rebuild_rate`**（0.9）—— P4 的代价模型参数，都是"未缓存输入 = 1.0"的相对价。
- 键由 `config::schema()` 自动同步到宿主与配置表单，**不需要改第二处**。

### 8.2 与设计稿的一处不同：摘尾时机（实现记账）

设计稿写"每轮先删上一轮的尾、再 push 新尾"（尾跨轮留在 `msgs` 里）。实现改成
**请求前 push、`llm::chat` 返回后立刻摘**（尾只活这一次请求），理由：`fold_history` 是
**按下标**改老轮次正文的（`RoundSlot`），任何跨轮的插/删都会让已记录的下标整体偏一格 ——
轻则折错消息，重则越界 panic。两种写法的**线上请求体完全一致**（都是 `[S][E][A]`），
但后者把 `msgs` 的下标纪律原样保住。
判据：`layout_on_does_not_shift_the_fold_bookkeeping`（布局开 + 折叠开，窗口内/外各查一遍）。

另：`align()` **未做** —— 理由见需求文档 §8.4（没有"块边界"这个计量依据时，凭空定块大小
正是本版要消灭的拍脑袋数字）。

## 3. 不可协商的约束

1. **一个可执行文件 + `global/` + `projects/` + `plugins/`**；卸载 = 删目录；
2. **零新运行时依赖**（token 计量用已有的 `tokenizers`；不引入 Python 运行时）；
3. **绝不写入用户仓库**：capsule / 账本落在 `<便携根>/projects/<项目键>/ctx/`；
4. **不改历史**：被压掉的内容只退出上下文，账本与侧存**永久保留**（与记忆层"证据必须无损"同一条公理）；
5. **判据不许建在"逐字相同"上**（多线程浮点归约不定 ⇒ 只比**决策**，不比浮点）；
6. **可回滚**：一个开关关掉 ⇒ 行为与今天**一字不变**。

## 4. 方案轮廓（三块，按风险从低到高；**不搬仿真件**）

| 块 | 内容 | 为什么它治上述症状 |
|---|---|---|
| **① 布局契约 `[S][E][A]`** | 不可变根 S（system + 工具声明 + 任务原文）· 只追加梯子 E · 每步重建的易变尾 A；`align()` 把 region 对齐到块边界，免得"跨块"浪费掉不可变 token | 直接消掉"每轮砸缓存"（G1）——**纯结构改动、零算法风险** |
| **② 去重账本 `ContextLedger`** | 三件：**规范化**（`read("./a")≡read("a")`、省缺省参数）· **包含关系**（整文件读 ⇒ 区间读冗余）· **版本有效期**（纯工具 ∧ 版本向量一致才允许去重） | 替掉"区间相交"和"execute 不算进展"两条错法（G3）；判据从"我觉得像重复"变成**可证条件** |
| **③ 重基线调度 `RebaseScheduler`** | horizon 已知（**H = `MAX_STEPS` = 96**，与上游设定一致）⇒ 反向 DP + 每步 MPC 重规划；未知 ⇒ ski-rental（竞争比 `e/(e−1)≈1.582`） | 替掉 `keep_rounds` 那个拍出来的数字（G1/G2）；`keep_rounds` 降级为**安全下限**而非策略 |

**明确不搬**：上游的 surrogate tokenizer / compressor / cache 模型 / workload（那是**仿真台**，用于让实验只反映策略差异）；我们只**复用它的工作负载定义**做黄金测试（见 §5）。

**替换表**（搬进来必须换掉的三件）：

| 上游件 | 本仓库替换为 | 备注 |
|---|---|---|
| surrogate tokenizer | 真 tokenizer（`tokenizers` crate，已有依赖） | 取不到就退化为字节代理并**在 trace 里写明** |
| surrogate compressor | 先做**抽取式**（同上游思路：无 LLM 调用、确定性） | 是否上 LLM 摘要**另立需求**，不在本期 |
| 仿真 cache 模型 | 真实信号：厂商命中 token（若可得）/ 否则"前缀逐字节未变"代理 | **未验证**，方案里按"先测再定"处理 |

### 8.3 能声称 / 不能声称

- **能声称**：仪器在**两臂**上都是同一份（`agent.ctx.metrics` 都开，处理变量只有 `agent.ctx.layout`）；
  脚本化配对臂上方向明确（33.2% → 72.4%，同一份动作序列）；"相邻两轮 S 段字节相同"在真 run 上成立
  （S 段指纹逐轮同一个值，臂关则每轮都变）；两臂交付的是同一结论（布局改动没伤任务质量）。
- **不能声称**：**真 run 的"占比上升"还没被有效测过** —— 见 8.4。上表的数字是"未配对观察"，
  不是判据的证据；样本也小（各 1 次、3 轮），更谈不上分布结论。
- 否定判据：**待测**（不是"未触发"）。第一次观察"未触发"、第二次观察"反向"，随后查明**指标本身**
  在未配对时不足以支撑这条判据（8.4）⇒ 在配对回放建好之前，这条判据**不置可否**。

### 8.4 P1 的**计量学结论**（比数字本身更重要）

同一条判据在两次真 run 上给出**相反**的答案（第一次 44.9% → 60.4% 判"对"；第二次 **77.7% → 69.6** 判"反"）。
两次都不是噪声，而是同一个原因：**这个指标是"每轮与前一轮比"，所以它量的是"这一轮的动作序列"，
而不完全是布局**。两臂的轨迹是模型自己走出来的（三次真 run 的轮数与每轮条数**各不相同**），
把两臂的加权占比直接相比，等于把"模型这一趟怎么干"混进了处理效应。三条落地结论：

1. **判据改成配对设计，并且已经建好了**：`examples/ctx_layout_ab.rs` 的
   `--capture`（真 run 一次，把每轮 `tool_calls` 抄成轨迹文件）+ `--pair`（**同一份动作序列**过两臂，
   附**保真校验**：回放后回显必须逐条相同，不然那一臂的读数直接判不可用）。

   | 量法 | 关 | 开 | 差 |
   |---|---|---|---|
   | 脚本化配对臂（确定性，6 轮） | 33.2% | **72.4%** | +39.2pp |
   | **真轨迹配对回放**（5 轮 / 6 条动作，保真 ✓） | 54.1% | **75.1%** | **+21.0pp** |
   | 真 run 未配对观察（第 1 次，3 轮） | 44.9% | 60.4% | +15.5pp（不可作判据） |
   | 真 run 未配对观察（第 2 次，5 轮） | 77.7% | 69.6% | −8.1pp（不可作判据） |

   ⇒ **判据成立**（真轨迹上配对量到 +21.0pp）；未配对那两行只作"为什么必须配对"的证据保留。
2. **旧布局在短 run 上确实可能更高**（不是 bug，是结构）：块只**追加**时，旧布局的整块几乎都落在
   公共前缀里（它在 system 里、且在变更点之前），而尾布局**每轮都要作废那条尾**（约 8KB）；
   尾布局真正保护的是**历史那一大块**（随轮数增长、是账单的大头）⇒ 优势随 run 变长而变大。
   三次真 run 的差异正好落在"块还小、历史还不厚"的区间。
3. **`capture` 会如实失败**：这一趟模型没走工具调用（它会偶发地模仿我们自己的回显格式）
   ⇒ 引擎的守卫报出来、`--capture` 退出码 2 并告诉你"重跑一次或换模型"，**不假装抄到了轨迹**。

### 8.5 与规格的一处偏离（必须记账）

原排期里 P1 还写了 `align()`（把 region 对齐到块边界）。**没做**，理由：那是给"按块计费的
缓存模型"服务的，而本仓库的 G1 真值是**厂商回报的命中 token**（8.1 已实测可用）与字节前缀，
没有"块边界"这个量；在没有计量依据时凭空定块大小，正是本版要消灭的"拍脑袋数字"。
真要做，得等 P4 把真 tokenizer（`agent.ctx.budget_tokens`）接上之后，按实测块粒度再定。

### 9.3 配对回放（**真轨迹**上的读数，判据成立）

`--capture` 真跑一次把动作序列抄下来（3 轮 / 4 条动作），`--pair` 用**同一份序列**过两臂，
回放后回显逐条校对（**保真 ✓**）：

| | 臂**关**（每次调用都真跑，v1.1 行为） | 臂**开**（纯工具 + 资源版本未变 ⇒ 复用） |
|---|---|---|
| 拦截重复 | 0 | **2** |
| 仍重复执行 | **2** | **0** |
| 唯一执行 | 2 | 2 |
| 加权公共前缀（同一份序列） | 48.6% | — |

⇒ **重复执行次数 2 → 0，下降 100%**（判据是"≥50%"）—— 这是本期 P2 的验收读数，
与 §9.2 的黄金测试、§9.2 的循环侧单测一起构成三条独立证据。

两条必须记账的实现细节（都是实测抓出来的）：

1. **审计口径要算"被覆盖"那一类**：真 run 里的浪费主要不是"同一个调用重复发"，
   而是**先整份读、再读一个窗口**（digest 不同、内容已被覆盖）。只按 digest 数，对照臂会显示
   `仍重复执行 0`，判据就成了"0 → 0"这种没法读的数（第一版就是这个毛病）。
2. **审计与记账的顺序**：必须**先审计、后记账**。反过来时，审计问的"账本会不会拦下它"
   会撞上**刚为这次执行记下的那一条** ⇒ 每次执行都被数成"重复"
   （实测症状：唯一执行 0 · 仍重复执行 2）。
3. 审计自带一张**只有键与版本**的表（不含结果），所以**对照臂也能量**（`dedup` 关着时账本
   根本不记结果，靠它的话反事实读数就无从谈起）。

### 9.4 真 run 的**未配对观察**（留作对照，不作判据）

| | 臂**关**（v1.1：每次都真跑） | 臂**开**（纯工具 + 版本未变 ⇒ 复用） |
|---|---|---|
| 拦截重复 | 0 | **5** |
| 唯一执行 / 仍重复执行 | 12 / **0** | 12 / 0 |
| 轮数 | 11 | 11 |

- **能声称**：机制在**真模型轨迹**上确实发生了（5 次重复的纯调用被拦下，交付结论没受影响）。
- **不能声称**：**"重复执行次数下降 ≥50%"在未配对时量不出来** —— 那次对照臂的 `仍重复执行` 是 0
  （模型这一趟没发完全相同的重复调用；第三步"回头核对"它换了窗口读，在当时的口径里算"新信息"），
  分母为 0 ⇒ 比值无意义。与 §8.4 是同一个病：**两臂的轨迹由模型自己走**。
  这条观察后来直接促成了两件事：**配对回放**（§9.3）与**审计口径补上"被覆盖"那一类**（§9.3 第 1 条）。
- 脚本化配对臂（确定性，可复跑）：`仍重复执行 2 → 0`、`拦截重复 0 → 2`（下降 100%）。

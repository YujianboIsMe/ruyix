# 需求：发行包改为 zip（v1.0.0 起）

**归属版本**：v1.0.0
**提出人**：用户
**原话**：*"但是我们发行的是单可执行文件。所以比较难插件化。除非改发行包为 zip. 这样吧，反正我们 git 才 1 颗星。
启动 1.0.0 版本，开始直接改发行包为 zip。zip 内部为可执行文件 + 全局配置文件目录 + 全局数据目录 + 项目目录。
按照惯例，先不动代码，先写需求文档、架构文档、排期文档。"*

---

## 一、为什么改（诉求的真实来源）

单 exe 形态的硬伤不是"不方便"，是**没有任何"落地目录"**：

- 插件（语法高亮扩展、附加语法、脚本、模板）既需要**用户可见可写**的位置，也需要**随包分发**的位置；
  单文件 exe 两个都给不了 —— 这就是 `doc/需求-高亮插件化-v0.14.md` 里"法子 2/4"绕不过去的墙：
  没有目录可放 `highlights.scm`，也没有目录可放 `tree_sitter_*.dll`。
- 顺带的收益：数据与程序分离后，"备份/迁移/换机"从"翻 `~/.ruyix`"变成"拷一个文件夹"。

所以本单定位是**改地基**：先让发行形态能承载扩展，插件本身随后（另单）。

## 二、现状（事实，全部带出处）

| 项 | 现状 | 出处 |
|---|---|---|
| 产物 | `ruyix.exe`，约 34 MB，绿色单文件 | `doc/release-v0.0.5.md` |
| 打包方式 | 手工 `cargo tauri build`；**没有任何 CI 流水线**（`.github/workflows` 不存在） | 仓库根 |
| 全局数据 | `~/.ruyix/code/**`（配置 + agent runs + debug 日志） | 架构文档 §一 的落点盘点 |
| 项目数据 | `<项目>/.ruyix/**`（stage / backups / proc / env / code） | 同上（**保持不变**，它是项目的一部分） |
| 引擎默认工作区 | `~/.darkhorse/harness/runs` —— 老血统还漏在文件系统里 | `crates/harness-engine/src/config.rs:41` |
| 二进制元数据 | `productName = "Darkhorse Code"`、`version = "0.1.0"` | `src-tauri/tauri.conf.json:3-4`、`src-tauri/Cargo.toml:3` |
| WebView2 user data | **没有显式指定**（直接 `WebviewWindowBuilder::new`）→ 必然落 `%LOCALAPPDATA%` | `src-tauri/src/main.rs:1688` |
| 随包文档 | 仓库有 `README.md` / `LICENSE`，但 exe 发行时**没随包** | 仓库根 |

## 三、目标形态（zip 内布局）

```
ruyix-1.0.0-win-x64/
├── ruyix.exe                 # 可执行文件（**仍自包含**：sidecar 缺失也能跑，见 R1）
├── config/                   # 全局配置目录（用户会改 → 要能备份/迁移/版本控制）
│   ├── config.toml           #   分节配置（ai / llm / harness / ui…）
│   ├── projects.toml         #   项目列表（含 current）
│   ├── mcp.toml  a2a.toml  tools.toml  skills.toml
│   └── README.md             #   "这些文件改坏了就删，程序会重新生成"
├── data/                     # 全局数据目录（可丢、可重建 → 不进备份也无所谓）
│   ├── runs/                 #   agent 沙箱产物（原 agent/runs）
│   ├── logs/debug.log        #   --debug 的落盘位置
│   ├── cache/                #   命令发现缓存等
│   └── webview/              #   WebView2 user data（**便携的关键**，见 R6）
├── plugins/                  # 预留：语法高亮插件等（v1.0.0 只建目录 + README，不实现加载）
│   ├── highlight/
│   └── README.md
├── projects/                 # 项目目录（默认工作区；"打开项目"对话框默认指向这里）
│   └── README.md
├── README.md                 # 来自仓库根（含来源与署名）
├── LICENSE
└── SHA256SUMS.txt            # 校验（zip 内每项的 sha256）
```

**四块目录的分工**（这张表是后面所有设计的基准）：

| 目录 | 谁写 | 丢了会怎样 | 随包？ | 备份价值 |
|---|---|---|---|---|
| `config/` | 用户 + 程序（表单保存） | **丢配置**（密钥、项目列表、run target） | 带一份最小可用模板 | 高 |
| `data/` | 程序 | 丢历史与缓存（会话存档、沙箱产物、日志） | 只带空目录 | 低 |
| `plugins/` | 用户 + 第三方 | 丢扩展 | 只带空目录 + README | 中 |
| `projects/` | 用户 | 丢用户自己的代码 | 只带空目录 + README | **用户自己负责** |

## 四、需求条目（每条都可验）

| # | 需求 | 判据（怎么证明它成立） |
|---|---|---|
| **R1** | **exe 仍自包含**：只把 exe 单独拷到别处双击，照样能用 | 单拷 exe → 启动 → 正常打开项目（落到遗留模式，见 R2）→ 不改一个字节的现有行为 |
| **R2** | **便携根判定**（优先级从高到低）：① `RUYIX_HOME` 环境变量；② exe 同级存在 `config/` 或 `data/` 或 `portable.marker`；③ 遗留 `~/.ruyix/code` | 三种摆放各跑一次，用 `--debug` 日志打印"本次用的根"（可核对，不靠猜） |
| **R3** | **全局路径只有一个解析点**（架构文档 §二 的 `Paths` 门面）；除它之外**不许**再出现 `home_dir()` 拼 `.ruyix` | 一条静态门禁：全仓 grep `home_dir()` 只允许出现在 `paths.rs`（引擎侧只接受注入根） |
| **R4** | 首次运行按模板创建缺失目录（幂等） | 删掉 `config/` 与 `data/` → 启动 → 目录回来、程序可用、**旧数据不动** |
| **R5** | **迁移**：检测到遗留 `~/.ruyix/code` 里有真数据 → 提供一次性导入（复制、先备份、幂等、可拒绝） | 造一份遗留数据 → 便携模式首启 → 提示出现；选"导入"→ 配置与项目列表都在；选"不导入"→ 程序仍可用（用空配置）；重复启动不会二次导入 |
| **R6** | WebView2 user data 落在便携根内（`data/webview`） | 便携模式启动后：`%LOCALAPPDATA%` 下**没有**新生成的 ruyix 数据目录；`data/webview/` 里有 |
| **R7** | 引擎默认工作区默认值改到新数据目录（去掉 `~/.darkhorse`） | `cargo test -p harness-engine` 里那条默认值断言改成新路径；全仓 grep 无 `.darkhorse` |
| **R8** | 版本与元数据对齐：`1.0.0` + `productName = ruyix` + 图标 + description/authors | exe 属性页（详细信息）里产品名与版本正确；`ruyix.exe --version`（若实现）一致 |
| **R9** | 发行包构成如上 §三（含 `README.md` / `LICENSE` / `SHA256SUMS.txt`） | 解压后逐项存在；sha256 可校验 |
| **R10** | 打包脚本进 `scripts/`（一条命令产出 zip） | 空 `target/` 起跑 → 得到 zip；脚本用 `RUYIX_HOME` 指定中间目录（不污染真实用户数据） |
| **R11** | 单实例语义在便携副本并存时不打架 | 解压两份到不同目录、各起一个实例 → 两个都正常（**待拍板**，见 §六） |
| **R12** | 文档：本单三份 + README 的"下载即用"章节更新 + `doc/release-v1.0.0.md`（中英双语，照 `release-v0.0.5.md` 的格式） | 逐份存在且在仓库里 |

## 五、非目标（这一版明确不做）

- **不做安装器**（NSIS / MSI）：仍然免安装，解压即用；
- **不做自动更新**：没有更新器、没有回连服务；
- **不实现插件加载**：v1.0.0 只把 `plugins/` 建出来 + 在文档里定清单位置（加载是 v0.14 那单的事）；
- **不动项目级 `<项目>/.ruyix/`**：它随项目走，与发行形态无关（stage / backups / proc / env / code 全部保持现位置）；
- **不重构引擎的 `workspace_root` 机制**：只改**默认值**（R7）。

## 六、待拍板点（定了我就按这个排期开工）

| # | 问题 | 我的倾向 |
|---|---|---|
| 1 | 便携根判定用"标记文件"还是"目录存在性"？ | 两者任一都算（`portable.marker` **或** 同级有 `config/`\|`data/`）—— 用户解压后不该还要手动建标记 |
| 2 | 遗留数据是"导入后停用旧目录"还是"长期双读"？ | **导入 + 写 `.migrated` 标记**；旧目录只读不动（出事能回退） |
| 3 | `projects/` 是"默认工作区"还是"随包示例项目"？ | **默认工作区**（打开项目的对话框默认指这里；不塞示例项目） |
| 4 | 单实例 mutex 是否按便携根区分？ | **按根区分**（便携版天生允许多份并存；现在的全局命名 mutex 会把第二份踢掉） |
| 5 | zip 里要不要带 `ui/` 源文件？ | **不带**（前端已编进 exe，带出去只是噪声；想要的人去 GitHub） |
| 6 | 是否继续同时发布单 exe？ | **继续发**（同一 commit 两份产物：zip 走便携模式，单 exe 走遗留模式） |

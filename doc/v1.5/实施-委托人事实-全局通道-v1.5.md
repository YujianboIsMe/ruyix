## 2. 落点形状（写侧两条通道 / 读侧三个面）

```
record_findings(items[{claim, evidence, note?, supersedes?, scope?, topic?}])
        │
        ├── scope 缺省/project ──▶ 项目记忆  finding.<claim 指纹>     （按项目 scope 隔离）
        └── scope=global +topic ──▶ 「委托人自述」user.<归一主题>      （GLOBAL_SCOPE，跨项目）
                                    同主题不同值 ⇒ 关旧区间（superseded）+ 装新值
```

- **写侧**：`agent/tools.rs::route_finding_to_memory()`（**纯函数**：进程级状态当参数收，
  所以可单测）—— 解析层 `action.rs::FindingSpec::{scope_kind, topic_key}` 先定死合法取值；
  `scope=global` 少了 `topic` **当面拒一轮**（不猜，也不编键）。
- **读侧三个面**：
  1. `read {scope:"global_mem"}` 的命中行带「用户自述 · 记于 …」，
     并且该层的口径说明写明**它不参与「以文件为准」的裁决**（`search.rs::memory_scope_note` /
     `memory_line` 两个纯函数是这条纪律的唯一落点）；
  2. **注入块**（第一屏）按 scope 换口径：全局块明说"别拿『以仓库为准』去推翻用户自述"，
     项目块照旧（`mem/retrieve.rs::block_for_prompt`）—— 这是"换个项目还答得出来"的**实际通路**：
     新项目开跑时全局块跟着首条用户消息一起进去；
  3. 系统提示词（`AGENT_SYSTEM`）+ 工具声明（`llm::TOOL_DECLS`）—— 能力不进提示词 = 不存在。
- **判据只有一条**：`mem::is_user_fact_key()`（键有没有 `user.` 前缀）。标记文案是常量
  `mem::USER_FACT_TAG`，「怎么算用户自述」不许在别处另立一套。

**为什么主题键不违背"矛盾的结论必须并存"**：那条纪律管的是**对项目的判断**
（`finding.<指纹>`，同指纹才折、不同结论各成一条）；日程是**同一个槽位在时间轴上的先后取值**
（昨天 1 场 → 明天 2 场），本来就该更新。两件事不冲突 —— 判据 4 钉住的就是它。

## 4. 能声称 / 不能声称

**能声称**：机制是通的 —— 委托人自述的事实落进全局层、**换个项目搜得到**、同主题是版本更新
（旧值留痕）、读侧三面都标了「用户自述」并且明确不吃「以文件为准」、项目树零写入。
以上每条都有可复现的判据（§3）。

**不能声称**（本刀没做，别拿它当"已解决"）：

1. **模型会不会真的用** —— `scope/topic` 是"写入权交给模型判断"的直接后果，提示词与工具声明都写了，
   但**能不能稳定判对**（哪些算"本人事实"、主题名会不会漂）是**提示词质量问题**，判据只能到
   "声明了必被正确路由"。**没有真模型跑过**：本轮全是确定性单测 + 一个零成本示例，
   真 run 读数（模型自己决定记什么、用哪个主题）**尚未采集**。
2. **主题漂移**：模型这次写 `面试`、下次写 `面试安排` ⇒ 两条并存（引擎不猜）。缓解是提示词
   要求复用 + 工具结果回执落点键，**没有**机械保证。
3. **`as_of` 的粒度**：时间戳是**秒**级；同一秒内的两次更新落进"同一时刻"，`as_of` 分不开它们。
4. **跨 session**：本刀只做"跨项目"（全局通道）；甸服的跨 session 检索仍未开（早前拍板不做）。
5. 早前候选 B/D（显式口令、"提升为全局"面板）**没做** —— 用户没声明但很重要的场合仍会漏。

## 5. 一起修掉的两个缺陷（+ 实施时抓出的第三个）

### 5.1 向量腿（`问题-…§2.5-1`）

现场：`<便携根>/global/memory/model/bge-small-zh-v1.5/` 只有 `config.json` + `tokenizer.json`，
`vectors` 表**恒 0 行** ⇒ 记忆两层只剩词法腿。

逐层查下来是**三个叠在一起**的问题，缺一个都修不成：

| # | 层 | 事实 | 修法 |
|---|---|---|---|
| a | 环境 | 缺 `model.safetensors`（96MB）。ModelScope 在本机**可达**（hf.co 不可达 —— 规格里的兜底源在这台机器上是死的） | 取回并**逐文件 sha256 核对**（三个都与 `model-spec.json` 一致），落进便携根 |
| b | 代码（仪器） | `Memory::stats()` 的 join **少写了 `\|obs_id`** ⇒ 与 `vectors.row_key` 永远不相等，**"向量条数"恒 0**，而向量其实是有的 | 键形状抽成 `mem::ROW_KEY_SQL`**唯一一份**（三处 SQL 共用）；**加判据**：写完向量后 `stats().vectors > 0` |
| c | 代码（可观测性） | `ensure_vectors` 的 `let Ok(stmt) = conn.prepare(..) else { return 0 }` —— **查询写错会长得像"没有缺向量"** | 准备失败留 `debug::note`（降级可以，静默不行） |

**b 尤其值得记**：一个**永远显示 0 的计数器比没有计数器更坏** —— 它会让人得出"向量腿坏了"的
错误结论，然后去修一处根本没坏的地方（本次差点就这么干）。同一个形状**手写在三处 SQL 里**，
错一处就是这种结果；现在只有一份。

**可复现证明（零成本、零联网）**：`examples/mem_vector_check.rs`

```bash
RUYIX_MEM_MODEL_DIR=D:/Tools/ruyix/global/memory/model \
  cargo run -q -p harness-engine --example mem_vector_check
# 实测（2026-10-11）：
#   自检：语义检索已就绪（3 个文件 / 96.3 MB）   ← 三个必需文件齐且哈希对
#   腿 = 词法 + 向量（is_available = true）
#   嵌入维度 512 · 同一文本两次的余弦 1.000000   ← 确定性
#   检索（字面不重合）：「他最近的日程安排是什么」→ 命中（纯词法腿在这一问上必然空手）
#   `vectors` 表：面板数字 2 · 库里真值 2        ← 修 b 之前这里是 0 / 2
#   ✓ 通过
```

退出码约定：`0` 通过 / `1` 有判据没达预期 / `3` **环境不齐（大声跳过，不假装通过）**。

### 5.2 跨 run 的钥匙（`问题-…§2.5-2`）

现场：会话 JSON 里**用户消息的 `run_id` 恒 `None`**，只有助手消息带 —— 某轮助手没交付
（中途致命失败）时，留痕（`ctx/<id>/transcript.jsonl`）**已经在盘上**，而链上没有任何一条消息
认得它（现象只是"少搜到几个 run"，界面上完全看不出来）。

- **引擎**：`pipeline::Sink::run_started(run_id)` 在与 run id 同一处**立刻**播出（不是等结局），
  `AgentOutcome.run_id` 照旧返回（正常收尾那条路一字不动）；
- **宿主**：`AgentSink` → `agent://run` 事件；
- **界面**：监听即落 —— **用户消息与助手消息都写**（`runningUserMsg` / `runningPlaceholder`），
  并在回复返回处做一次幂等兜底；用户气泡**不显示**那条 id 链接（它是给链用的，不是给人读的）。
- 判据：`the_run_id_reaches_the_host_even_when_the_run_fails`（空剧本 ⇒ 第一轮致命失败：
  返回值是 `Err`、sink 已收到 id、**留痕确实在盘上**）+ ui-smoke **U77** 三条新契约。

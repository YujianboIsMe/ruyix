# 四服验收：侯服 / 绥服 / 要服 的修复与判据（v1.5，2026-10-09）

> 由来：用户「今天必须把五服搜索的**甸服、侯服、绥服、要服**做好，荒服明天做」。
> 五服名字与 scope 的对应（按离王畿由近及远，只活在文档里）：**甸服**=session（今天已修好）·
> **侯服**=project_mem · **绥服**=global_mem · **要服**=files · **荒服**=kb（明天，第二刀）。
> 甸服的教训是**"实现了 ≠ 用得上"**（14 条判据全绿，用户那个场景一条都搜不到），所以这一轮对三服
> 用的是同一把尺子：**存了吗 / 能搜吗 / 真跑通吗**，每服立一条可判定的判据。

---

## 1. 现状核对（先看真实数据，不看代码里"应该有"）

查的是用户真实便携根的库：`<便携根>/global/memory/mem.db`（92 KB，不是空的）。

| 层 | 库里有什么（2026-10-09 实查） | 判定 |
|---|---|---|
| 绥服 `_global` | `events` 44 条**全是** `obs`、key 只有 `tool.cargo` / `tool.git` / `tool.docker`；`beliefs` 3 条（同一批）；`receipts` 22 条 `prompt_block` | 机制通、**内容薄**（只有命令发现） |
| 侯服（项目 scope） | **0 条**（`events` / `beliefs` / `receipts` 里一条都没有） | **空转**：问什么都是空的 |
| 要服 `files` | 数据就是磁盘本身（不需要"存"），但**清单来源**有问题（见 §3） | 能用，但漏一个纪律 |

三处根因：

1. **没人往项目 scope 写**：命令发现写的是 `GLOBAL_SCOPE`（对），压缩收据写的是"当时的 scope"（错，
   见下），而**模型跑一遍确认下来的结论从来没进过记忆库** ⇒ 侯服永远是空的。
2. **压缩收据的 scope 写错了**：宿主里 `record_compaction(..., &engine::mem::scope(), ...)` 在
   `set_scope(...)` **之前**执行 ⇒ 收据落进"上一次的 scope"（新进程里就是 `_global`；用户切项目时
   更糟——落进**上一个项目**）。22 条收据全在 `_global` 就是这个 bug 的现场。
3. **要服只按硬编码目录名跳生成物**，**不认 `.gitignore`** —— 而老路 `git grep` 是认的 ⇒
   用户自定义忽略的目录（数据集、构建产物、本地配置…）会被整棵扫进来、烧光检索预算。

## 2. 侯服（project_mem）：结论进项目记忆

- **写**：`Ctx::record_finding` 记下一条结论后**顺路**写项目记忆 —— `mem::record_finding_obs`
  （`mem/mod.rs`）：`key = finding.<claim 的 sha256 前 8 位>`，`value = claim + 证据 + 说明`，
  `origin = Agent`。
  - **为什么必须带 key**：`record_obs` 只在 key 非空时**折叠成信念**，而检索读的是信念 ——
    无 key 的观察进不了检索，等于没记。
  - **为什么键用 claim 的指纹而不是"主题"**：主题要从自由文本里猜，猜错就把两条**不该合并**的结论
    折成一条；而彼此矛盾的结论**必须并存**（与检索那条"冲突并列、引擎不裁决"是同一条纪律）。
    同一条 claim 才会折（重复记不积压）。
  - 记忆坏了不打扰 run（与 `record_discovery` 同款：失败不写日志也不抛）。
- **判据**（`mem/tests.rs`）：`侯服_结论写进项目记忆后按内容搜得到`（写 → 按内容检索 → 命中正文带
  结论与证据）· `侯服_同一条结论折不同结论并存`（两条矛盾结论都在）。

## 3. 绥服（global_mem）：机器事实也进全局

- **写**：宿主每次跑（`agent_reply`）把 `machine::facts()`（**不含"当前时间"**）记成全局观察，
  `key = machine.note`（固定键 ⇒ 折叠成一条信念、永远最新）。时间每次都变、记进去天天翻新，
  所以单开了 `facts()` 这个出口。
- **为什么**：全局记忆此前只有命令发现 —— "这台机器什么 GPU / 多少内存"是**跨项目通用**的事实：
  记一次，换个项目也搜得到。
- **判据**：`绥服_全局事实按内容搜得到`（`tool.<bin>` 与新加的 `machine.note` 都能按内容搜到；
  且全局事实**不许**出现在项目层里 —— 层与层不串）。
- **真模型现场证据（2026-10-09，`examples/mem_layers_smoke.rs`，flash）**：
  - 第 1 个 run（39 轮 / 66k token）：项目里两处说法冲突（`db/schema.sql` 是 `VARCHAR(72)`、
    旧文档写 `varchar(60)`），模型**自己**核对磁盘并记了 **4 条 findings**；
  - 库里的现场：项目 scope 出现 `key = finding.db3fc043`、`status = active`、
    值 = 结论 + 证据 `db/schema.sql:3-5` + 说明 —— "结论进了项目记忆"是真的；
  - **把两份来源文件删掉**再跑第 2 个 run（83 轮 / 232k token）：它**搜了 `project_mem`**，
    答案 `VARCHAR(72)`，并自己写明"这份文件已不在，答案来自本项目的记忆层（beliefs 表，
    scope=…，key=finding.db3fc043）"⇒ **只可能是侯服给的**；
  - 全局层**没有**串味（`global_now(m,"password")` 为空）。
  - ⚠ 一条要看的读数：第 2 个 run 花了 **83 轮 / 232k token** 才答出来 —— 答案本身很便宜，
    轮数说明它在"文件没了还要不要再找一遍磁盘证据"上打转（提示词那条"本地证据比检索结果硬"
    在**来源已消失**时把它的劲使到了错地方）。这是下一刀要看的，不是这一刀能顺手改的。
- **还不能自动化的部分**：`machine.note` 的写入在**宿主**（`agent_reply`）里 ⇒ 这条冒烟覆盖不到，
  要等新构建的实例真跑一次才有现场证据；这一轮验的是"写成的形状能按内容搜到"（形状层）。

## 4. 要服（files）：清单来源问 git（认 `.gitignore`）

- **改**：`files()` 的清单来源改成「**git 优先 + 目录树兜底**」——
  `gitops::listed_files` = `git ls-files --cached --others --exclude-standard -z`
  （已跟踪的 + 未跟踪但没被忽略的；`-z` 防怪文件名；路径相对被搜的目录给出）。
  - **为什么不自己实现 gitignore 匹配**：patterns / 取反 / 目录专属 / 嵌套 `.gitignore` …
    重写一套等于把 git 的定义抄一遍，抄错的地方就是"搜不到"或"搜到不该搜的"。**git 就是这个规则的
    定义者**，问它。
  - 不是仓库 / 没装 git ⇒ 退回目录树遍历，并把"**`.gitignore` 不适用**"写进结果
    （"没搜"与"没有"必须可分）。
- **顺带补的守卫**：目录树遍历加了**已访问目录**（规范化路径）集合 —— 符号链接 / Windows junction
  指回祖先会绕死，而 junction 在这台机器上是常态（`AppData\Local\Temp` 本身就是）。
- **判据**：`the_files_scope_honors_gitignore_with_a_control_arm` —— **两个方向都钉**：
  有 `.gitignore` ⇒ 被忽略的文件**搜不到**；**没有** ⇒ 同一个文件**必须搜到**（对照臂：证明排除来自
  忽略规则，而不是"目录名眼熟被跳了"）。只钉前一个方向的话，任何"什么都搜不到"的实现都会绿。

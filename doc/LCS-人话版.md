# LSC（Log-Structured Context）人话版

> 这份文档讲的是我们 v1.2 搬进 ruyix 的那套**上下文管理算法**。
> 上游：`D:\Projects\Python\context-algorithm`（README + 论文 `paper/cn`、`paper/en` + 实验 `results/`）。
> 落地代码：`crates/harness-engine/src/agent/context.rs`（布局）、`ledger.rs`（去重账本）、
> `capsule.rs`（侧存）、`scheduler.rs`（重基线调度）；需求与实测记录在 `doc/v1.2/`。

## 0. 先说名字（容易混，先对齐）

| 你看到的写法 | 指的是什么 |
|---|---|
| **LSC** = **L**og-**S**tructured **C**ontext | 就是这份文档的主角：上游仓库 `context-algorithm` 里的那套算法，全称「日志结构化上下文」 |
| 我这边文档里之前写的「LCS 算法迁移」 | 同一个东西（仓库里 `doc/v1.2/需求-...-v1.2.md` 的标题就是「LSC 算法迁移」）；两种拼法指的是它 |
| **LCS** = **L**ongest **C**ommon **S**ubsequence | **另一码事**：最长公共子序列，经典动态规划题（`git diff` 的底层）。它和 LSC 只差字母顺序，见本文最后 §9 |

一句话区分：**LSC 管「上下文怎么排布、什么时候压缩」；LCS 管「两段文本怎么对齐出差异」。**

## 1. 它要解决的事，用一句话说

> 把 agent 的上下文当成**日志文件**来管：**只往后追加，不改前面写过的东西**；
> 需要压缩时，不做「逐句删改」，而是**偶尔做一次可调度的大重写（重基线）**。

**类比**：数据库里有一种存储叫 LSM-Tree（日志结构化合并树）——新数据只追加到日志尾，
不是就地改；攒够了再做一次「合并（compaction）」，把旧日志压成一个新的基底。
LSC 就是把这个套路搬到 LLM 的对话上下文上：

| LSM 存储 | LSC 上下文 |
|---|---|
| 日志只追加 | 对话历史**只追加**，不回头改老消息 |
| 攒够了做一次 compaction | 攒够了做一次**重基线**（把老历史压成一条摘要，重开一段） |
| 内存表 + 磁盘层 | 上下文里放「摘要」，被压掉的**正文**放 **capsule 侧存**（磁盘文件） |
| 什么时候 compaction 由代价决定 | 什么时候重基线**由动态规划算**（不是拍一个固定轮数） |

## 2. 为什么非要这么干（四个疼点，就是 LSC 的四个目标）

长任务跑起来（我们的工具循环单次 run 最长 96 步）会同时疼四件事：

| # | 疼点 | 说人话 | LSC 的目标 | 我们的可测指标 |
|---|---|---|---|---|
| **G1** | **前缀缓存被砸** | 大模型按「请求前面的公共部分」计费/加速。只要**开头改一个字**，后面全部重算。而我们以前**每轮**把「进展笔记」拼进 system 提示 ⇒ 每轮都在砸开头 | **前缀稳定**：最大化可复用比例 | 相邻两轮请求的**公共前缀字节占比**；厂商回报的命中 token 为准（`cache_read()`） |
| **G2** | **上下文爆掉** | 对话只涨不缩，迟早撑爆预算或被 `max_tokens` 截断（截断 = 模型话说一半，输出直接废） | **有界上下文**：任意时刻 prompt ≤ 预算 B | prompt token 的上界 + 是否出现「被截断」标记 |
| **G3** | **同一件事反复做** | 模型忘了自己读过，于是再读一遍同一个文件、再跑一遍同一条命令——纯浪费轮次和钱 | **零冗余工具执行**：纯工具 + 资源没变 ⇒ 不执行第二次 | 重复调用次数（规范化后的调用键 + 版本未变） |
| **G4** | **压掉就找不回来** | 老内容被摘要顶掉后，模型想回头查证，只能「重新读一遍」——正是把 G3 又喂了一遍 | **事实无损可得**：被压掉的正文靠**侧存**召回，**不靠重跑工具** | 「为拿回已读内容而重跑工具」的次数；召回内容与原文**逐字节一致** |

## 3. 三块拼图（缺一块都站不住）

### 3.1 布局契约 `[S][E][A]` —— 先把形状摆对

请求体切成三段，**每段的改写规则不同**（`agent/context.rs` 抬头那张表就是这三条不变式）：

```text
[S 不可变根]  system 提示 + 工具声明 + 任务原文        ← 逐字节不变（一个字都不许动）
[E 只追加梯子] 一条条追加的摘要/事实                    ← 只能往后追加，不许回头改老条目
[A 易变尾]    本轮的临时拼装（当前问题、最新观察、待办）  ← 每步重建，随时可丢
```

三条不变式，以及**违反它的代价**：

| 不变式 | 内容 | 为什么这么严 |
|---|---|---|
| **I1** | `S` 字节不变 | 改了 `S` ⇒ **它后面所有缓存块失效**（上游论文里的定理 1）。我们以前每轮重建 `msgs[0]`，等于每轮把整段缓存砸一次 |
| **I2** | `E` 只追加 | 就地改写老条目 = 同样作废其后缓存，还违背「历史不可改」这条底线 |
| **I3** | `A` 可重建 | 丢掉 `A` 之后，仅凭 `S + E` 与侧存就能重建它；否则「被压掉的内容」只能靠**重跑工具**找回 |

还有个细节：`align()` 把内容对齐到**块边界**，免得为了塞半句话跨块——跨块也是浪费。

> **为什么先做布局、后做调度**：形状错了，后面每个策略都建在流沙上。所以 P1 只动结构、零算法风险。

### 3.2 去重账本 `ContextLedger` —— 「这活我刚干过」要有据可依

判「这是重复劳动」不能靠感觉，要**可证**。三件事：

1. **规范化**：`read("./a")` 和 `read("a")` 是同一个调用；`git diff -- ./a` 与 `git diff -- a` 也是同一个（这条是黄金测试逼出来的——少了它，换个写法就能绕过去重）；
2. **包含关系**：整文件读过一次，再读它的某个区间就是**白读**（`hi = -1` 表示「到末尾」）；
3. **版本有效期**：文件有 `(mtime, size)`；本会话写过的路径用**内容哈希**；仓库用 `git HEAD + 工作树脏否`。**拿不到版本 ⇒ 就老老实实执行**（宁可多跑一次，不可给旧数据）。

命中重复时**不执行**，但把**上次的原文**还回去并标一行：`（这条调用上次已经执行过，结果未变）`。
「失败的结果不入账」——一次瞬时空手不许把结论钉死。

### 3.3 重基线调度 `RebaseScheduler` —— 「什么时候压」用算的

老做法是拍一个数字（「保留最近 N 轮」）。LSC 的做法是把它变成一个**代价最小化**问题：

- 携带一个 token，每轮付一点「携带费」（`carry_rate`）；
- 丢一次，付一次「重建费」（`rebuild_rate` × 长度）——重建还要**打断前缀**，那是隐藏成本；
- 状态只有一维：「距离上次压缩几轮了」⇒ 可以直接**反向动态规划**算最优压缩点；
- 每轮用**实测增长**做一次滚动重规划（MPC），只取第一步；
- 跑得比视野还长（horizon 未知）⇒ 退化成 **ski-rental**（在线策略，竞争比 `e/(e−1) ≈ 1.582`，意思是「最多比事后最优多花 58%」）；
- 判定顺序是 **预算 → 安全下限 → ski-rental/DP**（预算越界是**强制**压缩，没得商量）。

我们给它加了一条 `MARGIN = 5%` 的**材料性下限**：DP 算出来的往往是「现在压」和「稍后压」的差额，
只有几个百分点——为了省这点就把前缀打断，不划算。差额不够大就**不动**。

## 4. 被压掉的正文去哪：capsule 侧存

压 ≠ 删。被折掉、或被去重命中要「还回去」的**全量结果**会落到磁盘：

```text
<便携根>/projects/<项目键>/ctx/<run-id>/
    <step>-<tool>-<hash8>.txt      # 正文
    index.jsonl                    # 一行一条索引：file/step/tool/key/target/version/sha256/len
```

- **绝不写用户仓库**（IDE 的状态属于 IDE）；
- 召回时**逐字节 sha256 校验**，不符就报错并计数——**绝不静默给脏数据**；
- 因此账本里存的是「引用」而不是正文 ⇒ **正文不常驻内存**，内存上限这件事自然消失；
- 写盘用 `.part` + rename 的原子写（和模型缓存同一套）。

## 5. 怎么知道它真的有用（读数，不是感觉）

| 结论 | 读数 | 怎么量的 |
|---|---|---|
| 前缀占比真的上去了 | **54.1% → 75.1%（+21.0 个百分点）**（脚本化臂 33.2% → 72.4%） | 同一份动作序列过两臂（**配对回放**，带保真校验） |
| 重复执行被消灭 | **2 次 → 0 次** | 真轨迹回放，逐条对着上游导出的决策表 |
| 压缩次数减少 | **8 次 → 1 次**（策略更会挑时机） | 脚本化配对臂，两臂都开着老机制 |
| 命中 token 有真值 | 厂商回报的 `cache_read` 才是真值（拿不到 ≠ 命中 0） | 抄 `Usage::cache_read()`：三家字段名都不一样 |
| 召回无损 | 召回内容与原文 **sha256 相等**；「为召回而重跑」= **0 次** | capsule 侧存的判据 |

**一条被我们自己推翻的判据**（值得记住）：不能拿 G1（前缀占比）当「该不该压缩」的判据——
压得越勤，prompt 越小，而那一大段固定开头是不变的，比值反而更高，等于**奖励多压**。
P4 的判据因此改成：**G2 不越界 + 压缩次数不多于老规则**。

**一条计量学教训**：读数必须走**配对**（同一份输入过两臂）。未配对时我们两次观察得出相反结论
（44.9→60.4 与 77.7→69.6）——因为那量的是「这一趟怎么干」，不是布局。

## 6. 我们真踩过的坑（比理论更值钱的那部分）

1. **每轮重建 `msgs[0]`**：把进展笔记拼进 system，看着无害，实际每轮砸掉整段前缀缓存——这是 LSC 进这个仓库的理由。
2. **「逐字相同」不能当判据**：多线程浮点归约的结果不稳定，判据要比**决策**，不比字符串。
3. **判据不许建在结构不变的部分上**：见上面那条 G1 的反例。
4. **折叠点会断开前缀**：所以压缩有隐藏成本，必须带门槛（MARGIN），不能「能压就压」。
5. **开关要能一行回滚**：`agent.ctx.layout` / `dedup` / `capsule` / `schedule` 每个都独立可关，关掉后行为与老版本一字不变。（出厂默认全开是拍板 7 定的。）

## 7. 一句话版（面试/讲给别人听）

> LSC 把长任务的上下文当**只追加的日志**：前面写得死死的不动（前缀缓存才能复用），
> 信息靠**往后追加**累积；量大了不做逐句删改，而是**按代价模型算出来的时机做一次重基线**，
> 把老历史压成一条摘要，被压掉的正文进**侧存**、按哈希校验召回。
> 它的四条目标是：前缀稳、上下文有界、工具不重复执行、压掉的事实还能无损拿回来。

**名词表**：`S/E/A` = 不可变根 / 只追加梯子 / 可重建尾；`rebase` = 重基线（压缩的正式动作）；
`capsule` = 侧存（被压正文的落点）；`horizon` = 视野（还要跑多少步）；
`MPC` = 用实测增长每轮滚动重规划；`ski-rental` = 视野未知时的在线策略。

## 8. 顺带：LCS（最长公共子序列）是什么，以及我们为什么**没用**它

**它是什么**：给两段序列（通常两行文本、两个文件，或 DNA 两条链），求**最长的、在两段里都按原顺序出现**
的子序列。经典解法是动态规划：`dp[i][j]` = 「A 的前 i 个」和「B 的前 j 个」的最长公共子序列长度，
转移 `dp[i][j] = dp[i-1][j-1] + 1`（相同）或 `max(dp[i-1][j], dp[i][j-1])`（不同），
复杂度 `O(nm)`。`git diff`、`difflib` 这类「对齐」工具就用它的变体。

**我们为什么没用它**（真踩过）：拆 `main.js` 那次，本来想用 `difflib`（底层是这类对齐）来判
「这段代码在主文件里、那段在模块文件里」。结果**贪婪对齐会漂**：它把某个函数的**收尾三行**
判成「主文件独有」而留在原地——主文件里于是留下一个**孤立的 `}`**，那是语法错误，不是「少删一行」。

改用了笨办法：**逐字符扫描算每一行的行首括号深度**（字符串/模板串/正则/注释/括号都认），
深度回 0 就是一个顶层项的结束。笨、但可枚举、可判。

**教训**：模糊对齐适合「给人看的差异」，不适合「给程序用的切分」。要切分，就得有一条
**能逐行验算的判据**。

# 重构：主循环抽离到 `agent/tool_loop.rs`

**起因**（用户指令）：*"harness-engine 里的 agent.rs 里的 run_with_ask 函数，代码特别长，独立出来，
抽取到专门的 rs 文件里。"*

## 一、事实与做法

| 项 | 值 |
|---|---|
| 改动前 `src/agent.rs` | 4361 行 |
| `run_with_ask` 占 | **3579–4358 行 = 780 行**（自成一个函数，占全文 18%） |
| 改动后 | `agent.rs` **3585** 行 ＋ `src/agent/tool_loop.rs` **795** 行（含 14 行模块文档） |
| 搬运方式 | **逐字未改** —— 一个字符都不动，`git diff` 里是一段纯位移，可审 |
| 对外路径 | 不变：仍是 `harness_engine::agent::run_with_ask`（宿主 `src-tauri` 一行没改） |

**为什么落点是 `src/agent/tool_loop.rs`**：`src/agent/` 这个目录早就存在（`tests.rs` 在里面），
是 `agent.rs` 的"子模块目录"。Rust 的私有可见性是**定义模块 + 它的所有后代**，所以子模块写
`use super::*;` 就能直接用父模块的私有项 —— `Ctx` / `Action` / `RoundSlot` / `GateState` 以及
全部私有辅助函数（`fold_history` / `wave` 调度 / `settle_steps` / `gate_before_final` / 解析器…）
**一个都不需要改成 `pub`**。这次是**文件切分**，不是可见性改造：没有任何一项的可见性被放宽。

`agent.rs` 里留下的是接线：

```rust
mod tool_loop;
pub use tool_loop::run_with_ask;
```

`agent/tests.rs` 的 `use super::*` 通过这条 `pub use` 照样拿到 `run_with_ask`，一行没改。

**边界为什么切在这里**：切出来的只有"循环本体"。它依赖的零件（动作解析与校验、波次调度、
历史折叠账本、计划收尾、验证门禁）留在 `agent.rs`。这些零件与 `Ctx` 是**跨阶段共享的可变状态**，
真要再往下拆（把循环拆成几个私有函数），得先把 `ctx` / `gate` / `out` / `plan_cursor` 的共享
状态包成一个结构体并立好分阶段判据 —— 这次**没做**，因为那是一次真正的行为重构，
和"把 780 行挪个地方"不是一件事。

**判据（与搬运前逐项相同）**：引擎 `353 passed + 8 ignored`、宿主 `121 + 3`、`clippy` **0**、
`cargo fmt --check` 干净、`node scripts/check-style.js` PASS、`node scripts/ui-smoke.js` **310/310**、
`cargo run -q -p harness-engine --example agent_loop_smoke` 32 项断言全绿。

## 二、这次切分踩出来的两个门禁缺陷（都不是新写的代码坏，是门禁自己不对）

### 缺陷 1：契约钉的是**文件名**，不是**模块** —— 8 条假红

`ui-smoke.js` 把引擎侧的全部契约（U15 计划收尾/U15 计划执行/U19 命令发现/U23 服务托管×2/
U25 批调用/U36 历史折叠/U26 提问通道）都读自**一个文件**：

```js
const intentRs = read("crates/harness-engine/src/agent.rs");
```

循环体一搬走，这 8 条立刻红 **"契约破了"** —— 其实只是**文件挪了**。门禁的判据没错，
取面的粒度错了：契约的对象是**模块**。

**修**：新增 `readEngineAgent()` = `agent.rs` ＋ `src/agent/*.rs`（**排除 `tests.rs`**，
免得某条契约被测试里的字符串凑上），那里改用它。以后引擎 agent 模块再怎么切文件，
这些契约都不会因为"搬了家"而红。

### 缺陷 2：整行锚点在 CRLF 工作树上**永远不命中** —— 2 条假红，且是长期旧账

`read()` 是 `readFileSync(..., "utf8")`，**不做行尾归一**。而本机 `core.autocrlf=true`：
工作树是 CRLF、仓库里的 blob 是 LF。于是

```js
mainSrc.indexOf("\n}\n")   // 恒为 -1
```

U33（右键复制路径回放）与 U34（自动保存不回刷 UI）各红一条，报的话是
**"main.js 里定位不到源码（切片锚点失效）"** —— 看起来像前端代码坏了，实际是行尾。

**只有整行的锚点会死**：先导锚点 `\nfunction foo(` 在 CRLF 上照样命中（`\r` 落在 `\n` 之前），
所以同一份文件里别的切片检查一直绿 —— 这也解释了为什么红的恰好是这两条。

**修**：新增 `readLf()`（行尾归一）并在 U33/U34/U45 三处改用它。**规矩是归一，不是把锚点
改成 `\r\n`** —— 那样在 LF 工作树上又反着红，等于把"按机器变色"换个方向而已。

> 顺带：这两条红是**本次改动之前就有**的（`git stash` 掉本次改动复跑证实：基线 298/301，
> 红的就是 U34/U33/U43）。它们长期潜伏的原因是：`indexOf` 找不到锚点时，检查会 `if (...) return;`
> 提前退出，**后续检查一起不跑** —— 所以总数会从 310 掉到 301，"绿"和"红"在总额上都看不出来。

### 待观察 3：U43（终端几何探针）偶发红

两次 ui-smoke 跑里它报"1 项不通过"，另两次绿；**单独连着跑 5 次全绿**。怀疑是负载下的时序
（等布局落定不够）。没复现就不改：下次再红时，收紧探针里那次等待的**判据**
（等 `.xterm-screen` 尺寸稳定两帧再断言），**不要**改断言里的几何数值。

## 三、护栏（写给下一个人）

1. **门禁读源码要按模块读，别按文件名读** —— 文件会搬家，模块不会。
2. **凡是按 `\n` 切整行的断言，一律走 `readLf()`** —— 本仓库工作树是 CRLF。
3. **切分的判据是"测试数字逐项不变"**，不是"编译过了"。纯位移的改动如果让任何一条断言
   变红，先怀疑门禁，别急着怀疑代码。
4. 想继续拆 `run_with_ask`（它还能按阶段拆），先立分阶段判据，再动共享状态的结构。

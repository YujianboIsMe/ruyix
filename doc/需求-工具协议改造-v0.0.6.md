# 需求：标准工具协议改造（收动作走 `tool_calls`）
## 归属版本：v0.0.6 · 状态：**已实施**（2026-09-21）· 提出：2026-09-21

> 用户原话：*"开始吧，进行标准工具协议改造，彻底解决这个问题。"*
> （"这个问题" = 模型自带的工具调用标记（DSML）漏进 content，让"算对了的命令"整轮作废，
> 诊断与 A/B 见 `doc/问题-DSML标记泄露.md`。）

## 1. 为什么是这条路（A/B 已经给过答案）

4 臂 × 8 轮对照（`scripts/dsml-ab-probe.py`，直打官方端点、temp=0、同一条上下文）：

| 臂 | 带标记 | 走 `tool_calls` |
| --- | --- | --- |
| A `response_format=json_object`（旧现状） | 2/8 | 0 |
| B 只有提示词 | 1/8 | 0 |
| C **声明 `tools`** | **0/8** | **6/8** |
| D `tools` + `json_object` | **0/8** | **6/8** |

⇒ 泄露的根因是"引擎从不声明 `tools`"（模型的原生调用无处可去），**不是** json_mode 冲突；
声明 `tools` 之后零泄露。真跑侧的基线是 **5/16 轮泄露**。

## 2. 设计：混合形态（只改"入口"，不动下游）

**声明 `tools` 收动作 + 自己维持消息链**：

```
请求：messages(自家格式) + tools[read/write/execute/connect/plan/ask_user/final] + response_format
响应：优先读 message.tool_calls ──┐
                                ├─→ parse_tool_calls() → Vec<Action>  ← 与老协议同一个枚举
响应：没有 tool_calls 时读 content ┘                                  （下游零改动）
下一轮：assistant 回显"它自己发的那串调用" + user 观察（沿用既有形状，不做 tool 角色记账）
```

四条取舍与理由：

1. **工具名/参数形状与解析器一一对应**：`llm::TOOL_DECLS` 是唯一一份声明表（表驱动），
   参数那一层就是 `agent::parse_one` 眼里的 `args`；契约由单测
   `tools_cover_every_parser_capability` 钉住（加能力 = 改表 + 改解析器 + 改断言）。
2. **严格只认工具调用**（2026-09-24 修订，见 §6）：content 里那套**不执行**，只作"识别 + 纠正"
   —— 引擎会认出它想调哪个工具、点名说"形状对、通道错"，然后让模型用工具重发。
   `llm.tool_protocol = false` 才回到老协议的兼容通道（`parse_actions` 照旧执行），**一行回滚**。
3. **`tools` 是"每次调用"的参数，不是全局配置**：工具语义只属于工具循环。plan / generate /
   repair / reflect / eval 是"单发一次拿 JSON 回来"的生成调用，给它们声明工具会让模型去调
   工具、content 变空，而它们只认 content —— 等于把那些阶段自己打瘸。所以 `llm::chat(...)`
   多了个显式 `tools` 形参（agent 与步骤执行体传 `cfg.llm.tool_protocol`，其余一律 `false`）。
4. **不在消息链上做 tool 记账**（不构造 `role="tool"` + 逐条对 id）：那会牵动历史折叠
   （`RoundSlot` 假设一轮一条观察消息）、批次的所有观察落点与上下文体积。C/D 两臂的历史里
   **全是老式 JSON**，模型照样 6/8 走工具协议 ⇒ 历史形状不会让模型不用工具。
   已备好的通路（`ChatMessage.tool_calls` / `tool_call_id` / `tool_result()`）留着，
   将来真要切"纯标准协议"时不用再动结构。

## 5. 边界与未做

- **只覆盖 `/chat/completions`**：`/responses`（`function_call` 项）与 anthropic（`tool_use`
  块）的工具形态各是一套，本次不映射 —— 那两条路保持老协议，与改造前逐字一致
  （`extract_responses` / `extract_anthropic` 里都写了这句）。
- **历史链仍是自家格式**（assistant 回显 + user 观察），不是 `role="tool"`；见 §2.4 的理由。
- **`final` 是工具，但不是"第五种能力"**：它是收尾（老协议里是 `final` 字段）；控制动作
  （`plan` / `ask_user` / `final`）依旧不许进批。
- **老协议不再执行，但仍要"认得出"**：`tool_protocol=false` 时才执行 content 里的动作。
  严格模式下它是**识别器 + 纠正器**（`content_channel_error`）：认出形状（`parse_one` →
  参数形状 → 再往里一层）→ 点名 → 拒。为什么留识别：只回"无法解析"模型会换包装重发，见 §6。

## 6. 严格化修订（2026-09-24，同一版本内）—— 用户批"按 C 改，要标准化"

### 6.1 触发它的真现场（cloud-shop 启动前后端，18 轮）

第 12 轮还走工具协议，**第 13–17 轮连烧五轮**，全部是同一个 final 答复换包装：

| 轮 | content 形状 | 当时引擎的判定 |
| --- | --- | --- |
| 13 | `{"answer": "前后端都已启动…"}` | 外层缺 `tool` |
| 14 | `{"tool":"final","args":{"answer":…}}` | 未知能力 "final" |
| 15 | 同 14 | 未知能力 "final" |
| 16 | `{"name":"final","arguments":{"answer":…}}` | 外层缺 `tool` |
| 17 | 同 14 | 未知能力 "final" |
| 18 | **真工具调用** `final({answer})` | ✓ 交付 |

**两个成因，都是上一版改造自己留下的**：

1. **兼容层没跟上新词汇**：`final` 在新协议里是**工具名**、参数键叫 `arguments`，而 `parse_one`
   只认老词汇（`final` 是字段、只认 `args`）—— 模型恰恰因为**学会了新词汇**才被拒。
2. **失败反馈在教相反的东西**：每轮只回"请重新只输出一个 JSON 对象"，等于把模型**按回**它
   已经在用的通道；而系统提示词要求"用工具调用、别写进 content"。两条提示打架 → 五轮空转。

（另：同一份日志里 6 个带模型自带标记的响应块，4 个是改造前的旧账、**2 个都是 reflect**；
agent 主循环当天 **0 次泄露** —— 工具协议对主循环是有效的。）

### 6.2 改了什么

- **A｜词汇对齐**：`parse_one` 认 `final` 作能力名、`args | arguments`、`name | tool`、
  裸 `{"answer": …}`（四种能力里只有 final 认这个键，无歧义）。
- **C｜严格闸门**（`llm.tool_protocol`，默认开）：content 里的动作**一律不执行**；拒绝时
  **先认出来再拒**（`content_channel_error`）：
  - 认三层：按动作解析 → 按**参数形状**（`cmd/op/handle`→execute、`path+content/edits`→write、
    `path`→read、`steps`→plan、`question`→ask_user、`action/server/agent`→connect）→ 再往里
    一层（`{"arguments":{…}}`）；
  - 第 1 次讲清道理（"形状是对的，通道错了"），第 2 次起只说短话（`content_strikes`）；
  - 认清形状**只用于把话说清，永不用于执行** —— 参数形状在四种能力的协议内是唯一解，但
    "替模型决定做什么"这件事仍然不干。
- **反馈口径**：`parse_failure_feedback(.., tools = true)` 不再说"请重新只输出一个 JSON 对象"，
  改成"请改用工具调用表达动作"。
- **提示词**：规则 1 改成"**严格只认工具调用**；写进 content 一律不执行（会被退回重发一轮）"。
- **测试**：`testllm::fake_llm` 把老形状的剧本**翻译成工具调用**再发（上百条既有脚本一行不用改，
  验的仍是主路）；要"就发这个 content"用 `fake_llm_raw`。新增三条：严格拒（用另一个文件名核对
  落盘事实）、§6.1 那五个真实形状逐一被点名、回滚开关恢复 content 通道；`parse_failure_feedback`
  的严格/宽松两套口径另有断言。

### 6.3 判据

引擎 **342 passed + 8 ignored**（宿主 121 + 3）、clippy **0**、fmt 干净、check-style PASS、
ui-smoke **273/273**。

### 6.4 仍未做（已知，不装作没有）

**reflect 复核那一轮仍会漏**（今天两次运行各一次）：content = `{"path": "…vite.config.js"}` +
三行闭标签 → 复核解析失败 → `[reflect] 结论：unknown（0 条 findings）`。原因是 reflect 属于
§2.3 那类"单发一次拿 JSON 回来"的调用、按设计不给它声明 tools，而它的活儿恰恰是**去 read
核对证据** → 原生调用无处可去。修法（B 方向）：给 reflect 声明它真需要的 `read` 工具，
让它的动作也走 `tool_calls`。

# 需求：标准工具协议改造（收动作走 `tool_calls`）
## 归属版本：v0.0.6 · 状态：**已实施**（2026-09-21）· 提出：2026-09-21

> 用户原话：*"开始吧，进行标准工具协议改造，彻底解决这个问题。"*
> （"这个问题" = 模型自带的工具调用标记（DSML）漏进 content，让"算对了的命令"整轮作废，
> 诊断与 A/B 见 `doc/问题-DSML标记泄露.md`。）

## 1. 为什么是这条路（A/B 已经给过答案）

4 臂 × 8 轮对照（`scripts/dsml-ab-probe.py`，直打官方端点、temp=0、同一条上下文）：

| 臂 | 带标记 | 走 `tool_calls` |
| --- | --- | --- |
| A `response_format=json_object`（旧现状） | 2/8 | 0 |
| B 只有提示词 | 1/8 | 0 |
| C **声明 `tools`** | **0/8** | **6/8** |
| D `tools` + `json_object` | **0/8** | **6/8** |

⇒ 泄露的根因是"引擎从不声明 `tools`"（模型的原生调用无处可去），**不是** json_mode 冲突；
声明 `tools` 之后零泄露。真跑侧的基线是 **5/16 轮泄露**。

## 2. 设计：混合形态（只改"入口"，不动下游）

**声明 `tools` 收动作 + 自己维持消息链**：

```
请求：messages(自家格式) + tools[read/write/execute/connect/plan/ask_user/final] + response_format
响应：优先读 message.tool_calls ──┐
                                ├─→ parse_tool_calls() → Vec<Action>  ← 与老协议同一个枚举
响应：没有 tool_calls 时读 content ┘                                  （下游零改动）
下一轮：assistant 回显"它自己发的那串调用" + user 观察（沿用既有形状，不做 tool 角色记账）
```

四条取舍与理由：

1. **工具名/参数形状与解析器一一对应**：`llm::TOOL_DECLS` 是唯一一份声明表（表驱动），
   参数那一层就是 `agent::parse_one` 眼里的 `args`；契约由单测
   `tools_cover_every_parser_capability` 钉住（加能力 = 改表 + 改解析器 + 改断言）。
2. **严格只认工具调用**（2026-09-24 修订，见 §6）：content 里那套**不执行**，只作"识别 + 纠正"
   —— 引擎会认出它想调哪个工具、点名说"形状对、通道错"，然后让模型用工具重发。
   `llm.tool_protocol = false` 才回到老协议的兼容通道（`parse_actions` 照旧执行），**一行回滚**。
3. **`tools` 是"每次调用"的参数，不是全局配置**：工具语义只属于工具循环。plan / generate /
   repair / reflect / eval 是"单发一次拿 JSON 回来"的生成调用，给它们声明工具会让模型去调
   工具、content 变空，而它们只认 content —— 等于把那些阶段自己打瘸。所以 `llm::chat(...)`
   多了个显式 `tools` 形参（agent 与步骤执行体传 `cfg.llm.tool_protocol`，其余一律 `false`）。
4. **不在消息链上做 tool 记账**（不构造 `role="tool"` + 逐条对 id）：那会牵动历史折叠
   （`RoundSlot` 假设一轮一条观察消息）、批次的所有观察落点与上下文体积。C/D 两臂的历史里
   **全是老式 JSON**，模型照样 6/8 走工具协议 ⇒ 历史形状不会让模型不用工具。
   已备好的通路（`ChatMessage.tool_calls` / `tool_call_id` / `tool_result()`）留着，
   将来真要切"纯标准协议"时不用再动结构。

## 5. 边界与未做

- **只覆盖 `/chat/completions`**：`/responses`（`function_call` 项）与 anthropic（`tool_use`
  块）的工具形态各是一套，本次不映射 —— 那两条路保持老协议，与改造前逐字一致
  （`extract_responses` / `extract_anthropic` 里都写了这句）。
- **历史链仍是自家格式**（assistant 回显 + user 观察），不是 `role="tool"`；见 §2.4 的理由。
- **`final` 是工具，但不是"第五种能力"**：它是收尾（老协议里是 `final` 字段）；控制动作
  （`plan` / `ask_user` / `final`）依旧不许进批。
- **老协议不再执行，但仍要"认得出"**：`tool_protocol=false` 时才执行 content 里的动作。
  严格模式下它是**识别器 + 纠正器**（`content_channel_error`）：认出形状（`parse_one` →
  参数形状 → 再往里一层）→ 点名 → 拒。为什么留识别：只回"无法解析"模型会换包装重发，见 §6。

## 6. 严格化修订（2026-09-24，同一版本内）—— 用户批"按 C 改，要标准化"

### 6.1 触发它的真现场（cloud-shop 启动前后端，18 轮）

第 12 轮还走工具协议，**第 13–17 轮连烧五轮**，全部是同一个 final 答复换包装：

| 轮 | content 形状 | 当时引擎的判定 |
| --- | --- | --- |
| 13 | `{"answer": "前后端都已启动…"}` | 外层缺 `tool` |
| 14 | `{"tool":"final","args":{"answer":…}}` | 未知能力 "final" |
| 15 | 同 14 | 未知能力 "final" |
| 16 | `{"name":"final","arguments":{"answer":…}}` | 外层缺 `tool` |
| 17 | 同 14 | 未知能力 "final" |
| 18 | **真工具调用** `final({answer})` | ✓ 交付 |

**两个成因，都是上一版改造自己留下的**：

1. **兼容层没跟上新词汇**：`final` 在新协议里是**工具名**、参数键叫 `arguments`，而 `parse_one`
   只认老词汇（`final` 是字段、只认 `args`）—— 模型恰恰因为**学会了新词汇**才被拒。
2. **失败反馈在教相反的东西**：每轮只回"请重新只输出一个 JSON 对象"，等于把模型**按回**它
   已经在用的通道；而系统提示词要求"用工具调用、别写进 content"。两条提示打架 → 五轮空转。

（另：同一份日志里 6 个带模型自带标记的响应块，4 个是改造前的旧账、**2 个都是 reflect**；
agent 主循环当天 **0 次泄露** —— 工具协议对主循环是有效的。）

### 6.2 改了什么

- **A｜词汇对齐**：`parse_one` 认 `final` 作能力名、`args | arguments`、`name | tool`、
  裸 `{"answer": …}`（四种能力里只有 final 认这个键，无歧义）。
- **C｜严格闸门**（`llm.tool_protocol`，默认开）：content 里的动作**一律不执行**；拒绝时
  **先认出来再拒**（`content_channel_error`）：
  - 认三层：按动作解析 → 按**参数形状**（`cmd/op/handle`→execute、`path+content/edits`→write、
    `path`→read、`steps`→plan、`question`→ask_user、`action/server/agent`→connect）→ 再往里
    一层（`{"arguments":{…}}`）；
  - 第 1 次讲清道理（"形状是对的，通道错了"），第 2 次起只说短话（`content_strikes`）；
  - 认清形状**只用于把话说清，永不用于执行** —— 参数形状在四种能力的协议内是唯一解，但
    "替模型决定做什么"这件事仍然不干。
- **反馈口径**：`parse_failure_feedback(.., tools = true)` 不再说"请重新只输出一个 JSON 对象"，
  改成"请改用工具调用表达动作"。
- **提示词**：规则 1 改成"**严格只认工具调用**；写进 content 一律不执行（会被退回重发一轮）"。
- **测试**：`testllm::fake_llm` 把老形状的剧本**翻译成工具调用**再发（上百条既有脚本一行不用改，
  验的仍是主路）；要"就发这个 content"用 `fake_llm_raw`。新增三条：严格拒（用另一个文件名核对
  落盘事实）、§6.1 那五个真实形状逐一被点名、回滚开关恢复 content 通道；`parse_failure_feedback`
  的严格/宽松两套口径另有断言。

### 6.3 判据

引擎 **342 passed + 8 ignored**（宿主 121 + 3）、clippy **0**、fmt 干净、check-style PASS、
ui-smoke **273/273**。

### 6.4 复核员那一路也修了（B 方向，2026-09-24 同日）

**原来漏在哪**：reflect 是"单发一次拿 JSON"的调用，按 §2.3 不给它声明 tools，而它的活儿
恰恰是**去 read 核对证据** → 原生调用无处可去，就写进 content：两次真跑各漏一次
（content = `{"path": "…vite.config.js"}` + 三行闭包标记 → 复核解析失败 → `结论：unknown`
（0 条 findings），等于把质检环节废掉）。

**修法**：`chat` 拆出 `chat_with_tools(...)` —— **声明面就是权限面**，工具由调用方点名，
复核员**只给 `read`**（给它 write/execute 等于把只读约束交给模型自觉；`tool_decls_for()` 按
名字过滤，`TOOL_NAMES_ALL` 与 `TOOL_DECLS` 的对齐由契约单测钉住）。循环里 `read` 优先走
**工具调用**（`read_via_tool_calls`：读得到就回灌、别的工具打回、参数不全报清楚），
content 形态保留作兼容 —— 复核是只读辅助环节，降级代价高（结论会变 unknown），
所以两条都收，但话术改成先教工具调用。

**真机复验**（`tools_protocol_probe` 场景 2，只声明 `read`）：

```
finish_reason: Some("tool_calls")
tool_calls   : 2
  · read({"path": "cloud-shop-admin-web/vite.config.js"})
  · read({"path": "cloud-shop-admin-web"})
content      : 0 字符
```

正是过去漏成 `{"path": …} + 标记` 的那一次读文件意图，现在走标准通道、**零泄露**。

**附带发现**（写在这里免得下次再撞）：`response_format=json_object` 要求**提示词里出现
"json" 这个词**，否则服务端直接 400（`Prompt must contain the word 'json'…`）。
真跑里的提示词天然带着（`请只输出一个 JSON 结论` / 规则里的"JSON"），手写探针时容易漏。

判据：引擎 **343 passed + 8 ignored**（宿主 121 + 3）、clippy **0**、fmt 干净、check-style PASS、
ui-smoke **273/273**；新增 `tool_call_read_reads_and_refuses_other_tools` 与
`tools_cover_every_parser_capability` 的子集断言。

## 7. 回显格式的坑（2026-09-24 修复）—— 我们自己教会了模型一种「能发」的形状

**用户新会话第 6 轮的原样证据**（`~/.ruyix/code/debug.log`）：

```
finish_reason: Some("stop")   tool_calls: 0   content: 219 字符
{"tool_calls":[{"arguments":"{\"path\": \"cloud-shop-authority/…/RoleController.java\"}","name":"read"}, …]}
[warn] [agent] 第 6 轮输出无法解析：content 里没有可执行的工具调用。…
```

模型的**意图和参数都对**，只是发在了 content 通道：`finish_reason=stop` 说明服务端把它当**纯文本**
收下的，所以 `tool_calls` 是空的。

**病因在我们的回显**：工具轮的 content 天生是空的，引擎为了让模型看得见自己刚发过什么，把它的
调用写回历史 —— 而旧实现写的是 `{"tool_calls":[{"name":…,"arguments":…}]}` 这个 **JSON 信封**。
一个反复出现在历史里、「看起来能发」的 JSON，模型就学着用它发。真跑里 2/73 轮被它带偏
（当时我把它记为"新失败模式、约 3%"；新会话又中一次 ⇒ 它不是偶发，是我们教出来的）。

**修法（三处）**：

1. `tool_calls_echo` 改成**流水文字**：`〔已发出调用〕read(path="…")；execute(cmd="…")`
   —— 一眼看得出是"引擎记的账"，没有可复制的信封（抄了也只是散文，不执行）；
2. 系统提示词规则 1 补一句：历史里 `〔已发出调用〕…` 是引擎的流水**记录**，不是发送格式；
3. 严格闸门的纠正话术新增**专用一条**：认出"抄了流水"这种形状（content 顶层带 `tool_calls` 键）
   就点名说"那是引擎记的账，不是发送格式；发送动作只有一条路：直接用工具调用" ——
   且**不把那个信封抄回去**（引用等于又教一遍）。

**判据**：引擎 **351 passed + 8 ignored**（新增 `a_copied_record_is_refused_and_named_without_quoting_it`；
另在 `tool_calls_round_runs_and_the_model_sees_its_own_call` 里钉住回显形状：必须含
`〔已发出调用〕`、必须**不含** `"tool_calls"`）；宿主 121 + 3、clippy 0、fmt 干净、check-style PASS、
ui-smoke 273/273。

**未证的一点（诚实留档）**：换形之后模型是否还会偶尔抄回显 —— 基线约 3%，小样本 A/B 分辨不了。
判据是**下一次真跑**：debug.log 里若再出现"content 顶层带 `tool_calls` 键"被拒的回合，说明这条路
还没堵严（那时应当**不再回显任何形状**，只把上一次的调用并进观察消息里）。

**这条判据已兑现（2026-09-24）**：用户自测一轮会话，从 `~/.ruyix/code/debug.log` 独立复核 ——
该会话 **6 轮全走标准协议、被拒回合 0 次、7 轮完成**（对照：同一类任务此前 73 轮 / 6 次全停全起，
以及修复前那次新会话第 6 轮就翻车）。判据没有被触发 ⇒ 回显换形在真机上成立。

## 8. 子 agent 的声明面（2026-09-24 修复）—— 声明七个、能执行四个

**用户报**：*"子agent没有严格的工具协议定义。"*

### 8.1 病：`STEP_SYSTEM` 里那句话是假的

`step_agent.rs` 的提示词写着：

> **动作一律用工具调用表达**（引擎已声明 read / write / execute / final 四个工具，参数见工具声明）。

而请求走的是 `llm::chat(..., true, cfg.llm.tool_protocol)` —— `tools=true` 时 `chat` 声明的是
`TOOL_NAMES_ALL`（**全七个**：read / write / execute / **connect / plan / ask_user** / final）。
模型于是能从 `tools` 字段里看到那三个**它执行不了**的工具；一调用，`to_step_action` 把它变成
`StepAction::Unsupported`，回一句 `plan（本步不支持）` —— **白烧一轮**，而且与提示词自相矛盾。
（`llm.rs` 里 `tool_decls_for` 的文档早就写着"步骤执行体没有 connect"，代码却仍然声明了它。）

**顺带普查**（`grep -rn "llm::chat\|chat_with_tools" src/`）：主循环声明全七个 ✓（它真能执行七个）、
`reflect` 只声明 `read` ✓、旧管线四阶段（plan/generate/repair/eval）一律 `false`（不声明，走 content）✓
—— **只有子 agent 这一处是错的**。

### 8.2 改法：单一真相 + 声明面 = 权限面

- `agent.rs` 新增 `STEP_TOOL_NAMES = ["read","write","execute","final"]`（紧挨 `STEP_TOOLS_HINT`，
  单一真相是 `to_step_action` 的那四支）；
- `step_agent.rs` 改用 `llm::chat_with_tools(..., step_tools)`：协议开着 → 只声明那四个；
  关掉 → 空切片（请求里不发 `tools` 字段，走 content 通道）。

### 8.3 判据

- `a_step_declares_only_the_tools_it_can_execute`：**直接解析请求体**的
  `tools[].function.name`，断言恰好是那四个、且不含 connect/plan/ask_user ——
  请求体才是服务端看到的东西，断言它才有意义；
- `step_tool_names_match_the_hint_and_exclude_parent_only_ones`：`STEP_TOOL_NAMES` 必须与

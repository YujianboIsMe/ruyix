# 需求：编辑器超长行的水平方向按需渲染（v0.13）

**归属版本**：v0.13
**报单人**：用户（真机）
**现象**：用 ruyix 打开 `ui/xterm.js`，**编辑器直接崩溃**。用户判断：*"因为这个文件特别大，而且只有一行"*。
**诉求**：能不能实现【水平方向按需渲染】？

---

## 一、现象与量级（先把"大"这个模糊词换成数字）

| 文件 | 字节 | 行数 | 最长行（字符） | 该行估算像素宽 | 近似 token 数 |
|---|---|---|---|---|---|
| **`ui/xterm.js`** | 283,404 | **2** | **283,184** | **2,208,835 px** | **104,747** |
| `crates/harness-engine/src/agent.rs` | 162,394 | 3,586 | 295 | 2,301 px | 50,285 |
| `ui/main.js` | 134,214 | 3,809 | 156 | 1,217 px | 41,634 |

> 像素宽按等宽字体 13px（`styles.css` 的 `.editor-textarea` / `.editor-code-backdrop`）估 7.8px/列。

**结论一句**：变量不是"文件大小"，是**最长行的长度**。xterm.js 只比 agent.rs 大 1.7 倍，
但它的最长行是 **960 倍**（2,208,835px vs 2,301px）—— agent.rs 那种"200KB、3586 行"的文件
编辑器打开毫无问题，问题全在那**一行**上。

而且现有虚拟化**救不了**：`paintEditorWindow` 是**纵向**虚拟化（只画可视行 + overscan），
而 xterm.js 整个文件就是一行 —— 那一行永远是"可见行"，于是它必然被整行渲染。

## 二、崩溃的四个放大器（都在现有代码里，各有行锚）

按我预计的量级排序（**第 0 步就是把这个排序测准，见 §四**）：

| # | 放大器 | 代码位置 | 为什么致命 |
|---|---|---|---|
| 1 | **背板一次 `innerHTML` 塞进几万个 `<span>`** | `ui/main.js` `editorLineHtml`（808）/ `paintEditorWindow`（867-873） | 那一行约 10 万 token，`editorLineHtml` 为它拼一个 ~283KB+ 的 HTML 串，`backdrop.innerHTML` 一次性解析。纵向虚拟化对"一行"无能为力 |
| 2 | **两个各含 2.2M px 内容宽的文本元素**：textarea 自己 + 背板那条 `.code-line` | `setEditorContent`（`main.js` 1069-1076）/ `styles.css` 1020-1035 | `.editor-textarea{width:100%}` + `white-space:pre` + `wrap=off` ⇒ textarea 装着 283k 字符的**单行**，它内部 `scrollWidth` 到 2.2e6 px（`.editor-view` 的横滚区因此也是 2.2e6）；背板那条 28 万字符的 `.code-line` 同样宽度。**订正（2026-09-24，探针实测）**：本文档第一版说"容器 `min-width` = 2.2M px"，**判错了** —— `keeper` 只在"行数超出窗口"时才渲染（2 行的文件不虚拟化 ⇒ 没有宽度占位），容器其实= 视口宽，是**里面这两个元素各自在撑宽**。修法不变，但病根的描述必须准确 |
| 3 | 宽度占位（keeper）与强制量宽 —— **本例其实不成立** | `setEditorContent`（`keeper: texts.length > rows ? editorWidestText(texts) : ""`）/ `syncCodeWidth`（936-973） | 订正：2 行的文件**不**虚拟化 ⇒ 不渲染 `.editor-virt-keeper`，`syncCodeWidth` 直接清 `min-width` 返回。它仍是一条真实隐患（"行数 > 窗口"且含超长行的文件才踩：那时 keeper 会把 2.2e6 px 的宽度钉进容器，并对它做一次 `Range` 强制同步布局）。这里留着是为了说明**同一类病在不同触发条件下从不同入口进来** |
| 4 | **`highlight_code` 整份 IPC** | `ui/main.js` 1010-1017；`src-tauri/src/main.rs` 605-629 | 283KB 源码送 tree-sitter，回的是那一行约 10 万 token 对应的扁平三元组（粗估 ~1MB JSON）；`read_file`（`main.rs` 287-303）**没有任何大小闸** |

> **落到 xterm.js 这个文件上，成立的是 1、2、4**（3 不成立，见上）。
> 也就是说：**背板的整行**与**textarea 的整行**是两处独立的炸弹，只掐一处，另一处照样崩 ——
> 这正是修法必须同时做"切段"与"textarea 退出布局"两件事的原因（实测：只切段不撤 textarea，
> 或只撤 textarea 不切段，都不成立）。

**顺带发现的第五个（不是崩溃元凶，但会让"改完仍然卡"）**：
`setupTextareaSync` 的输入路径 `if (newContent.split("\n").length <= 1000) renderPlainCode(tab)`
（`main.js` 1869-1871）—— xterm.js 是 **1 行**，于是**每敲一个键都全量重绘**（283k 字扫描 +
`Range` 量宽 + 十万级 span 重排 + 重新送高亮）。这个必须和主方案一起处理。

## 三、现有设计的四条硬约束（方案不能违反，否则踩回旧坑）

- **C1**：`textarea.value === tab.content`（ui-smoke U31 钉住，`doc/editor.md` §载荷形状）——
  textarea 必须持有**全文**，且是**唯一输入面**（光标/选区/IME/撤销全赖它）。
- **C2**：backdrop 绝对定位 + textarea 显式高度（P0/P2 的性能成果：25000 行重绘 110ms → 1.4ms，U31 钉住）。
- **C3**：容器宽 = 最宽行宽（`doc/editor.md` §宽度不变量）—— 破了就"双滚动条 + 光标与字形错开"。
  **注意**：这条正是本需求要**开一个口子**的地方（超长行不允许等于内容宽）。
- **C4**：三个渲染入口（高亮 / 纯文本 / 终端输出）都必须走 `setEditorContent`（`doc/editor.md` 末尾）。

C1 与"水平按需渲染"天然冲突：**只要 textarea 里放着那 283k 字符的单行，浏览器就得为它整形**，
而整形正是放大器 2/3 的根源之一。方案的分野全部落在这句话上。

## 四、第 0 步：先测量，再动手（预注册）

**不先测就改，等于在四个放大器里赌一个。** 四个放大器各自对应**不同**的修法：
- 若元凶是 ①②③（页面元素宽度 / span 数 / keeper）→ **方案 B 能救，超长行仍可编辑**；
- 若元凶是"textarea 单行 283k 字形的整形"→ **B 救不了**，只能走"只读分块视图"（方案 A）或自绘光标（方案 C）。

**测量载体**：新脚本 `scripts/editor-huge-line.js`，沿用 `scripts/editor-layout.js` 的骨架
（真实 `ui/index.html` 剥 script/link + 真 `styles.css` + 真 `main.js` 剥引导块 + 无头 Edge + CDP）。
**不改 `editor-layout.js` 的现有判据**（它对正常文件仍要求"容器宽 ≫ 视口"），新脚本单独一条。

**喂什么**：1 行 283,184 字符的合成内容（形状与 xterm.js 同量级，不真读那个文件 —— 探针要可复现）。

**量什么**（每条都打印原始值，不看结论只看数）：
1. `container.style.minWidth` / 实际 `offsetWidth`；
2. `keeper` 的 `Range.getBoundingClientRect().width` **与这次量宽的耗时**；
3. `#editor-code-backdrop` 子树里的元素数与文本节点字节数（`querySelectorAll("*").length`）；
4. `setEditorContent` 调用到首帧画完的**墙钟耗时**；
5. `textarea.scrollWidth / clientWidth`；
6. 渲染进程是否还活着（CDP 断连 = 崩；探针要能区分"超时"与"断连"）。

**预注册判据（现在就写死，免得事后解释）**：
- **现在这版**应当在上述 1-5 里至少有一项**数量级异常**（预计：① 元素数 ≥ 1 万，或 ② 宽 ≥ 2.0e6，
  或 ④ 首绘 ≥ 5s / 超时 / 渲染进程断连）；
- **哪一项先爆，就认定它是元凶**，并据此选方案（§五的分段）；
- 若四项都"正常"（首绘 < 500ms、元素数 < 2000、宽 < 1e5）而真机上仍然崩 → 说明元凶在
  **Rust/IPC 侧**（放大器 4），改测 `highlight_code`（见下）。

**Rust 侧同时测**（一条 ignored 测试或 example 打印，不联网）：`highlight_code`
对 283KB 单行 JS 的**耗时**、返回的 `tags` 长度、那一行的三元组个数、`serde_json` 序列化后的**字节数**。

## 五、候选方案

### 方案 A：超长行分级降级 → 只读分块视图（**推荐先做，与测量结果无关**）

- **触发**：任一行的视觉列数 > `EDITOR_WIDE_LINE_MAX_COLS`（候选 **2000 列 ≈ 15.6k px**）。
- **行为**：
  1. 该标签页进入**只读分块视图**：超长行按 `EDITOR_SEG_COLS`（候选 **200 列 ≈ 1.56k px**）
     切成 display row；行模型从"逻辑行"换成"**显示行**"，`paintEditorWindow` 的窗口数学
     （spacer 之和 = 显示行数 × 行高）**原样复用**；
  2. **textarea 退出渲染**（不参与布局；不是"藏起来但仍布局"）——只读态没有光标映射问题；
  3. 容器宽度上限 = `SEG_COLS × charW + padding`（≈1.6k px），**永不出现 2.2M px**；
  4. 顶部横幅：`该文件单行 283,184 字符（约 2.2e6 px），已切换为分块只读视图` +
     【用系统程序打开】【复制全部内容】；
  5. 超阈值文件**不进 tree-sitter**（纯文本单色），省掉放大器 1/4。
- **好处**：一次性消掉四个放大器；不碰 C1/C2（只读态不适用）；实现量小（复用现有虚拟化）。
- **代价（诚实说）**：① 不能编辑（要编辑就外部打开）；② 视图把一行折成多行，
  **框选复制会带上折行换行** → 所以给"复制全部"按钮（走 `navigator.clipboard.writeText(tab.content)`）；
  ③ 需要新的"显示行"行模型（`editorModel` 里多一层 `displayOf(logical)` 映射）。
- **判据**（预注册）：打开 283KB 单行文件后 —— 首绘 < 300ms；`container.minWidth ≤ 2000px`；
  背板元素数 ≤ 5000；渲染进程存活；滚动到底部不卡；**显示内容 = `tab.content` 按
  `SEG_COLS` 切片的逐段等值**（不是"看起来像"，是逐段字符串比对）。

> **已实施（2026-09-24，用户批复"先做这个"）**。落地的形状与上面 §五 的方案 A 一致，只有两处
> 按实测改了：**段宽不写死**（= `min(200 列, 视口 − 行号列 − padding)`，写死 200 列在 560px 视口下
> 会撑出 1587px 的横向滚动区），以及 `lineOf` 用**完整映射**（第一版只存"要不要编号"，
> 于是显示段拼不回原文 —— 被探针当场抓住）。
>
> - 主代码：`ui/main.js`（`EDITOR_WIDE_MAX_COLS` / `isWideText` / `splitWideLine` / `wideRowsOf` /
>   `editorSegCols` / `recutWideModel` / `setEditorContent` 的 wide 分支 / `paintEditorWindow` 的行号推导）、
>   `ui/index.html`（`#editor-flow-spacer`）、`ui/styles.css`（`.editor-flow-spacer` /
>   `.code-line.editor-warn-row`）、`ui/command.js`（打开路径先打标记，图标一次画对）；
> - 门禁：`scripts/editor-wide-line.js`（真浏览器四臂：2000 不触发 / 2001 触发 / 283,184 列的全部判据 /
>   视口变窄重切段 ＋ **反向验证**：把阈值调大后旧病征必须复现）→ ui-smoke **U47** 转调它。
>   ui-smoke **311/311**；
> - 实测（探针，560px 视口）：283,184 列 → 显示行 4,570、每段 62 列、背板节点 **74**、
>   无横向滚动条、可滚到底、拼回原文逐行相等；
> - 用户要求的界面形状：**顶部虚拟行**写【行太宽，触发只读限制】、**不进行号**（gutter 第一格空、
>   内容首行仍是 1）、标签图标换 **🔒**；
> - 未做（仍在 §六 的待办里）：方案 B（可编辑的横向窗口）、`read_file` 的整体大小闸、
>   `setupTextareaSync` 那条"1 行文件每次按键全量重绘"的闸。

### 方案 B：保留可编辑，只挂横向窗口（"真·水平按需渲染"）

- **保留** textarea 持全文（C1 不破），但：
  1. 容器 `min-width` 改成 **min(内容宽, `EDITOR_WINDOW_MAX_PX`)**（候选 3 × 视口宽）；
  2. 允许 textarea 内部横滚（**废止** C3 在超宽行上的那一半），并把
     **backdrop 的横向偏移跟随 `textarea.scrollLeft`**（`backdrop.style.transform = translateX(-scrollLeft)`），
     于是"字在这儿、光标在那儿"不再发生 —— 这是 C3 那条不变量当初要解决的两个病之一，另一个
     （双滚动条）用"backdrop 跟随"同样化解；
  3. 背板**只渲染横向窗口**：可见行的每个片段按 `colStart × charW` 错位摆放，窗口外不建节点。
- **好处**：超长行**仍可编辑**，编辑语义完全不变（native caret/selection/undo 全留）；纯渲染层改动。
- **代价**：textarea 的 `scrollWidth` 仍是真实的 2.2M px（**整形成本还在**）—— 所以
  **能不能救取决于第 0 步的结论**；另外"backdrop 跟随"是一个新的同步路径（滚动路径上多一次 transform，
  要按 rAF 节流，别碰宽度）。
- **判据**：A 的全部判据（除"只读"）+ 编辑仍可用（打字 → 自动保存 → 重开文件内容正确）+
  光标与字形对齐（探针量：把光标放到第 N 列，`backdrop` 该列的 `getBoundingClientRect().left`
  与 textarea 的 `scrollLeft` 换算值之差 ≤ 1px）+ **滚动重绘耗时不得回归**（现基线 1.9ms）。

### 方案 C：把输入面也窗口化（自绘光标）—— **建议本轮不做**

textarea 只持可见窗口片段，输入/选区/IME/撤销全部自己映射回全局偏移。
等于自己写一个编辑器内核（跨段选择、IME 组合、查找替换都要接管），与 C1 的 native 路线决裂。
**只有在第 0 步证明"元凶是 textarea 整行整形"且用户不接受只读视图时，才谈这条。**

### 顺带修（无论选哪个方案）

- `setupTextareaSync` 的打字重绘闸从"行数 ≤ 1000"改成**行数与总字符数双闸**
  （xterm.js 是 1 行，现行闸门放行 → 每次按键全量重绘）；
- `read_file` 加**整体大小闸**（如 > 8MB 不整份读入，或走流式/只读快速视图），
  顺手解决"无上限读入"这个更大的隐患（本单只是 283KB 就崩了）。

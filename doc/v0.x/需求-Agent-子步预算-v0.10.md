# 需求：子步骤轮次预算 24 → 96（顺带挖出"落盘弄丢助手回复"的真凶）
## 归属版本：v0.10 · 状态：**已实施**（2026-09-21）· 提出：2026-09-21

> 用户原话（附 OUTLINE 截图：`Task plan · ✅ 5/6 · ❌ 1`，失败的是第 2 步「写飞机大战页面」）：
> *"看这里，这是一个失败的过程。我觉得原因在于子步骤24步太小，也改成96步吧。这样就不会失败了。"*

## 1. 结论先行：值改了，但**归因没能证实**（先说清楚，免得把猜测当结论）

用户给的是一条**推断**（"24 太小 → 所以失败"）。我按这条推断去找证据，结果**取不到那一步的失败原因**：

| 我查的地方 | 结果 |
| --- | --- |
| `~/.ruyix/code/agent/runs/agent-20260921-200052/` | **不存在** —— 会话跑的是工具循环，本来就不落 RunRecord（v0.4 起的既定纪律） |
| 该 run 的 `trace/logs.jsonl` | **不存在** —— `observe::log` 要有 run 上下文，对话轮没有 |
| 会话文件 `sess_2026-09-21T1733068908168000800.json` | **这一轮的助手回复压根没落盘**：盘上只有 `user(19:47:14)` → `system(20:13:18) 「✅ written 30 files」` |

❌ 的理由（`PlanStepState.note`，UI 里是 tooltip）只活在内存里，**重启即失** ——
所以"24 用尽"这句话既无法证实，也无法否定。

⇒ 本次改动的依据**不含"这次失败的原因"**，而是下面 §2 那两条独立事实。
⇒ "改成 96 就不会失败了"这句我**不能认领**：它只拆掉"预算用尽"这一种死法，其它死法（模型返回空 /
墙钟超时 / 取消）照旧。要证实，需要 ❌ 的 tooltip 原文，或同任务在 96 下重跑对照（见 §5）。

## 2. 改动依据（与那次失败无关，独立成立）

1. **子预算比父预算更紧，只会白烧父预算。** 主循环 `MAX_STEPS = 96` 记的是"步/干预轮"，
   子步按自己的 `step.max_steps` 记账。子步先耗尽时的处理是**停下、交给模型一个干预轮**
   （重规划 / 自己修 / 交付并说明），可**步骤没做完这个事实不变** —— 换来的是父预算多烧一轮，
   最坏还会触发 `MAX_PLAN_RESETS` 重规划。**同样的 24 换 96 在这一层已经发生过一次**：
   2026-09-19 的三次 run 全部在 24 轮上限处停下（三份会话的收尾文案就是
   `（达到 24 轮上限，循环停止。已完成 22/23/24 次工具调用 …）`），09-20 的 run 已经是
   `（达到 96 轮上限 …）` —— 父预算当时就是为同一类"轮数不够"提上去的。这次是把子预算对齐。
2. **子步写的是整文件，且没有外科手术式 `edit`。** 引擎的 Write 就是交出全文，所以一个
   "改页面"的步骤光前期 `read` 就可能要 3~4 个文件（现有页面 / 路由 / 样式 / 入口），
   再叠加写完触发窄层语法检查失败后的重写 —— 24 轮在"本步还没交付"时用尽是**设计上可预期**的。

## 3. 放开之后靠什么兜底（代价说清楚）

轮数是**软**上界，真正收口的是 `ruyix.code.harness.agent.max_elapsed_secs`（默认 1800s）那道
**墙钟**闸 —— 主循环与子步骤都看它。所以代价是：一个真卡住的步骤现在会多烧最多 4 倍轮次
（token 与时间），但不会无限跑。觉得吵就把它调回小值或调小墙钟，两个键都在配置里。

## 4. 顺带挖到的真 bug：`persist()` 把助手回复抹掉了（已修）

查 §1 那张表时发现的：**这不是"24 是元凶"的证据，而是一个独立的落盘缺陷。**

```js
// ui/session.js · persist()（改前）
const saved = await invoke("agent_session_save", { sessionJson: JSON.stringify(s), … });
Object.assign(s, saved);            // ← 元凶
```

后端回显的是**请求发出那一刻**的快照。`Object.assign` 把 `messages` 一起盖回来，
于是"发请求之后才 push 的消息"（**正在跑的助手气泡**）被从 `s.messages` 里抹掉：
`placeholder` 变成游离对象，`placeholder.text = rep.answer` 与 `placeholder.plan = 快照`
全写在游离对象上 —— 盘上只剩 [用户任务, 写回回执]，**计划快照一起消失**，
重启后大纲区的 ❌ 与失败原因就再也回看不了。（当场看着还是好的：大纲渲染的是 `s._plan`，
它挂在会话对象上、不跟着消息走 —— 这正是"看着没丢、其实没存"的那类最难发现的不一致。）

修法两条（都在前端，改的是**事实源归属**）：

- 回显**只同步元数据**（`id` / `title` / `created_at` / `updated_at`），绝不整体 assign；
  会话内容的唯一事实源是内存里那份 `s`，后端只是持久化通道。
- 每处落盘都 `await`：同一会话两次落盘共用同一个 `<id>.json.tmp`，并发时必有一次 `rename`
  失败（用户看到"会话保存失败"，而盘上留下的是旧内容）。

契约：`scripts/ui-smoke.js` **U29 persist-no-clobber**（两条）钉住"回显不许整体 assign"与"落盘必须 await"。

> 仍**未定论**（记在这里，别当已解决）：这一条的触发时序我没能复现 ——
> 需要"首次落盘的回显在 `push(placeholder)` 之后才返回"这个窗口，本次没法证明它真的发生了。
> 代码层的事实成立（回显必然晚于请求，晚到就必然抹消息），所以修它是对的；
> 但"19:47 那轮到底是不是这么丢的"仍是推断。另一条**未修**的残留：`.json.tmp` 名字固定，
> 跨进程同时写同一项目仍会撞（本机单实例，风险低，要修就是把临时名加唯一后缀）。

## 5. 判据（可证伪）

1. `cargo test`：`config_bridge` 两条断言子步默认 = 96（含"非法值回落默认"那条）；
2. `node scripts/ui-smoke.js`：U29 两条绿（含新编号进文件头清单）；
3. **归因核实**（还没做，需要用户配合）：同任务重跑，看第 2 步是否仍 ❌ ——
   若仍 ❌，日志里应出现 `96 轮内没有交付本步（预算用尽）` 才算"预算仍是瓶颈"；
   若 ❌ 的理由换成了别的东西，则 24 不是元凶，本条归因推翻。

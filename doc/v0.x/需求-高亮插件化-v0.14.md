# 需求：语法高亮的插件化（v0.14）

**归属版本**：v0.14
**提出人**：用户
**原话**：*"那么如何支持语法高亮扩展？硬编码肯定不行啊！如何插件化？想几个法子出来。"*

---

## 一、现状：硬编码在三处（改一门语言要动 4 个地方 + 重编译）

| # | 在哪 | 内容 | 加一门语言要做什么 |
|---|---|---|---|
| 1 | `src-tauri/Cargo.toml:26` | `arborium = { features = ["lang-python", "lang-rust", "lang-html", "lang-css", "lang-javascript", "lang-markdown", "lang-sql", "lang-java"] }` | **加 feature → 重编译**（arborium 家族可选 **112 门**，我们只开了 8 门） |
| 2 | `ui/main.js:1323` `extToLanguage()` | 12 个扩展名 → 语言名的 map | 改 JS |
| 3 | `ui/main.js:1342` `fileIcon()` | 扩展名 → 图标 | 改 JS |
| 4 | `src-tauri/src/main.rs:144` `TOK_TABLE` + `ui/styles.css` 的 `.tok-*` | **27 个 token 名的闭集**，两侧由契约测试钉住 | 想加新 token 名 → 改 Rust 枚举 + CSS + 测试 |

结论：**现在是"编译期插件"** —— 普通用户完全无法扩展，加一门语言等于发一个版本。

## 二、关键发现：缝已经留好了（这是本方案能便宜的前提）

四条都是实测读源码得到的（`~/.cargo/registry/.../arborium-2.18.2` 等，版本 2.18.2）：

1. **query 是纯文本**：`arborium-highlight-2.18.2/src/tree_sitter.rs:39-48`
   ```rust
   pub struct GrammarConfig<'a> {
       pub language: Language,          // 解析器
       pub highlights_query: &'a str,   // ← "什么算关键字"就是这份文本
       pub injections_query: &'a str,
       pub locals_query: &'a str,
   }
   ```
2. **第三方 grammar 有官方注册口**：`arborium/src/store.rs:18-77`
   > *Third-party grammars can be registered with `insert`. Registered grammars participate in the same
   > lookup path as built-ins, so `Highlighter::with_store` and related APIs pick them up automatically.*
   ```rust
   pub fn insert(&self, language: impl Into<String>, grammar: Arc<CompiledGrammar>) -> Option<Arc<CompiledGrammar>>
   ```
   配 `Highlighter::with_store(Arc<GrammarStore>)`（`highlighter.rs:113`）即可用。
3. **grammar 就是一个 C 符号**：`arborium-python-2.18.2/src/lib.rs:5-14`
   ```rust
   use tree_sitter_language::LanguageFn;
   unsafe extern "C" { fn tree_sitter_python() -> *const (); }
   pub const fn language() -> LanguageFn { unsafe { LanguageFn::from_raw(tree_sitter_python) } }
   pub const HIGHLIGHTS_QUERY: &str = include_str!("../queries/highlights.scm");
   ```
   ⇒ **任意能导出 `tree_sitter_<lang>` 的产物（含动态库）都能走完全同一条构造**。
4. **扩展名表已经自带**：`arborium::detect_language(path) -> Option<&'static str>`，`lib.rs:398`，112 门语言的表 —— 我们那份 `extToLanguage()` 是重复劳动。

> 一句话概括：**解析器（代码）与"什么算关键字"（文本）是分开的**。插件化的本质就是把这两样的**来源**变成可插拔 ——
> 而下游（载荷 `{tags, lines}`、UTF-16 偏移、前端渲染、虚拟化、4 条契约、U31）**一行都不用改**。

## 三、五个法子（按代价从低到高）

### 法子 1：把三处硬编码变成**注册表**（最小步，立刻消掉 JS 侧硬编码）
- 形态：`<ruyix 根>/global/highlight.toml` + 项目级 `<ruyix 根>/projects/<项目key>/highlight.toml`
  （**沿用 `capability.rs` 的现成惯例**：全局+项目、按名合并、项目覆盖全局）。
  ⚠️ 路径口径已随 v1.0.0 的便携形态改动：**根 = exe 同目录**，全局与项目两级都在根内，
  项目级按 key 分桶（见 `doc/需求-便携形态与零残留-v1.0.0.md` / `doc/架构-便携根与项目状态搬迁-v1.0.0.md`）；
  插件本体放 `<ruyix 根>/plugins/`（项目专属插件放 `<ruyix 根>/projects/<key>/plugins/`）——
  程序**不再往用户仓库里写任何东西**；
  ```toml
  [[lang]]
  id = "javascript"
  ext = ["js", "mjs", "cjs", "ts", "tsx"]   # 同语法多扩展名，零编译
  icon = "Ⓙ"
  ```
- 好处：`.ts/.tsx` 这类"同一门语法、新扩展名"**改配置就生效**；`fileIcon` 硬编码一并消掉；`extToLanguage` 的实现换成 `arborium::detect_language` 兜底 + 注册表覆盖。
- 不能解决：**arborium 没编译进来的语言**（那才是硬编码的真身）。
- 判据：加一条 `ext = ["tsx"]` 的注册，重开 ruyix（不重编译）→ `.tsx` 文件有颜色。

### 法子 2：**query 外置**（性价比最高：不重编译就能改/加高亮规则）
- 形态：插件目录放 `highlights.scm`，我们用它去构造 grammar：
  ```rust
  let q = std::fs::read_to_string("plugins/highlight/toml/highlights.scm")?;
  let g = CompiledGrammar::new(GrammarConfig {
      language: arborium::lang_toml::language().into(),  // 或动态库来的 Language
      highlights_query: &q, injections_query: "", locals_query: "",
  })?;
  store.insert("toml", Arc::new(g));                      // 官方支持
  ```
- 好处：**只要 grammar 在手，高亮规则本身就是可热插拔的数据** —— 改配色语义、给内嵌语言（HTML 里的 JS/CSS）加规则、修某门语言的高亮，全都不用重编译 ruyix。
- 代价：需要 `GrammarStore` 常驻 + query 编译缓存（`CompiledGrammar::new` 会编译 query，要按语言缓存，别每个文件编一次）；脱离 arborium 的"一体化"入口，自己持有 store。
- 判据：把某门语言的 `highlights.scm` 换一份（比如让所有函数名都不亮）→ 重启后生效、且**不重编译**。

### 法子 3：**多编几门进来**（体积换零运维）
- 形态：把 feature 表扩到"常用 20~30 门"（或按组：前端组/后端组/数据组），配法子 1 的注册表按需启用。
- 好处：零运行时开销、零 ABI 风险，`detect_language` 直接可用。
- 代价：**二进制体积与编译时间**（每门 grammar 是编译进去的 C 解析器）。需要先测：8 门 → 30 门的体积增量（未测，别拍脑袋）。
- 判据：先量体积再决定门槛（例：30 门 ≤ +8MB 可接受）。

### 法子 4：**动态 grammar（cdylib / `.dll`）** —— 真·任意语言，零重编译
- 形态：
  ```rust
  let lib = libloading::Library::new(p)?;                       // plugins/grammars/toml.dll
  let sym: Symbol<unsafe extern "C" fn() -> *const ()> = lib.get(b"tree_sitter_toml")?;
  let lf = unsafe { LanguageFn::from_raw(*sym) };               // 与内置 crate 同一条构造
  let g = CompiledGrammar::new(GrammarConfig { language: lf.into(), highlights_query: &q, .. })?;
  store.insert("toml", Arc::new(g));
  ```
  插件侧用脚本把 tree-sitter 语法编成 cdylib（**Neovim 的 nvim-treesitter 就是这么干的**：用户机器上编 `parser.so`）。
- 好处：**语言不再受 ruyix 的编译期约束**。
- 代价/风险：① 插件侧要有 C 工具链（或预编译产物）；② **ABI 版本**要校验（tree-sitter 的 `Language` 带版本，`set_language` 会失败 → 必须给出"这枚 dll 与内置 tree-sitter 不匹配"的明确报错，并降级为纯文本）；③ **信任边界**：加载第三方本机代码 = 等于给它进程权限，必须显式开启 + 留痕（照 `env install` 那条纪律：开关 + 一条 JSONL 记录 + 面板里可见）。
- 判据：装一个现在没有的语言（如 `toml`/`yaml` 的 dll）→ 打开文件有颜色；把 dll 删掉 → 优雅降级为纯文本 + 一行状态栏提示，**不崩**。

### 法子 5：**外部高亮服务 / MCP**（语言无限、进程隔离，无需 C 工具链）
- 形态：把"高亮"当成一个**连接**（与现有 Connect 原语同构）—— 宿主已有 MCP 客户端（`mcp.rs`，注册表 `mcp.toml`，能力面板可管），所以最便宜的做法是：**约定一个 `highlight` 工具**，把源码传进去、拿片段回来；实现侧可以是 shiki / pygments / highlight.js / 自写 tree-sitter，语言随它们。
- 好处：零编译、语言无上限、崩溃不带走 IDE；且**协议越小越好**：插件只要回**字节区间**的 span + capture 名，UTF-16 换算与载荷组装仍由我们做（`unit_table` 现成的）——插件作者不必理解我们的单位约定。
- 代价：常驻进程 + 每份文件一次序列化往返；离线可用性取决于插件自备依赖；大文件要定闸（比如 >2MB 才考虑用，不然 IPC 比本地解析慢）。
- 判据：挂一个 shiki 服务，喂 `.tsx` → 彩色；停掉服务 → 降级纯文本 + 提示。

### 法子 6：**TextMate 语法（`.tmLanguage.json`）**（备选通道，生态最大）
- 形态：纯 JSON + 正则，可热加载；Rust 侧用 `syntect`，或前端用 `vscode-textmate`。
- 好处：**全世界编辑器插件生态都在这个格式上**（VS Code 语言扩展几乎全是 TM 语法），拿来即用。
- 代价：等于维护**第二套高亮引擎**，且大文件/minified 单行表现明显不如 tree-sitter（正是我们刚处理过的那类文件）。
- 建议：只作为"插件语言专用通道"（内置语言继续走 tree-sitter），两条通道产出**同一个载荷**。

## 四、共同前提：把"片段来源"抽成一个接口（载荷契约不动）

不管选哪几个法子，落地形状都是同一句话 —— 现在 `highlight_code` 里直接 new 了 `arborium::Highlighter`
（`main.rs:611`），把它换成：

```rust
/// 高亮的唯一缝：给定语言与源码 → 产出**载荷**（就是现有 HighlightPayload）。
/// 实现一：内置 arborium（现状）；实现二：插件 grammar（法子 2/3/4）；
/// 实现三：外部服务（法子 5）；实现四：TextMate（法子 6）。
trait FragmentSource {
    fn fragments(&self, lang: &str, code: &str) -> Result<HighlightPayload, String>;
}
```

**为什么这不是空话**：载荷形状（`{tags, lines}`、扁平三元组、UTF-16 码元、行由前端切）已经被 4 条 Rust 契约 +
ui-smoke U31 钉死了 —— 那是**接口**，不是实现细节。所以插件只影响"片段从哪来"，前端渲染、虚拟化、
主题、门禁**全都不用动**。（顺带：`HighlightPayload` 与 `build_line_highlights` 可以原样复用，
插件只负责给 `&[(start, end, capture_name)]`。）

## 五、插件清单长什么样（草案）

```toml
# <ruyix 根>/global/highlight.toml（全局）
# 或 <ruyix 根>/projects/<项目key>/highlight.toml（项目级，覆盖全局同名）
# 根 = exe 同目录；见 doc/需求-便携形态与零残留-v1.0.0.md
[[lang]]
id = "toml"
ext = ["toml"]
icon = "⚙️"
grammar = "builtin"                    # builtin | dll:<path> | service:<mcp-server>
highlights = "plugins/highlight/toml/highlights.scm"   # 省略 = 用内置 query
token_map = { "property" = "property", "key" = "property" }  # capture → 我们的 token 名
css = "plugins/highlight/toml/theme.css"               # 只接受 .tok-* 规则（见 §六）
```

## 六、信任与安全（插件能干什么、不许干什么）

1. **CSS 只收 `.tok-*` 选择器**：注入的样式表逐条校验，非 `.tok-*` 规则一律丢弃并记录 ——
   否则插件能 `.tab-bar{display:none}` 把 IDE 藏了；
2. **token 名**：优先要求映射进现有 27 个闭集（这样 `every_tag_has_a_css_class` 那条契约不用改）；
   允许插件引入新名，但**必须自带对应 CSS**，且门禁要扩成"插件的每个新 token 名在它自己的 css 里有规则"；
3. **动态库 / 外部服务必须显式开启 + 留痕**：一条 JSONL（谁、哪个文件、何时加载、结果），面板里可见 ——
   照 `env install` 的现成做法；
4. **失败必须降级，不许白屏/崩**：任何插件加载/解析失败 → 该文件走纯文本单色 + 状态栏一行说明
   （现在的 `highlightAndRender` 已经有 `catch → renderPlainCode` 这条兜底，扩展点要复用它）；
5. **路径封闭**：插件目录之外的 `dll:` / `css:` 路径拒绝（与产物写回同一套纪律）。

## 七、推荐路线（阶段与判据）

| 阶段 | 做什么 | 判据（可证伪） |
|---|---|---|
| 1 | **法子 1 注册表** + 用 `detect_language` 替掉 `extToLanguage`；`fileIcon` 也走注册表 | 加 `ext=["tsx"]` → 重开即生效、不重编译 |
| 2 | **法子 2 query 外置**（先只对**已编译进来**的 8 门语言开放） | 替换一份 `highlights.scm` → 生效且不重编译 |
| 3 | 量体积后决定 **法子 3**（多编几门）或直接上 **法子 4**（dll） | 法子 3：体积门槛；法子 4：装一门 dll 语言成功 / 删掉优雅降级 |
| 4 | 需要"生态即战力"时再上 **法子 5（MCP 服务）** | 挂 shiki 服务喂 `.tsx` 有颜色；停服务降级不崩 |
| 5 | **法子 6 TextMate**：不做，除非明确要 VS Code 插件生态 |

## 八、待拍板点

1. **插件粒度**：是"一门语言一个文件"（`plugins/highlight/<id>/`）还是"一个 toml 全装下"？我倾向目录形态（scm/css/manifest 分开放，好共享）。
2. **信任级别**：要不要允许**动态库**（法子 4）？它是"能力最强 + 风险最高"的那个 —— 若你暂时不想在插件侧装 C 工具链，就先走法子 5（外部服务），把 dll 留到以后。
3. **token 名**：插件必须映射进 27 个闭集，还是允许新名 + 自带 CSS？（我倾向**允许新名但要求自带 CSS**，否则插件永远只能做"换肤"）
4. **体积预算**：法子 3 能接受多大的二进制增量？（决定"多编几门"和"上 dll"谁先来）
5. **门禁落点**：新判据放哪 —— 我建议 `cargo test -p ruyix`（后端契约：query 覆盖 / token_map / 路径封闭）+ ui-smoke 新条目（前端：加载一个假插件后彩色 / 插件坏掉时降级不崩）。

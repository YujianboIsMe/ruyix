# 需求：判据自相矛盾守卫（后台启动的 ready_cmd 闸门）
## 归属版本：v0.11 · 状态：**已实施**（2026-09-24）· 提出：2026-09-24（用户批"只改 A"）

> 用户原话：*"判据自相矛盾就当面拒……引擎只需从两串里抽数字，不需要任何 app 知识。这个不错。
> 先改这个。判据不一致空跑很多轮太伤了！只改A"*

## 1. 触发它的真现场（cloud-shop「启动前后端」，73 轮）

用户看到的是"33 轮、而且只启动了前端"——实际跑到 **73 轮**，动作分类（逐条数出来）：

| 类别 | 次数 |
|---|---|
| 侦察/验证（netstat / tasklist / curl / status） | **74** |
| 读文件 | 31 |
| **后台启动（含重复）** | **15** |
| **停止服务** | **8** |
| 写文件 | 2 |

**6 次完整"全停 → 全起"**（轮次 22 → 33-34 → 40-41 → 60-61 → 69），handle 一路 p2 排到 p12。
用户截图那一刻（11:17）后端刚被模型自己 `stop p4`（p4 是**已 ready** 的后端），只剩前端
（p5，npm pid 28000 on 5174）—— 这就是"只启动了前端"。

**引信是 ready_cmd 写错端口**（日志里的原始参数）：

```json
{"cmd": "mvn -f cloud-shop-admin/pom.xml spring-boot:run", "background": true,
 "ready_cmd": "netstat -ano | findstr \":5173\" | findstr \"LISTENING\"",
 "ready_timeout_secs": 1}
```

起的是后端（8083），判据却等 5173（前端端口）—— **判据永远命不中** → 引擎如实回
"⚠ 进程还活着，但就绪判据在窗口内没命中" → 模型不信 → 侦察几轮 → "全停重来" → 又带错判据……

## 2. 修法（A 的两条腿，都在 `proc.rs`，**零 app 知识**）

### A1｜判据与命令自相矛盾 → **当面拒**（`ready_port_conflict`）

`ports_in()` 从两串里抽端口（**只认强标记**：`:8083` / `127.0.0.1:5173` / `--port 5174` /
`PORT=8083`；**不认**裸数字，所以 `pom.xml`、`app-0.0.1-SNAPSHOT.jar`、`2026-09-24`、
`mysql:5.7` 都不会被误当成端口）。两侧**都抽到端口**且**完全不相交** → `start()` 在最前面就拒
（**不 spawn、不占 handle、不写日志**），并附证据：

```
❌ 这条命令没有执行：**就绪判据与启动命令自相矛盾**，它永远不会命中。
启动命令里的端口：18100
就绪判据里的端口：18999
两侧完全不相交 —— 这条判据等的是**别的服务**的端口，白等 5s 之后只会拿到"没就绪"，
然后你会以为服务没起来。
请二选一后重发：① 判据改成匹配本次启动的端口；② 命令改成监听判据里的端口（端口被占就先解决占用）。
```

**边界（都不拒）**：任一侧没抽出端口（`mvn spring-boot:run` 的端口在配置里，判据等 8083 完全
合法）；两侧有交集（多端口服务）。

### A2｜判据没命中时**把病因摆成证据**（`ready_miss_note`）

A1 抓不到"命令里本来就没有端口"那一类（**真跑 73 轮的正是这一类**），所以补第二条腿：
启动前后各取一次 `netstat -ano` 的 LISTENING 端口，没命中时给出**前后对比**，并分三种病因说话：

- **判据端口 ≠ 本次新增监听端口** → "**判据写错了端口**：判据在等 18999，而这次启动新在听的是
  18099 —— 服务其实起来了，只是不是判据等的那个端口。**不要重启**（重启还是同一条错判据）…"
  ← 真跑里模型就是缺这一句才去重启的；
- **判据端口确实在监听** → 是判据**写法**的问题（引号 / 大小写 / 匹配串格式）；
- **没有任何新端口** → 服务可能真没起来，或它本来就不监听端口（那就别用端口判据）。

"启动前在听的端口"**限长**（>16 个只报数量）：这段文字要进模型上下文，有用的是"新出现了什么"。

## 3. 真机可复现证明

`cargo run -q -p harness-engine --example proc_demo`（自当替身：`--serve --port 18100` /
`--serve 18099` 两种启动形态，不依赖 python / java / maven）：

```
--- ⑦ 判据与命令自相矛盾（应被拒，且不该起进程）---
❌ 这条命令没有执行：**就绪判据与启动命令自相矛盾**，它永远不会命中。
启动命令里的端口：18100
就绪判据里的端口：18999
…

--- ⑧ 判据没命中：给出「判据错在哪」的对比证据 ---
出口=NotReady（进程还活着 —— 不是启动失败）handle=p3
**判据为什么没命中**（本次启动前后对比了 LISTENING 端口，4.3s 窗口）：
启动前在听的端口：共 50 个（太长就不列了）
启动后新出现的端口：18099
→ **判据写错了端口**：判据在等 18999，而这次启动新在听的是 18099 —— 服务其实起来了，
  只是**不是**判据等的那个端口。**不要重启**…

--- ⑨ 阳性对照：同一条命令 + 正确的判据（应 Ready）---
handle=p4 pid=29724 等了 608ms
出口=Ready，证据：exit=0 TCP 0.0.0.0:18099 … LISTENING 37040
```

## 5. 边界（明确不做的）

- **不做"替模型决定"**：A1 只拒**纯机械矛盾**（两侧端口都不相交）；A2 只**描述**对比结果，
  不替模型改判据、不重启、不执行任何补救动作。
- **A1 抓不到"命令里没有端口"那一类**（故意：那是误伤区）—— 这一类交给 A2 的证据，
  或后续 B（同一条命令重复启动计数）、C（停掉 ready 的服务要留痕）。
- 端口抽取**只认强标记**：宁可漏（判据写错但形式不标准就放过），也不误伤一条合法命令。

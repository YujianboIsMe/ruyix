# 豁免（suppressions）

> 对应规则：`HX900`（豁免未说明理由）、`HX901`（豁免超预算）、`HX903`（豁免指向不存在的规则）

## 为什么豁免要有规则

Agent 面对 lint 有一个非常强的倾向：**让检查闭嘴，而不是把代码改对。**

```
最省力的路径：  报错 → 加 # noqa → 绿了
正确的路径：    报错 → 读懂为什么 → 改代码 → 绿了
```

如果放任前者，整套"自我纠正循环"会退化成"豁免生成器"：
违规数确实归零了，代码质量一点没变。所以豁免必须**带理由、可统计、有预算、可审计**。

## 写法

```python
# 1. 行内豁免（最常见）：必须带 reason
result = risky_call()  # noqa: HX201 reason=上游 SDK 在异常时返回 None 而不抛异常

# 2. 文件级豁免：整个文件关闭某条规则
# harnesslint: disable-file HX101 reason=由代码生成器产出，手改会被覆盖

# 3. 配置级豁免：整个项目关闭某条规则（写在 .harnesslint.toml）
# [lint] ignore = ["HX105"]
```

## 三条元规则

| 规则 | 触发条件 | 为什么要它 |
|---|---|---|
| `HX900` | 豁免没有 `reason=` | 无理由的豁免无法复核，规则升级后也没人知道它是否还成立 |
| `HX901` | 生效豁免数 > 预算（`--max-suppressions`） | **自我纠正循环的核心闸门**：预算设 0 时，"加 noqa 糊过去"这条路直接堵死 |
| `HX903` | 豁免里的规则 ID 不存在 | 拼错一个字符 = 你以为豁免了 X，其实什么都没豁免；也可能规则改名后留下死配置 |

## 工程实践

- **新代码库**：`--max-suppressions 0`，一条豁免都不给，逼着改代码
- **存量代码库**：先 `harness-lint --write-baseline` 写基线，之后只对**新增**违规负责
  （"存量豁免、增量严格"）。没有这一步，任何规则都上不了已有项目
- **评审时**：把"本次新增了几条豁免"当作 review 的必看项——豁免数是比违规数更灵敏的
  质量信号

## 与 `--baseline` 的分工

| 机制 | 管的范围 | 粒度 |
|---|---|---|
| `--baseline` | 存量违规 | 按规则计数（允许存量存在） |
| `noqa` + `HX901` | 新增豁免 | 逐条（每条都要理由） |

两者叠加才完整：基线让规则能落地，豁免预算防止落地之后被绕过。

## 两个容易踩的细节

**1. 豁免只在真正的注释里生效。** 写在字符串/文档字符串里的 `# noqa: HX101` 只是文本，
不会生效（早期版本的 linter 逐行找 `#`，结果文档里的示例会误伤，也能被用来偷偷关检查）。

**2. `# noqa` 是全生态共享的命名空间。** 所以：

```python
except Exception:  # noqa: BLE001 reason=上游 SDK 行为不可预测
```

`BLE001` 是 ruff/flake8 的规则 ID，本 linter **不会**判定它"不存在"——只有 `HX` 前缀
才归我们管。写自己工具的 code 时才需要严格校验（否则就是 HX903）。

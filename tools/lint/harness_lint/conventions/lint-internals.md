# linter 自身的故障（HX000 / HX998）

> 对应规则：`HX000`（文件无法读取或解析）、`HX998`（规则执行失败）

## 为什么这两条要单独存在

linter 最阴的失效方式不是"报错太多"，而是**悄悄地少检查**：

- 某个文件解析失败 → 被静默跳过 → 报告一片绿
- 某条规则抛异常 → 被静默吞掉 → 报告一片绿

两种情况都会给出"看起来健康"的结论，而实际上没有任何保护。
所以本 linter 把这两类情况都做成**显式诊断**：宁可报告难看，也不要假绿。

## HX000 文件无法读取或解析

```
HX000  error  语法错误，无法解析：expected ':'
```

语法错误由 Python 解析器给出，没有通用改法 —— 必须看具体报错。修掉之后 lint
才能继续检查其余规则（这也是为什么 lint 通常安排在验证阶段之前跑）。

## HX998 规则执行失败

```
HX998  error  规则 HX104 执行失败（这条不是代码问题，是 linter 自身的问题）
```

看到这条时：

1. **不要试图改被检查的代码来让它消失** —— 它不是你代码的问题
2. 把诊断里附带的 traceback 末尾几行交给 linter 维护者
3. 顺手给这条规则补一个反例测试（能复现异常的最小输入）

## 设计原则（写给想改 linter 的人）

- **规则异常必须外显**：`engine.py` 里对每条规则的调用都包了 try/except，
  捕获后转成 HX998，绝不允许 `pass` 掉
- **新增规则必须配反例测试**：只测"能报出来"是不够的，还要测"正常代码不报"。
  误报率才是这类工具的生命线
- **宁可漏报不误报**：判不准的时候选择不报（分层规则判不出层就不报、
  密钥规则宁可用保守阈值），因为一次误报就会让用户学会忽略所有报错

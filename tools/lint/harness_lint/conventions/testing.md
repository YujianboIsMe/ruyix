# 测试质量

> 对应规则：`HX103`（测试无断言）、`HX902`（测试数不得减少）

## 为什么盯着测试

Harness 的自我验证依赖"测试真的会失败"。一旦测试里没有断言，它就永远通过 ——
这时整套流程会给出一个**看起来很健康**的报告，而代码其实没有被保护。

这比"没有测试"更危险：没有测试时你知道自己没保护；有假测试时你以为有保护。

## 什么算断言

```
✅ assert add(2, 3) == 5                   # pytest 风格
✅ self.assertEqual(add(2, 3), 5)          # unittest 风格
✅ self.fail("不该走到这里")                # 显式失败
✅ with pytest.raises(ZeroDivisionError):  # 异常路径
       safe_div(1, 0)
✅ with self.assertRaises(ValueError):
       parse("")

❌ def test_add():
       add(2, 3)                            # 只是调用，没校验
❌ def test_add():
       pass                                 # 空桩
```

## 一个测试至少覆盖两件事

1. **正常路径**：典型输入 → 期望输出
2. **边界或异常路径**：空输入 / 单元素 / 越界 / 除零 / 非法类型 / 重复调用

只有正常路径的测试，等价于"确认代码在理想情况下能跑"，对回归几乎没有价值。

## 测试数不得减少（HX902）

`HX902` 拿当前测试用例数与基线对比，**下降就报错**。它挡的是这类"修复"：

```
- def test_parse_empty():        ← 删掉
-     assert parse("") == []
+ # 空输入暂时不支持，v2 再说        ← 用注释替代测试
```

合理的测试重构（把 3 个用例合并成 1 个参数化用例）会触发这条规则，此时需要人工确认，
再执行 `harness-lint --write-baseline` 重写基线。**这条规则的目的是让人看见变化，
不是禁止变化。**

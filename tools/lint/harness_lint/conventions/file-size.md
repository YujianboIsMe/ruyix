# 文件与函数大小

> 对应规则：`HX101`（文件行数）、`HX102`（函数行数）

## 为什么限制大小

不是为了"好看"，而是两个具体后果：

1. **一次读不完就只看局部。** 超过一定长度后，人和模型都会退化成"只读改的那几行"，
   于是局部改动的正确性依赖对没读到的部分的心智模型 —— 这正是 bug 的来源。
2. **爆炸半径随长度增长。** 同一文件里无关代码越多，一次修改误伤无关逻辑的概率越大。

## 阈值

| 规则 | 默认 | 配置项 |
|---|---|---|
| 文件行数 | 200 | `[lint] max_file_lines` |
| 函数行数 | 50 | `[lint] max_function_lines` |

阈值可以调，但**不要为了过检查而调高**：调高阈值等于把问题藏起来。要调就在
`.harnesslint.toml` 里写明原因，让后来人能看到"这里为什么放宽了"。

## 怎么拆

按**职责**拆，不是按行数拆。

```
✅ 正确的拆法
   parse.py      只做解析（输入字符串 → 数据结构）
   validate.py   只做校验（数据结构 → 错误列表）
   render.py     只做输出（数据结构 → 字符串）
   io_utils.py   只做读写（路径 → 内容）

❌ 形式主义拆分（规则没被满足，只是被绕过了）
   order.py          180 行
   order_part2.py    150 行   ← 还是同一坨逻辑，只是切成了两半
```

函数拆分的目标是**让名字能当注释用**：读一遍调用序列就知道这段在干什么，不必读实现。

典型切分点：

- `try/except` 里的主体 → 单独一个函数，异常处理留在外面
- 循环体的单次处理 → 单独一个函数
- 多分支 `if/elif` 的各个分支 → 各自一个函数
- 一长串参数校验 → 单独一个 `_validate_xxx()`

## 合理的例外

- 自动生成的代码（表驱动、协议常量）：加
  `# harnesslint: disable-file HX101 reason=由代码生成器产出，手改会被覆盖`
- 密集的数据表/字面量：考虑挪到 `types/` 或独立数据文件，而不是放宽阈值
